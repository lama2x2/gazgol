# 13.1 HTTP, REST и сеть

## Что происходит, когда вводишь URL (вопрос в 23% интервью):
1. **Разбор URL** и проверка кэшей: HSTS (сразу HTTPS), кэш браузера
2. **DNS**: кэш браузера и ОС → резолвер провайдера → корневые серверы → TLD → авторитетный сервер; получаем IP (запись A/AAAA, возможно через CNAME)
3. **TCP**: тройное рукопожатие SYN → SYN-ACK → ACK (в HTTP/3 вместо TCP — QUIC поверх UDP)
4. **TLS**: согласование версии и шифров, сертификат сервера проверяется по цепочке до доверенного корня, обмен ключами (ECDHE) → симметричное шифрование. TLS 1.3 — одна поездка туда-обратно
5. **HTTP-запрос**: `GET / HTTP/1.1`, заголовки `Host`, `Cookie`, `Accept-Encoding`…
6. **На стороне сервера**: CDN или балансировщик → reverse proxy (nginx) → сервер приложения (gunicorn/uvicorn) → фреймворк → БД и кэши → ответ
7. **Ответ**: статус, заголовки (`Content-Type`, `Cache-Control`, `Set-Cookie`), тело (часто сжатое gzip/br)
8. **Браузер**: разбирает HTML, строит DOM, догружает CSS, JS и картинки (повторно используя соединение), рендерит

Хороший ответ — уверенно по шагам, с готовностью углубиться в любой: DNS-кэширование и TTL, что внутри TLS, как балансировщик выбирает бэкенд.

## TCP и UDP:
| | TCP | UDP |
|---|---|---|
| соединение | есть (рукопожатие) | нет |
| доставка | гарантированная, по порядку, с повторами | без гарантий |
| управление потоком и перегрузкой | есть | нет |
| где | HTTP/1–2, БД, почта | DNS, видео и голос, игры, QUIC (HTTP/3) |

## Версии HTTP:
- **HTTP/1.1** — keep-alive (несколько запросов в одном соединении, но по очереди — head-of-line blocking), поэтому браузеры открывают по 6 соединений на хост
- **HTTP/2** — бинарный протокол, мультиплексирование потоков в одном соединении, сжатие заголовков (HPACK)
- **HTTP/3** — поверх QUIC (UDP): потеря пакета не тормозит остальные потоки, быстрое установление соединения, миграция при смене сети

## Методы — безопасность и идемпотентность:
| Метод | Безопасный (не меняет состояние) | Идемпотентный (повтор = тот же эффект) | Тело |
|---|---|---|---|
| GET, HEAD, OPTIONS | да | да | нет |
| PUT | нет | **да**: заменяет ресурс целиком | да |
| DELETE | нет | **да**: второй раз удалять уже нечего | обычно нет |
| POST | нет | **нет**: два POST — два заказа | да |
| PATCH | нет | не обязательно | да |

**Ключ идемпотентности**: клиент генерирует `Idempotency-Key` и шлёт его с POST. Сервер запоминает ответ по ключу; повтор (после таймаута, сбоя сети) получает тот же ответ, а операция не выполняется второй раз. Если с тем же ключом пришло **другое** тело — ошибка 409/422. Так делают платёжные API (Stripe, ЮKassa).

## Коды ответов, которые надо знать:
| Код | Когда |
|---|---|
| 200, 201 (+ `Location`), 204 | успех, создано, нет тела |
| 301 / 302 / 307 / 308 | перенаправления: постоянное или временное; 307 и 308 сохраняют метод |
| 304 | не изменилось (условный запрос с `ETag`/`If-None-Match`) |
| 400, 422 | плохой запрос, ошибка валидации (FastAPI отдаёт 422) |
| 401 / 403 | не аутентифицирован / аутентифицирован, но нет прав |
| 404, 405, 409 | нет ресурса, метод не поддерживается, конфликт состояния |
| 429 | слишком много запросов (+ `Retry-After`) |
| 500, 502, 503, 504 | ошибка сервера, плохой ответ апстрима, недоступен, таймаут апстрима |

::: quiz choice q131-1 собес
Клиент отправил `POST /payments`, соединение оборвалось по таймауту, ответа нет. Клиент не знает, прошёл ли платёж. Как спроектировать API, чтобы повтор был безопасен?
- [ ] запретить клиенту повторять запросы
- [ ] заменить POST на GET
- [x] клиент передаёт уникальный `Idempotency-Key`; сервер атомарно сохраняет ключ вместе с результатом, а на повтор с тем же ключом возвращает сохранённый ответ, не проводя платёж снова
- [ ] проверять, нет ли платежа с такой же суммой за последнюю минуту
--- why
Повторы неизбежны: таймауты, ретраи в клиентах и балансировщиках. Проверка «такая же сумма» ломает законные повторные покупки. Ключ нужно сохранять в той же транзакции, что и сам платёж (или с уникальным ограничением), а параллельный повтор, пока первый ещё выполняется, должен ждать или получить 409.
:::

## REST — договорённости:
- ресурсы — существительные во множественном числе: `GET /users/42/orders`, а не `/getUserOrders`
- действие выражает метод; для операций, которые не ложатся на CRUD, — подресурс: `POST /orders/42/cancel`
- фильтры, сортировка, пагинация — в query: `?status=paid&sort=-created_at&limit=20&cursor=…`
- **пагинация**: `OFFSET` медленный на дальних страницах и «пляшет» при вставках → курсорная (keyset): `WHERE (created_at, id) < (:last_created, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20`
- версионирование: `/v1/…` или заголовок; обратно совместимые изменения — только добавление полей
- ошибки — единым форматом (RFC 9457 Problem Details: `type`, `title`, `detail`)

## Аутентификация:
| | Сессия + cookie | JWT |
|---|---|---|
| где состояние | на сервере (Redis, БД) | в самом токене, подписанном сервером |
| отзыв | удалить сессию — мгновенно | сложно: короткий срок жизни плюс refresh-токен и чёрный список |
| масштабирование | нужно общее хранилище сессий | проверка подписи без обращения к хранилищу |
| риски | CSRF (нужны `SameSite`, CSRF-токен) | кража токена; нельзя хранить секреты в payload — он только подписан, не зашифрован |

JWT — три части в base64url: `header.payload.signature`, подпись HS256 = HMAC-SHA256 от `header.payload` общим секретом (или RS256/ES256 — асимметричная пара ключей). **OAuth 2.0** — делегирование доступа (вход через Google), **OpenID Connect** — аутентификация поверх него.

**CORS** — браузер не даёт JS с одного источника читать ответы другого, пока сервер не разрешит (`Access-Control-Allow-Origin`; для «непростых» запросов — предварительный `OPTIONS`). Это защита пользователей браузера, а не сервера: `curl` CORS не знает.

* `parse_request` — разобрать сырой HTTP/1.1-запрос в байтах: метод, путь, параметры query, заголовки без учёта регистра, тело по `Content-Length` {test_parse_request}
+ Раздели по `b"\r\n\r\n"` на заголовки и тело. Первая строка — `метод цель версия`. `urllib.parse.urlsplit` и `parse_qs` для пути и query. Заголовки — в словарь с ключами в нижнем регистре; `partition(":")` и `strip()`. Тело — первые `Content-Length` байт.
! Значение заголовка может содержать `:` (`Host: example.com:8080`). Повторяющийся параметр query — список значений. Битый запрос (нет пустой строки после заголовков, кривая стартовая строка) — `ValueError`.
* `Router` — маршрутизатор с параметрами пути `/users/{id:int}/orders/{name}` и различием 404 и 405 {test_router}
+ `add(method, pattern, handler)` преобразует шаблон в регулярное выражение: `{id:int}` → `(?P<id>\d+)`, `{name}` → `(?P<name>[^/]+)`. `resolve(method, path)` перебирает маршруты; совпал путь и метод — вернуть `(handler, params)` с приведёнными типами.
! Путь совпал, а метод нет — `MethodNotAllowed` с набором допустимых методов (для заголовка `Allow`), ничего не совпало — `NotFound`. `re.fullmatch`, иначе `/users/1/extra` совпадёт с `/users/{id}`.
* `IdempotencyStore` — хранилище ответов по ключу идемпотентности {test_idempotency}
+ `run(key, body, handler)`: если ключа нет — вызвать `handler()`, сохранить `(хеш тела, ответ)`, вернуть ответ. Если ключ есть и хеш совпал — вернуть сохранённое, не вызывая `handler`. Если тело другое — `IdempotencyConflict`. Если `handler` упал — ничего не сохранять.
! Хеш тела — `hashlib.sha256(body).hexdigest()`, тело — `bytes`. Ключи живут `ttl` секунд (часы — параметром).
* `jwt_encode` / `jwt_decode ★` — JWT HS256 на `hmac` и `base64` без библиотек {test_jwt}
+ base64url без `=` в конце: `base64.urlsafe_b64encode(b).rstrip(b"=")`; при декодировании добавь `=` до кратности 4. Заголовок `{"alg": "HS256", "typ": "JWT"}`, JSON — `json.dumps(…, separators=(",", ":"))`. Подпись — `hmac.new(secret, f"{h}.{p}".encode(), hashlib.sha256).digest()`.
! Сравнивай подписи через `hmac.compare_digest`, а не `==` (атака по времени). Проверь `alg == "HS256"` (атака `alg: none`). Истёкший `exp` (часы — параметром) — `TokenExpired`, плохая подпись или формат — `InvalidToken`.
:::

## Вопросы с собеседования по уроку:
::: quiz open q131-2 собес
Чем отличаются PUT, PATCH и POST? Что такое идемпотентность и зачем она бэкенду?
--- answer
POST создаёт ресурс или запускает действие; не идемпотентен — два одинаковых POST создадут два заказа. PUT заменяет ресурс целиком по известному адресу (или создаёт его там); идемпотентен — повтор даёт то же состояние. PATCH частично изменяет ресурс; идемпотентность не гарантирована (`{"op": "increment"}` — нет, `{"name": "x"}` — да). GET, HEAD, OPTIONS — безопасные (не меняют состояние) и идемпотентные; DELETE — идемпотентен по эффекту, хотя код ответа при повторе может быть 404. Идемпотентность нужна, потому что в распределённой системе повторы неизбежны: таймауты, обрывы сети, автоматические ретраи в клиентах, балансировщиках и очередях. Если операция идемпотентна, её можно безопасно повторить. Для неидемпотентных операций (платежи, создание заказа) используют ключ идемпотентности: клиент генерирует ключ, сервер сохраняет результат по нему атомарно с операцией и на повтор отдаёт сохранённый ответ. Та же идея — в консьюмерах очередей (дедупликация по id сообщения) и в фоновых задачах.
--- points
- семантика POST, PUT, PATCH
- безопасные и идемпотентные методы
- почему повторы неизбежны
- ключ идемпотентности и атомарное сохранение
- идемпотентные консьюмеры и задачи
:::

::: quiz open q131-3 собес
Сессии или JWT — что выбрать для аутентификации и почему?
--- answer
Сессия: сервер хранит состояние (в Redis или БД), клиент получает cookie с непредсказуемым идентификатором (`HttpOnly`, `Secure`, `SameSite`). Плюсы — мгновенный отзыв (выход, бан, смена пароля), маленькая cookie, секреты не уходят клиенту. Минусы — нужно общее хранилище сессий и обращение к нему на каждый запрос, защита от CSRF. JWT: подписанный токен с данными (id пользователя, роли, `exp`), проверяется без хранилища по подписи — удобно для микросервисов и сторонних клиентов. Минусы — трудно отозвать до истечения срока, поэтому короткий access-токен (минуты) плюс refresh-токен (хранится и отзывается на сервере), в payload нельзя класть секреты, токен растёт, частые ошибки реализации (`alg: none`, слабый секрет, отсутствие проверки `exp` и `aud`). Для классического веб-приложения с браузером обычно проще и безопаснее сессии. Для API с мобильными клиентами и межсервисных вызовов — JWT (часто выпускаемые внешним Identity Provider по OAuth 2.0/OIDC), с коротким сроком жизни. Где хранить в браузере: `HttpOnly`-cookie лучше `localStorage` (XSS не украдёт).
--- points
- состояние на сервере против в токене
- отзыв: мгновенный против сложного, refresh-токены
- масштабирование и микросервисы
- риски: CSRF против кражи токена и ошибок реализации
- рекомендации по выбору и хранению
:::
