# 14.1 Кэши, очереди, фоновые задачи, надёжность

## Redis — для чего его берут:
| Задача | Структура Redis |
|---|---|
| кэш | строка с `SET key value EX 60` |
| сессии | хеш, TTL |
| счётчики и rate limit | `INCR` + `EXPIRE`, Lua-скрипт для атомарности |
| распределённая блокировка | `SET key token NX PX 30000`; снимать — только своим токеном (Lua) |
| очереди, брокер Celery | списки (`LPUSH`/`BRPOP`), streams с группами потребителей |
| лидерборды | отсортированные множества (`ZADD`, `ZRANGE`) |
| pub/sub | каналы (без гарантий доставки) |

Однопоточное выполнение команд → каждая команда атомарна. Персистентность — RDB-снимки и/или AOF-журнал; при заполнении памяти — политика вытеснения (`allkeys-lru`, `volatile-ttl`…).

## Стратегии кэширования:
- **cache-aside** (чаще всего): приложение читает кэш, при промахе — БД, затем пишет в кэш. При изменении данных — **удалить** ключ (а не обновить: так меньше гонок)
- **write-through**: запись идёт в кэш и БД синхронно
- **write-behind**: запись в кэш, а в БД — асинхронно (быстро, но риск потери)
- проблемы: **stampede** (одновременный промах горячего ключа), **инвалидация**, **холодный старт**, рассинхронизация между кэшем и БД

## Очереди и брокеры: RabbitMQ против Kafka (вопрос в 17% интервью):
| | RabbitMQ | Kafka |
|---|---|---|
| модель | брокер очередей: сообщение доставляется потребителю и удаляется после подтверждения | распределённый журнал: сообщения хранятся заданное время, потребители читают со своего смещения (offset) |
| маршрутизация | богатая: exchanges (direct, topic, fanout), routing keys | топики и партиции, ключ определяет партицию |
| порядок | в рамках очереди | в рамках партиции |
| повторное чтение | нет (сообщение удалено) | да: можно перечитать с любого offset |
| масштаб | тысячи–десятки тысяч сообщений в секунду | сотни тысяч–миллионы, горизонтально по партициям |
| для чего | задачи, команды, RPC, сложная маршрутизация (Celery) | поток событий, event sourcing, аналитика, интеграция сервисов, CDC |

## Гарантии доставки:
- **at-most-once** — может потеряться, но не придёт дважды (подтверждение до обработки)
- **at-least-once** — не потеряется, но может прийти **повторно** (подтверждение после обработки). Стандарт де-факто, поэтому потребитель обязан быть **идемпотентным**: дедупликация по id сообщения, `UPSERT`, условные обновления
- **exactly-once** — в общем случае недостижимо; на практике это at-least-once плюс идемпотентная обработка (Kafka даёт exactly-once в связке транзакций продюсера и консьюмера внутри Kafka)

## Transactional outbox:
Проблема: нужно и записать заказ в БД, и отправить событие `OrderCreated` в брокер. Если сделать два шага, между ними может случиться сбой: заказ есть, события нет (или наоборот). Решение — в **той же транзакции** записать событие в таблицу `outbox`; отдельный процесс-релей читает неотправленные записи, публикует их в брокер и помечает отправленными. Доставка — at-least-once, поэтому потребители идемпотентны.

::: quiz choice q141-1 собес
Celery-задача списывает деньги и отправляет чек. Воркер упал после списания, задача выполнилась повторно. Что спасает от двойного списания?
- [ ] `acks_late=False` — подтверждать задачу сразу при получении
- [x] идемпотентная задача: уникальный id операции, проверка «уже выполнено» и списание в одной транзакции с записью этого id (или условный UPDATE/уникальное ограничение)
- [ ] увеличить число ретраев
- [ ] запускать задачу синхронно
--- why
С `acks_late=True` задача подтверждается после выполнения, поэтому при падении воркера она придёт снова — это at-least-once. Без `acks_late` задача может просто потеряться. Значит, повтор нужно сделать безопасным. Сюда же: `transaction.on_commit`, чтобы задача стартовала только после коммита, таймауты на внешние вызовы и `retry` с экспоненциальной задержкой.
:::

## Надёжность при вызовах других сервисов:
- **таймауты** на всё: подключение, чтение, общий дедлайн запроса. Без таймаута зависший сервис забирает все воркеры
- **ретраи** — только для идемпотентных операций и временных ошибок (таймаут, 503, обрыв), с **экспоненциальной задержкой и джиттером**: `delay = random(0, min(cap, base · 2^attempt))`. Без джиттера все клиенты повторяют синхронно и добивают сервис («thundering herd»)
- **circuit breaker** — после серии ошибок перестаём звать сервис на время, отвечаем запасным вариантом, затем пробуем пропустить один запрос (half-open)
- **rate limiting** и **bulkhead** — ограничить нагрузку и изолировать пулы ресурсов
- **graceful degradation**: кэш, значение по умолчанию, отключение функции

::: quiz output q141-2
Что выведет программа?
```python
def backoff(attempt, base=0.1, cap=2.0):
    return min(cap, base * 2 ** attempt)

print([backoff(a) for a in range(7)])
```
--- answer
[0.1, 0.2, 0.4, 0.8, 1.6, 2.0, 2.0]
--- why
Экспонента быстро растёт, поэтому её ограничивают сверху (`cap`). В реальном коде к этому добавляют случайность: «full jitter» — `random.uniform(0, backoff(a))`. Так повторы разных клиентов разносятся во времени.
:::

+ `handle(msg)` смотрит `msg["id"]`: если id уже в `processed` — вернуть `"duplicate"`. Иначе вызвать `handler(msg)`; если он успешен — запомнить id и вернуть `"ok"`; если упал — **не** запоминать и пробросить исключение (брокер доставит ещё раз).
! Хранилище обработанных id ограничено: храни не больше `max_ids` последних (`OrderedDict` или `deque` + множество) — иначе память растёт бесконечно.
* `OutboxService` — заказ и событие в одной транзакции SQLite, релей публикует неотправленные события {test_outbox}
+ `create_order(user_id, total)`: в `with conn:` вставь заказ и строку в `outbox(event, payload, sent=0)`. `relay(publish)`: выбери неотправленные по `id`, для каждой вызови `publish(event, payload_dict)`; успех — `sent = 1`; ошибка — остановись (порядок важен), остальные отправятся в следующий раз.
! Если вставка заказа упала, события быть не должно (и наоборот) — проверяется. Повторный `relay` не отправляет уже отправленное.
* `HashRing ★` — консистентное хеширование с виртуальными узлами: ключ → узел; при добавлении узла переезжает малая доля ключей {test_hash_ring}
+ Для каждого узла положи `vnodes` точек `hash(f"{node}#{i}")` в отсортированный список. Узел ключа — первая точка по часовой стрелке: `bisect` по `hash(key)`, при выходе за конец — точка 0. Хеш — стабильный: `int(hashlib.md5(s.encode()).hexdigest()[:16], 16)`, а не встроенный `hash()`.
! Встроенный `hash()` для строк рандомизирован между запусками — кольцо будет разным на каждом сервере. Тест проверяет, что при добавлении пятого узла к четырём переехало ~20% ключей (не больше 30%), а при простом `hash % n` переехали бы ~80%.

## Вопросы с собеседования по уроку:
::: quiz open q141-3 собес
RabbitMQ или Kafka — что выбрать? Как обеспечить, чтобы сообщения не терялись и не обрабатывались дважды?
--- answer
RabbitMQ — классический брокер очередей: гибкая маршрутизация (exchanges), подтверждения потребителем, сообщение удаляется после обработки, удобен для задач и команд (Celery), RPC, приоритетов и отложенной доставки. Kafka — распределённый журнал: события хранятся заданное время, потребители читают с собственного offset и могут перечитывать, порядок гарантирован в партиции (ключ партиционирования — например, id заказа), огромная пропускная способность, горизонтальное масштабирование, хорош для потоков событий между сервисами, аналитики и CDC. Чтобы не терять: на стороне продюсера — подтверждения записи (publisher confirms, `acks=all` в Kafka), устойчивые очереди и репликация; запись события вместе с данными через transactional outbox; у потребителя — подтверждение (ack/commit offset) только после успешной обработки. Это даёт at-least-once, поэтому против дублей — идемпотентный потребитель: дедупликация по id сообщения в той же транзакции, что и эффект, upsert-ы и условные обновления. Сообщения, которые постоянно падают, — в DLQ после N попыток, с алертом.
--- points
- RabbitMQ: очереди, маршрутизация, задачи
- Kafka: журнал, offset, партиции, перечитывание, масштаб
- не терять: подтверждения продюсера, outbox, ack после обработки
- at-least-once → идемпотентный потребитель
- DLQ и мониторинг
:::

::: quiz open q141-4 собес
Как сделать вызов внешнего сервиса надёжным?
--- answer
Таймауты на подключение и чтение плюс общий дедлайн запроса — обязательно. Ретраи — только для временных ошибок (таймауты, 502/503/504, обрыв соединения) и только для идемпотентных операций (или с ключом идемпотентности), с экспоненциальной задержкой, потолком и джиттером, с ограничением числа попыток и общего времени (бюджет ретраев, чтобы не умножать нагрузку). Circuit breaker: после доли ошибок выше порога размыкаемся, сразу отдаём ошибку или запасной ответ, через время пропускаем пробный запрос. Bulkhead — отдельный пул соединений или семафор на зависимость, чтобы медленный сервис не съел все ресурсы. Graceful degradation — кэш, устаревшие данные, отключение второстепенной функции. Асинхронность там, где ответ не нужен сразу: очередь вместо синхронного вызова. Наблюдаемость: метрики задержек и ошибок по зависимости, трассировка, алерты. В Python — `httpx` с `Timeout`, `tenacity` для ретраев, `aiobreaker`/`pybreaker`.
--- points
- таймауты и дедлайн
- ретраи: временные ошибки, идемпотентность, backoff + jitter, лимит
- circuit breaker
- bulkhead, rate limit
- деградация и асинхронность через очередь
- метрики и трассировка
:::
