# 11.1 Задачи «как в продакшене»

## Чем практический лайвкод отличается от алгоритмического:
На платформенной секции (Авито, Ozon, Kaspersky, Т-Банк) часто дают не LeetCode, а маленькую рабочую задачу: кэш, разбор логов, синхронизация данных, ретраи. Алгоритм там обычно простой. Оценивают:
- **понимание требований**: какие данные, сколько их, что делать с ошибками, нужна ли потокобезопасность
- **идиоматичный Python**: `collections`, генераторы, контекстные менеджеры, `dataclass`, аннотации
- **инженерные вопросы**: память на больших данных, сложность, граничные случаи, тестируемость (время и случайность — параметрами)
- **развитие решения**: «а если данных в 100 раз больше?», «а если из нескольких потоков?», «а если упадёт посередине?»

::: py Как отвечать на «а если…»
Не переписывай молча. Сначала назови, что сломается («Counter не влезет в память», «два потока одновременно пройдут проверку»), потом — варианты с компромиссами («разбить по хешу на файлы — точно, но медленно; Count-Min Sketch — приближённо и в фиксированной памяти»), потом спроси, что важнее. Это и есть сигнал middle+.
:::

## LRU-кэш — самая частая задача этого типа:
```python
from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity):
        self.capacity = capacity
        self.data = OrderedDict()

    def get(self, key, default=None):
        if key not in self.data:
            return default
        self.data.move_to_end(key)            # стал самым свежим
        return self.data[key]

    def put(self, key, value):
        self.data[key] = value
        self.data.move_to_end(key)
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)     # выкинуть самый старый
```
Следующие вопросы интервьюера: «без `OrderedDict`» (словарь + двусвязный список, урок 8.2), «с TTL», «потокобезопасно» (`threading.Lock` вокруг операций), «чем `functools.lru_cache` отличается» (кэширует функцию по аргументам, без TTL, есть `cache_info`).

::: solve Синхронизация с «плохим» API (задача с собесов middle)
«Раз в час скачиваем JSON из 100 000+ объектов с первичным ключом. Нужно создать новые записи, обновить изменившиеся и пометить удалёнными те, которых нет в выгрузке».

*«Наивно — запрос в БД на каждую запись: 100 000 запросов. Лучше построить два словаря "id → данные": из выгрузки и из базы (или батчами по 1000 id), — и посчитать три множества: `api - db` создать, `db - api` удалить, пересечение с отличающимися данными — обновить. Это O(n). Запись — пакетно: `executemany`, `INSERT … ON CONFLICT DO UPDATE`, или загрузка во временную таблицу и три SQL-запроса. Если выгрузка не влезает в память — стримить JSON (ijson) и сравнивать батчами, отсортированными по id».*
```python
def sync_diff(db: dict, api: dict):
    db_ids, api_ids = db.keys(), api.keys()
    create = sorted(api_ids - db_ids)
    delete = sorted(db_ids - api_ids)
    update = sorted(k for k in api_ids & db_ids if api[k] != db[k])
    return create, update, delete
```
`dict.keys()` поддерживает операции множеств — это часто забывают.
:::

Тебя просят посчитать p95 времени ответа по логу. Что верно?
- [ ] p95 — это среднее, умноженное на 0.95
- [x] p95 — значение, ниже которого 95% наблюдений; его считают по отсортированным значениям (или приближённо — гистограммой или t-digest на потоке), а усреднять p95 разных серверов нельзя
- [ ] p95 всегда меньше среднего
- [ ] p95 считают как максимум за 95 секунд
--- why
Перцентили — основная метрика задержек: среднее прячет хвосты. Точный p95 требует хранить или сортировать значения; в мониторинге используют гистограммы (Prometheus `histogram_quantile`) или t-digest. Среднее p95 по нескольким серверам — не p95 всего трафика; правильно сливать гистограммы.

! Не запускай фоновый поток для очистки: ленивое удаление при обращении проще и тестируемо. Сравнение со временем — строгое: в момент `expires_at` запись уже мертва.
* `sync_diff` — что создать, обновить и удалить при синхронизации базы с выгрузкой API {test_sync_diff}
+ Операции множеств над `keys()`, как в разборе. Верни `(create, update, delete)` — три отсортированных списка id.
! Сравнение «изменилось» — по значениям словарей целиком. Тест на 200 000 записей: вложенный поиск по спискам не уложится.
* `flatten_json` — развернуть вложенный JSON в плоский словарь с ключами через точку, индексы списков — числами {test_flatten_json}
+ Рекурсивная функция `walk(prefix, value)`: для словаря — `walk(f"{prefix}.{k}" if prefix else k, v)`, для списка — то же с индексом, иначе `out[prefix] = value`. Пустые `{}` и `[]` сохраняй как значения.
! Корень-скаляр: `flatten_json(5)` → `{"": 5}`. Ключи словарей — строки, но могут содержать цифры — это не индексы.
* `endpoint_stats ★` — по строкам лога посчитать для каждого эндпоинта число запросов, долю ошибок 5xx и p95 времени ответа {test_endpoint_stats}
+ Строка: `"2026-10-14T10:00:00 GET /api/users 200 12ms"`. Ключ — `(метод, путь)`. Собери времена в списки, ошибки — счётчиком. p95 по методу nearest-rank: отсортируй, индекс `ceil(0.95 * n) - 1`. Доля ошибок округляется до 3 знаков.
! Битые строки пропускай. Путь с query-строкой (`/api/users?page=2`) относится к пути без неё. Тест проверяет p95 на 1, 20 и 100 значениях.

## Вопросы с собеседования по уроку:
::: quiz open q111-2 собес
Как бы ты сделал кэш для сервиса, который ходит в медленное внешнее API? Какие вопросы надо решить?
--- answer
Сначала требования: насколько свежими должны быть данные (TTL), объём и число ключей (память, вытеснение — LRU/LFU), один процесс или много (локальный кэш в памяти против общего Redis), допустимы ли устаревшие данные при недоступности API. Устройство: cache-aside — читаем кэш, при промахе идём в API и кладём результат с TTL. Проблемы и решения: **cache stampede** — когда горячий ключ истёк, тысяча запросов одновременно идёт в API; лечится блокировкой или singleflight («один загружает, остальные ждут»), ранним фоновым обновлением, случайным разбросом TTL. **Инвалидация** — по событию об изменении или по TTL. **Отрицательное кэширование** — кэшировать «не найдено» на короткое время. **Отказ API** — отдавать устаревшее значение (stale-while-revalidate), circuit breaker. **Двухуровневый кэш**: локальный LRU плюс Redis. Метрики: hit rate, задержки, размер. Сериализация и размер значений в Redis, а ключи — с версией схемы, чтобы безопасно выкатывать изменения формата.
--- points
- требования: свежесть, объём, один или много процессов
- cache-aside и TTL, вытеснение LRU
- stampede и singleflight, разброс TTL
- инвалидация и отрицательное кэширование
- поведение при отказе API: stale, circuit breaker
- метрики hit rate и версия ключей
:::
