# 12.2 Индексы, транзакции, изоляция, блокировки

## Индекс — как он устроен:
Обычный индекс в PostgreSQL и MySQL — **B+-дерево**: отсортированные ключи в широких узлах размером со страницу диска (8 КБ), листья связаны в список. Поиск по равенству и диапазону — O(log n) с очень маленькой высотой (3–4 уровня на миллионы строк), плюс последовательное чтение листьев для диапазона и `ORDER BY`. Цена — место на диске и замедление записи: каждый `INSERT`/`UPDATE` обновляет все индексы таблицы.

## Составной индекс `(a, b, c)` и правило левого префикса:
Строки отсортированы по `a`, при равных `a` — по `b`, затем по `c`. Поэтому индекс помогает для условий на `a`, `a и b`, `a и b и c`, для `a = ? ORDER BY b`, но **не** для условия только на `b` или `c`. Столбцы с равенством — первыми, столбец диапазона или сортировки — после них.

## Когда индекс не помогает (вопрос в 27% интервью):
- функция или выражение над столбцом: `WHERE lower(email) = …`, `WHERE created_at::date = …` → нужен индекс по выражению или переписать условие диапазоном
- `LIKE '%текст'` — с ведущим `%` (для поиска подстроки — триграммы `pg_trgm` или полнотекстовый поиск)
- низкая селективность: `WHERE status = 'active'`, когда активны 90% строк, — полное сканирование дешевле
- условие не на левый префикс составного индекса
- несовпадение типов, неявное приведение
- `OR` по разным столбцам (иногда спасает Bitmap Or)
- маленькая таблица — планировщику проще прочитать её целиком
- устаревшая статистика — планировщик ошибается в оценках (`ANALYZE`)

**Покрывающий индекс**: если все нужные столбцы есть в индексе (`INCLUDE (…)` в PostgreSQL), база не ходит в таблицу — Index Only Scan.

::: quiz choice q122-1 собес
Есть индекс `(user_id, status, created_at)`. Какие запросы смогут эффективно его использовать? Отметь все.
- [x] `WHERE user_id = 7`
- [x] `WHERE user_id = 7 AND status = 'paid' ORDER BY created_at DESC LIMIT 20`
- [ ] `WHERE status = 'paid'`
- [ ] `WHERE created_at > '2026-01-01'`
- [x] `WHERE user_id = 7 AND created_at > '2026-01-01'` (частично: поиск по `user_id`, дальше фильтр)
--- why
Правило левого префикса. Второй запрос — идеальный случай: два равенства и сортировка по следующему столбцу, база читает 20 записей подряд из индекса и не сортирует. В последнем запросе пропущен `status`, поэтому по `created_at` индекс уже не упорядочен — используется только префикс `user_id`.
:::

## EXPLAIN — читать план запроса:
```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 7 ORDER BY created_at DESC LIMIT 20;
-- Limit (actual time=0.05..0.09 rows=20)
--   -> Index Scan Backward using orders_user_created on orders (rows=20)
--        Index Cond: (user_id = 7)
```
| Узел | Что значит |
|---|---|
| Seq Scan | читаем всю таблицу |
| Index Scan | по индексу находим строки, читаем их из таблицы |
| Index Only Scan | всё есть в индексе, в таблицу не ходим |
| Bitmap Heap Scan | собрали битовую карту страниц по индексу(ам), читаем страницы по порядку |
| Nested Loop / Hash Join / Merge Join | способы соединения: для маленького внешнего набора, для больших несортированных, для отсортированных |
| Sort, «external merge Disk» | сортировка, не влезла в `work_mem` |

`EXPLAIN` — только план и **оценки**, `EXPLAIN ANALYZE` — **выполняет** запрос и показывает реальное время и число строк. Большое расхождение `rows` оценки и факта — признак устаревшей статистики. Осторожно: `EXPLAIN ANALYZE` для `UPDATE`/`DELETE` реально меняет данные — оборачивай в транзакцию с `ROLLBACK`.

## ACID:
- **Atomicity** — транзакция выполняется целиком или никак
- **Consistency** — после транзакции соблюдаются все ограничения (ключи, `CHECK`, `UNIQUE`)
- **Isolation** — параллельные транзакции не мешают друг другу (насколько — задаёт уровень изоляции)
- **Durability** — подтверждённое не потеряется при сбое (журнал WAL сбрасывается на диск до ответа «COMMIT»)

## Уровни изоляции и аномалии:
| Уровень | Грязное чтение | Неповторяющееся чтение | Фантомы | Аномалия сериализации |
|---|---|---|---|---|
| Read Uncommitted | возможно (в PostgreSQL — нет) | возможно | возможно | возможно |
| **Read Committed** (PostgreSQL по умолчанию) | нет | возможно | возможно | возможно |
| Repeatable Read | нет | нет | в стандарте возможно, в PostgreSQL — нет | возможно |
| Serializable | нет | нет | нет | нет |

- **неповторяющееся чтение**: в одной транзакции прочитал строку дважды — значения разные, потому что между чтениями кто-то закоммитил изменение
- **фантом**: повторный запрос с тем же условием вернул новые строки
- **потерянное обновление**: обе транзакции прочитали баланс 100, обе записали «100 − 30» — одно списание пропало. Лечится атомарным `UPDATE … SET balance = balance - 30`, `SELECT … FOR UPDATE` или оптимистической версией
- PostgreSQL реализует изоляцию через **MVCC**: у строки несколько версий, читатель видит снимок и не блокирует писателя. Repeatable Read в нём — изоляция снимка. Serializable (SSI) может отменить транзакцию с ошибкой сериализации — приложение обязано **повторить** её

## Блокировки:
- `SELECT … FOR UPDATE` — заблокировать строки до конца транзакции (пессимистично). `NOWAIT` — сразу ошибка, если занято; `SKIP LOCKED` — пропустить занятые строки (очередь задач в таблице: каждый воркер берёт свои)
- **оптимистичная блокировка**: столбец `version`, `UPDATE … WHERE id = ? AND version = ?`; обновилось 0 строк — кто-то успел раньше, перечитать и повторить. Хороша, когда конфликты редки
- **deadlock** между транзакциями — база найдёт цикл и отменит одну. Лечится одинаковым порядком обновления строк и короткими транзакциями

::: quiz choice q122-2 собес
Два запроса одновременно покупают последний товар: `SELECT stock …; if stock > 0: UPDATE products SET stock = stock - 1`. На Read Committed что может произойти и как исправить?
- [ ] ничего, транзакция защищает
- [x] оба прочитают `stock = 1` и оба продадут — товар уйдёт в минус; исправить атомарным условным `UPDATE … SET stock = stock - 1 WHERE id = ? AND stock > 0` (проверить число изменённых строк), или `SELECT … FOR UPDATE`, или `CHECK (stock >= 0)`
- [ ] база выдаст deadlock
- [ ] второй запрос всегда увидит обновлённое значение
--- why
Read Committed не защищает от гонки «прочитал — решил — записал». Самое простое и быстрое решение — перенести проверку внутрь `UPDATE`: строка блокируется на время обновления, второй запрос дождётся и увидит `stock = 0`. Ограничение `CHECK` — страховка на уровне данных.
:::

## Вопросы с собеседования по уроку:
::: quiz open q122-3 собес
Как работают индексы и когда они не помогают? Как бы ты ускорил медленный запрос?
--- answer
B-tree-индекс хранит отсортированные ключи со ссылками на строки, поиск — O(log n) с малой высотой, плюс быстрые диапазоны и сортировка. Составной индекс работает по левому префиксу: сначала столбцы с равенством, затем диапазон или сортировка. Покрывающий индекс (`INCLUDE`) позволяет Index Only Scan. Индекс не помогает при функции над столбцом, `LIKE '%…'`, низкой селективности, условии не на префикс, приведении типов, на маленьких таблицах и при устаревшей статистике; каждый индекс замедляет запись и занимает место. Алгоритм ускорения: найти запрос (`pg_stat_statements`, slow log), посмотреть `EXPLAIN (ANALYZE, BUFFERS)` — где время, Seq Scan по большой таблице, сортировка на диск, расхождение оценок и факта; затем — подходящий индекс (составной, частичный `WHERE status = 'paid'`, по выражению), переписать запрос (убрать функцию со столбца, `EXISTS` вместо `IN`, keyset-пагинация вместо `OFFSET`), `ANALYZE` для статистики, уменьшить выборку (только нужные столбцы, `LIMIT`), убрать N+1 на стороне приложения, денормализация или материализованное представление для тяжёлой аналитики, кэш. Проверить результат тем же `EXPLAIN ANALYZE`.
--- points
- B-tree, O(log n), диапазоны и сортировка
- составной индекс и левый префикс, покрывающий
- случаи, когда индекс не помогает; цена на запись
- EXPLAIN ANALYZE и что в нём искать
- методы: индексы, переписать запрос, статистика, keyset, N+1, кэш
:::

::: quiz open q122-4 собес
Расскажи про уровни изоляции транзакций. Какие аномалии они предотвращают? Какой уровень по умолчанию в PostgreSQL?
--- answer
Стандарт SQL определяет четыре уровня по допускаемым аномалиям. Read Uncommitted допускает грязное чтение (видны незакоммиченные изменения других транзакций) — в PostgreSQL он ведёт себя как Read Committed. Read Committed (по умолчанию в PostgreSQL) — каждый запрос видит снимок на свой момент, поэтому возможны неповторяющееся чтение и фантомы, а также потерянное обновление при схеме «прочитал — изменил в приложении — записал». Repeatable Read — снимок на начало транзакции; в PostgreSQL это snapshot isolation, фантомов нет, но возможна аномалия write skew (две транзакции читают пересекающиеся данные и пишут разные строки, нарушая общий инвариант — например, «хотя бы один врач на дежурстве»); при конфликте записи одна транзакция получает ошибку сериализации. Serializable в PostgreSQL — SSI: результат эквивалентен последовательному выполнению, конфликтующие транзакции отменяются, и приложение должно их повторять. Реализация — MVCC: читатели не блокируют писателей. На практике — Read Committed плюс точечные средства: атомарные условные `UPDATE`, `SELECT FOR UPDATE`, оптимистичные версии, ограничения `UNIQUE`/`CHECK`, а Serializable — для сложных инвариантов с ретраями.
--- points
- четыре уровня и аномалии: грязное, неповторяющееся, фантомы
- Read Committed по умолчанию в PostgreSQL
- MVCC и снимки
- потерянное обновление и write skew
- Serializable требует повторов
- практические средства: атомарный UPDATE, FOR UPDATE, версии
:::
