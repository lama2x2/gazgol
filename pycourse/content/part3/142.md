# 14.2 System design и поведенческое интервью

## Секция system design:
С уровня middle — 45–60 минут: «спроектируй сокращатель ссылок / ленту / чат / трекинг курьеров». Правильного ответа нет, оценивают ход мысли: вопросы, оценки нагрузки, узкие места, компромиссы. По статистике system design занимает уже больше четверти времени технических интервью, а на позициях лида встречается в 78% случаев.

## План (держись его и проговаривай этапы):
1. **Требования** (5 мин): функциональные (что делаем и что **не** делаем) и нефункциональные (пользователи, RPS чтения и записи, задержка, доступность, согласованность, объём, география)
2. **Оценки** (5 мин): RPS, объём хранения на годы, трафик. Цель — порядок величин: хватит одной базы или нужен шардинг?
3. **API** (5 мин): основные эндпоинты
4. **Модель данных и хранилища** (5 мин): сущности, ключи, какая база и почему
5. **Общая схема** (10 мин): клиенты → CDN → балансировщик → stateless-сервисы → кэш, БД, очереди, объектное хранилище
6. **Углубление** (15 мин): узкие места, масштабирование, отказы, согласованность — обычно интервьюер сам скажет, куда копать
7. **Компромиссы**: что выбрали, от чего отказались и почему

## Цифры, которые надо помнить:
| Величина | Порядок |
|---|---|
| секунд в сутках | 86 400 ≈ 10⁵ |
| 1 млн запросов в сутки | ≈ 12 RPS (пик ×2–5) |
| обращение к памяти / Redis / запрос в PostgreSQL по индексу | 100 нс / ~1 мс / 1–5 мс |
| запрос между континентами | 100–150 мс |
| Python-воркер на простом эндпоинте | сотни–пара тысяч RPS (асинхронный — больше) |
| PostgreSQL на хорошем железе | десятки тысяч простых запросов в секунду; запись — узкое место |

::: quiz choice q142-1 собес
Сервис: 5 млн активных пользователей в день, каждый в среднем делает 20 запросов на чтение. Пик — ×4 от среднего. Какой порядок пикового RPS?
- [ ] ~100
- [ ] ~1 000
- [x] ~5 000
- [ ] ~500 000
--- why
5·10⁶ × 20 = 10⁸ запросов в сутки; делим на 10⁵ секунд — 1 000 RPS в среднем, в пике ×4 — около 4–5 тысяч. Это несколько инстансов сервиса, реплики БД для чтения и кэш — без экзотики. Важен не точный ответ, а то, что ты считаешь вслух и делаешь вывод о масштабе.
:::

## Кубики, из которых собирают системы:
| Кубик | Зачем |
|---|---|
| CDN | статика и медиа ближе к пользователю |
| балансировщик L4/L7, API-шлюз | распределить запросы, TLS, аутентификация, rate limit |
| stateless-сервисы | масштабируются копированием; состояние — во внешних хранилищах |
| кэш (Redis) | горячие чтения, сессии, счётчики |
| реляционная БД + реплики | источник истины, транзакции; реплики для чтения |
| шардинг | когда не влезает запись или объём: по ключу (user_id), консистентное хеширование |
| очередь / журнал (RabbitMQ, Kafka) | асинхронность, сглаживание пиков, развязка сервисов |
| объектное хранилище (S3) | файлы, фото, бэкапы |
| поисковый движок (Elasticsearch/OpenSearch) | полнотекстовый поиск, фильтры |
| генерация ID | Snowflake, UUIDv7 — уникально без центрального узла и растёт со временем |

**CAP**: при сетевом разделении приходится выбирать между согласованностью и доступностью. На практике говорят о выборе для конкретных данных: деньги и остатки — строгая согласованность, лента и счётчики лайков — eventual consistency.

::: quiz design q142-2 собес
Спроектируй сокращатель ссылок для SMS-рассылок: ссылки с метками делают SMS длиннее 70 символов, это дорого. 50 млн новых ссылок в месяц, переходов в 20 раз больше. (Задача с собеседований на Python-бэкенд.)
--- answer
**Требования.** Создать короткую ссылку для длинного URL (API для сервиса рассылок), редирект по короткой ссылке, срок жизни (рассылки живут недолго — например, 90 дней), статистика переходов. Не делаем: пользовательские алиасы, личный кабинет. Нефункциональные: редирект быстрый (< 50 мс), высокая доступность редиректа (ссылка уже ушла в SMS), запись может быть медленнее.

**Оценки.** 5·10⁷ / (30·10⁵) ≈ 20 записей в секунду; чтений ≈ 400 RPS, в пике ×5 — 2 000. Хранение: ~300 байт × 5·10⁷ × 3 месяца ≈ 45 ГБ живых данных — одна база справится. Длина кода: 62⁶ ≈ 5.7·10¹⁰ — 6 символов base62 хватит с запасом, а короткий домен (`sms.ru/aB3x9Z`) экономит символы.

**Генерация кода.** Уникальный id (последовательность БД, выдаваемая пачками, или Snowflake) → base62. Случайный код — с проверкой уникальности при вставке (UNIQUE и повтор). Хеш URL — коллизии и одинаковые ссылки для разных рассылок, не надо.

**Хранилище.** PostgreSQL: `codes(code PK, url, campaign_id, expires_at)`; партиционирование по времени — старые партиции удаляются целиком. Альтернатива — key-value (Redis с персистентностью, DynamoDB/Cassandra) при росте.

**Чтение.** Сервис редиректа stateless, несколько экземпляров за балансировщиком; Redis-кэш горячих кодов (рассылка → всплеск переходов по одним и тем же ссылкам сразу после отправки). Ответ 302 (не 301), чтобы браузер не кэшировал навсегда и переходы считались.

**Статистика.** Асинхронно: событие перехода в Kafka/RabbitMQ → ClickHouse; редирект не ждёт записи.

**Отдельно.** Отдельный ли это сервис или модуль монолита (обосновать: разный профиль нагрузки и требования к доступности — за отдельный сервис), rate limit и авторизация на создание, проверка URL на вредоносность, мониторинг доли 404 и задержки редиректа, деплой и резервирование.
--- points
- требования и что вне рамок, срок жизни
- оценки RPS и объёма, длина кода
- генерация кода без коллизий (id → base62)
- хранилище и удаление старого (партиции, TTL)
- кэш для всплесков, 302 против 301
- статистика асинхронно, отдельный сервис или нет
:::

::: quiz design q142-3 собес
Нужно сделать быстрый сервис поверх двух медленных: «профиль пользователя» (300 мс) и «рекомендации» (1 с). Менять эти сервисы нельзя — ни новых событий, ни новых контрактов. Как? (Задача из собеседования на позицию лида.)
--- answer
Раз нельзя изменить источники, остаются два рычага: **кэшировать** и **считать заранее**.
- **Параллельные запросы** к обоим сервисам (`asyncio.gather` с таймаутами): задержка = максимум, а не сумма
- **Кэш** ответов с TTL по допустимой свежести: профиль меняется редко — минуты и часы, рекомендации — десятки минут. Stale-while-revalidate: отдаём устаревшее и обновляем в фоне. Singleflight против stampede
- **Предподсчёт**: фоновые воркеры заранее прогревают кэш для активных пользователей (по логам посещений), например ночью или при входе пользователя (первый запрос запускает загрузку того, что понадобится дальше)
- **Деградация**: если рекомендации не успели к дедлайну (например, 200 мс), отдаём профиль и популярные рекомендации или пустой блок, а клиент дозагрузит их позже (отдельный эндпоинт)
- **Защита источников**: ограничение параллельных запросов к ним (они медленные — значит, и маломощные), circuit breaker, ретраи только с джиттером
- **Хранилище кэша**: Redis (общий для всех экземпляров) плюс небольшой локальный LRU
- Метрики: hit rate, доля деградированных ответов, p95/p99, нагрузка на источники

Обсудить компромисс свежести и скорости с бизнесом: насколько старые рекомендации допустимы.
--- points
- параллельные вызовы с таймаутами
- кэш с TTL и stale-while-revalidate, singleflight
- предподсчёт и прогрев
- деградация по дедлайну
- защита медленных источников: лимит, circuit breaker
- метрики и согласование свежести
:::

## Поведенческое интервью:
Отвечай по схеме **STAR**: Situation (контекст), Task (твоя задача), Action (что сделал **ты**, а не «мы»), Result (измеримый итог и выводы). Подготовь 4–5 историй, которые можно поворачивать под разные вопросы:
1. самая сложная техническая задача
2. конфликт или несогласие с коллегой или руководителем
3. ошибка или провал и что ты из этого вынес
4. ситуация, когда пришлось быстро разбираться в незнакомом
5. инициатива: что улучшил без просьбы

::: quiz open q142-4 собес
Расскажи о случае, когда ты ошибся в продакшене. Что произошло и что ты сделал? (Ответь по STAR на своём примере.)
--- answer
Пример структуры (подставь свой опыт):

**Situation.** В сервисе приёма жалоб на FastAPI я выкатил миграцию, которая добавляла `NOT NULL`-столбец с дефолтом в таблицу на 8 млн строк.

**Task.** Изменение было нужно для новой функции, выкатка — в рабочее время.

**Action.** Миграция заблокировала таблицу, запросы начали копиться, сервис отвечал ошибками около 4 минут. Я откатил релиз, подтвердил в мониторинге, что очередь рассосалась, и написал в канал инцидентов, что произошло. Потом сделал миграцию в три шага: nullable-столбец без дефолта → заполнение батчами в фоне → ограничение `NOT NULL` через `NOT VALID` и валидацию. Провёл разбор инцидента без поиска виноватых и добавил в CI проверку миграций линтером (squawk) и правило выкатывать изменения схемы отдельно от кода.

**Result.** Повторно миграция прошла без простоя. За следующие полгода похожих инцидентов не было, а чек-лист миграций стал частью шаблона пулл-реквеста.

Что оценивают: честность (без перекладывания вины), скорость реакции (сначала остановить ущерб, потом искать причину), системные выводы, а не «теперь я буду внимательнее».
--- points
- конкретная ситуация с масштабом
- своя роль и честное признание ошибки
- действия: остановить ущерб, коммуникация, исправление
- системные выводы: процесс, проверки, автоматизация
- измеримый результат
:::

::: hw 142
* `base62_encode` / `base62_decode` — короткие коды для ссылок {test_base62}
+ Алфавит `0-9a-zA-Z`. Кодирование: пока `n > 0` — `n, r = divmod(n, 62)`, символы с конца, затем развернуть; ноль — `"0"`. Декодирование: `n = n * 62 + ALPHABET.index(ch)` (или словарь «символ → цифра»).
! Отрицательное число и неизвестный символ — `ValueError`. Пустая строка — тоже ошибка. Тест проверяет обратимость на случайных числах до 2⁶⁴.
* `Snowflake` — генератор 64-битных уникальных id, растущих во времени {test_snowflake}
+ `id = (ms - epoch) << 22 | node << 12 | seq`. В той же миллисекунде — `seq += 1`; дошли до 4096 — подожди следующую миллисекунду (крути `clock()`); новая миллисекунда — `seq = 0`. Всё под `threading.Lock`. Номер узла — от 0 до 1023, иначе `ValueError`.
! Часы подменяются тестом. Если время пошло назад — `ClockMovedBackwards`: id не должны повторяться. id из 8 потоков одновременно — все уникальны.
* `UrlShortener ★` — сервис коротких ссылок в памяти: создание, свои алиасы, срок жизни, счётчик переходов {test_url_shortener}
+ Счётчик id → `base62_encode`. `shorten(url, alias=None, ttl=None)`: проверь URL (`urlsplit`: схема `http`/`https` и непустой `netloc`), алиас — 3–32 символа из алфавита base62 и не занят. Храни `code → (url, expires_at, clicks)`. `resolve(code)` увеличивает счётчик и возвращает URL; несуществующий или истёкший — `KeyError`. `stats(code)` — число переходов.
! Сгенерированный код не должен совпасть с чужим алиасом: если занят — бери следующий id. Время — из `clock()`. Истёкший код можно занять снова как алиас.
:::

## Как готовиться дальше — план и критерии:
1. Пройди тренажёры всех трёх частей; где ошибся — перечитай урок
2. Реши все домашки ★ без подсказок: это уровень лайвкода
3. Перед каждым собеседованием прогони **карточки «Вопросы с собеседований»** в конце каждой части: вслух, по таймеру, 2–3 минуты на вопрос
4. Алгоритмы: по паттернам части 2 добери задачи из NeetCode 150 или Grind 75, решая с таймером и без запуска
5. Проведи 2–3 пробных собеседования (с другом или с Claude в роли интервьюера) с разбором ошибок
6. После каждого настоящего собеседования записывай вопросы, которые застали врасплох, и добавляй в свою колоду
