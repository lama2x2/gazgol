# 11.2 Бизнес-логика: банкомат, уведомления, бронирование

## Формат:
Яндекс на Python-позициях часто даёт не алгоритм, а **бизнес-задачу**: банкомат, заказ такси, фильтр уведомлений, бронирование. Оценивают чистоту кода, обработку ошибок и то, как кандидат рассуждает. Типичный провал из реального отзыва: потратить 20 минут на модели данных и не дойти до логики фильтра.

## План на такую задачу:
1. **Сценарии и инварианты** (3–5 минут): что система должна делать, что запрещено («нельзя выдать больше, чем есть в кассетах», «бронь не пересекается с другой»), что при ошибке
2. **Минимальная модель**: `dataclass` для сущностей, `Enum` для статусов, один класс-сервис с публичными методами. Не строй иерархии «на будущее»
3. **Ядро логики** — сначала счастливый путь, затем ошибки. Ошибки — **своими исключениями**, а не `return False`
4. **Атомарность**: если операция не удалась, состояние не меняется (сначала вычисли, потом применяй)
5. **Тестируемость**: время, случайность, хранилища — параметрами
6. **Расширения вслух**: конкурентный доступ (блокировки, транзакции в БД), персистентность, масштабирование

::: solve Конечный автомат статусов заказа
Половина бизнес-задач — про допустимые переходы. Таблица переходов вместо россыпи `if`:
```python
from enum import Enum

class Status(Enum):
    CREATED = "created"
    PAID = "paid"
    SHIPPED = "shipped"
    DELIVERED = "delivered"
    CANCELLED = "cancelled"

TRANSITIONS = {
    Status.CREATED: {Status.PAID, Status.CANCELLED},
    Status.PAID: {Status.SHIPPED, Status.CANCELLED},
    Status.SHIPPED: {Status.DELIVERED},
}

class InvalidTransition(Exception):
    pass

def move(current: Status, new: Status) -> Status:
    if new not in TRANSITIONS.get(current, set()):
        raise InvalidTransition(f"{current.value} → {new.value}")
    return new
```
Новый статус добавляется правкой таблицы, а не кода. Ту же таблицу можно отрисовать для документации и проверить тестом, что из каждого статуса достижим финальный.
:::

## Банкомат и почему жадность ломается:
Выдать сумму минимальным числом купюр, если купюр **ограниченное** количество. Жадно «берём крупную, пока можно» неверно: в кассетах 50 × 1 и 20 × 3, сумма 60. Жадно — взяли 50, осталось 10, выдать нельзя. А 20 + 20 + 20 — можно. Решение — перебор от крупных номиналов с откатом (номиналов мало, перебор быстрый) или динамика по сумме.

::: quiz choice q112-1 собес
В `withdraw` банкомат посчитал, какие купюры выдать, но при выдаче второй кассеты случилась ошибка. Как должна быть устроена операция?
- [ ] уменьшать остатки в кассетах по мере подбора купюр
- [x] сначала полностью вычислить план выдачи, не трогая состояние; применить его целиком, только если план найден; при сбое применения — откатить
- [ ] записать ошибку в лог и продолжить
- [ ] вернуть пользователю частичную сумму
--- why
Это атомарность на уровне объекта: «вычислить, потом применить». В реальной системе применение — транзакция в БД, а физическая выдача — отдельный шаг с компенсацией (если купюры не вышли, вернуть остатки и отменить списание). Интервьюер ждёт, что ты сам заговоришь о том, что будет при сбое посередине.
:::

## Фильтр уведомлений (задача из реального собеса Яндекса):
«Уведомление: id, тип (EMAIL/SMS/PUSH), получатель, отправитель, текст. Применить настройки получателя (разрешённые каналы, заблокированные отправители) и не отправлять дубликаты за 24 часа». Хранилище не нужно — только контракты и логика. Ждут работающий фильтр с тремя проверками. Ключ дедупликации — `(получатель, канал, текст)`; окно — по времени отправки, часы передаются параметром.

::: quiz review q112-2 собес
Сделай код-ревью сервиса бронирования переговорок:
```python
bookings = []

def book(room, start, end, user):
    for b in bookings:
        if b["room"] == room and b["start"] < end and start < b["end"]:
            return "занято"
    bookings.append({"room": room, "start": start, "end": end, "user": user})
    return "ok"
```
--- answer
- **глобальное изменяемое состояние** — модульный список: нельзя иметь два независимых экземпляра, тесты влияют друг на друга. Класс-сервис с хранилищем, переданным в конструктор
- **нет валидации**: `start >= end`, бронь в прошлом, неизвестная комната
- **ошибки строками** («занято»/«ok»): вызывающий код должен сравнивать строки. Свои исключения: `RoomBusy`, `InvalidInterval`
- **O(n) по всем броням всех комнат** на каждое бронирование → словарь «комната → отсортированный список», `bisect` для поиска соседей — O(log n)
- **гонка**: два параллельных запроса оба пройдут проверку и забронируют одно время → блокировка на комнату в памяти; в БД — `EXCLUDE`-ограничение PostgreSQL по диапазону времени или `SELECT … FOR UPDATE`
- **словари вместо модели** → `dataclass(frozen=True) Booking`; нет id брони, а значит, нельзя отменить
- **время**: часовые пояса (хранить в UTC, `datetime` с tzinfo)
- проверка пересечения `b.start < end and start < b.end` правильная (полуинтервалы), её стоит оставить и покрыть тестами на касание
--- points
- глобальное состояние и тестируемость
- валидация интервала
- исключения вместо строк
- сложность и структура по комнатам с bisect
- гонка при параллельных запросах и ограничение в БД
- модель данных, id, часовые пояса
:::

* `RoomBooking` — бронирование переговорок без пересечений, с отменой {test_room_booking}
+ Словарь «комната → отсортированный список `(start, end, booking_id)`». `book`: проверь `start < end`, найди позицию через `bisect` и проверь только соседей слева и справа; вставь. `cancel(booking_id)`. `free_rooms(start, end)` — комнаты из списка `rooms`, свободные на весь интервал.
! Касание (`[9, 10)` и `[10, 11)`) — не пересечение. Неизвестная комната и `start >= end` — `ValueError`, занято — `RoomBusy`. Тест бронирует 20 000 интервалов: проверка всех броней комнаты на каждое бронирование — O(n²).
* `ATM ★` — банкомат: выдать сумму минимальным числом купюр из ограниченных кассет {test_atm}
+ Перебор от крупного номинала к мелкому: для номинала `d` попробуй взять `k` купюр от `min(count, rest // d)` вниз до 0 и рекурсивно добери остаток мелкими. Отсечения: остаток больше, чем денег в оставшихся кассетах, — тупик; `использовано + ⌈остаток / d⌉` не меньше лучшего найденного — дальше не идти (даже крупнейшими купюрами не обогнать). Найденный план применяй только целиком.
! Жадный алгоритм ошибается на кассетах `{50: 1, 20: 3}` и сумме 60 — тест это проверяет. Невозможно выдать — `CannotDispense`, кассеты не меняются. `deposit` добавляет купюры, `balance` — сумма в банкомате.

## Вопросы с собеседования по уроку:
::: quiz open q112-3
Как ты подходишь к задаче на бизнес-логику на лайвкоде, чтобы уложиться во время?
--- answer
Первые 3–5 минут уточняю сценарии и инварианты и проговариваю их: что система делает, что запрещено, что происходит при ошибке, какие данные на входе. Затем пишу минимальную модель — пару `dataclass` и `Enum`, без иерархий «на будущее», — и сразу перехожу к ядру логики: сначала счастливый путь, потом ошибки через свои исключения. Внешнее (время, хранилище, отправку) получаю параметрами — это ускоряет и проверку, и тесты. Слежу за атомарностью: сначала вычисляю результат, потом применяю. Если вижу, что не успеваю, говорю, какую часть упрощаю и как бы сделал полностью. В конце прогоняю 2–3 сценария вслух и называю расширения: конкурентный доступ (блокировки, транзакции, ограничения в БД), персистентность, масштаб. Главное — дойти до работающей логики, а не идеальной модели.
--- points
- сценарии и инварианты в начале
- минимальная модель без оверинжиниринга
- счастливый путь, затем ошибки через исключения
- зависимости параметрами, атомарность
- проговорить упрощения и расширения
:::
