# 13.2 WSGI, ASGI, Django и FastAPI

## WSGI и ASGI:
**WSGI** (PEP 3333) — синхронный контракт между веб-сервером и приложением: приложение — вызываемый объект `app(environ, start_response)`, который возвращает итерируемое тело.
```python
def app(environ, start_response):
    body = b'{"status": "ok"}'
    start_response("200 OK", [("Content-Type", "application/json"),
                              ("Content-Length", str(len(body)))])
    return [body]
```
Один запрос занимает воркер (процесс или поток) до конца: долгие соединения (WebSocket, стриминг) так не держат. Серверы — gunicorn, uWSGI. Фреймворки — Django (классически), Flask.

**ASGI** — асинхронный контракт: `async def app(scope, receive, send)`. События приходят и уходят сообщениями: `http.request` (тело, возможно кусками с `more_body`), `http.response.start`, `http.response.body`, плюс `websocket.*` и `lifespan.*` (старт и остановка приложения). Серверы — uvicorn, hypercorn, granian. Фреймворки — FastAPI/Starlette, Django (с 3.0), Litestar.

## Как запускают в продакшене:
- **gunicorn** с N процессами-воркерами (обычно `2 × ядра + 1` для синхронных); для ASGI — `uvicorn.workers.UvicornWorker` или сам `uvicorn --workers N`
- типы воркеров: `sync` (запрос на процесс), `gthread` (потоки), асинхронные (uvicorn): тысячи соединений в одном процессе
- перед ними — nginx или балансировщик: TLS, статика, буферизация медленных клиентов, ограничения
- `max_requests` — перезапуск воркера после N запросов как страховка от утечек памяти; `timeout`, graceful shutdown по SIGTERM

Что выведет программа?
```python
def app(environ, start_response):
    print("app")
    start_response("200 OK", [])
    return [b"ok"]

def middleware(name, inner):
    def wrapped(environ, start_response):
        print("до", name)
        result = inner(environ, start_response)
        print("после", name)
        return result
    return wrapped

handler = middleware("A", middleware("B", app))
handler({}, lambda status, headers: None)
```
--- answer
до A
до B
app
после B
после A
--- why
Middleware — это «луковица» из декораторов вокруг приложения: запрос проходит слои снаружи внутрь, ответ — изнутри наружу. Так устроены и `MIDDLEWARE` в Django (первый в списке — самый внешний), и middleware в Starlette/FastAPI. Отсюда вопросы «в каком порядке выполнятся middleware» и «почему аутентификация должна стоять раньше логирования пользователя».

## Django — что спрашивают:
- **жизненный цикл запроса**: WSGI/ASGI-хендлер → middleware (`process_request`, …) → URL-резолвер → view → ORM, шаблоны → ответ обратно через middleware
- **QuerySet ленивый**: запрос в БД уходит при итерации, `len`, `list`, срезе с шагом, `bool`. Результат кэшируется в QuerySet. Цепочки `filter().exclude().order_by()` ничего не выполняют до вычисления
- **N+1**: `select_related` — JOIN для ForeignKey и OneToOne (один запрос); `prefetch_related` — отдельный запрос для обратных связей и ManyToMany и склейка в Python. Обнаруживать — django-debug-toolbar, `assertNumQueries` в тестах
- `F()` — ссылка на столбец в выражении (`update(stock=F("stock") - 1)` атомарно в БД); `Q()` — сложные условия с `|` и `~`; `annotate`/`aggregate`
- **транзакции**: `transaction.atomic()` (вложенные — savepoints), `select_for_update()`, `on_commit()` для отправки задач после коммита (иначе Celery-задача может стартовать раньше, чем данные появятся в БД)
- **сигналы** (`post_save`) — неявная связность и скрытые запросы; не срабатывают на `bulk_create` и `update()`
- **миграции на больших таблицах**: добавление столбца с дефолтом, индексы (`AddIndexConcurrently`), разделение схемы и данных, обратная совместимость при выкатке

## FastAPI — что спрашивают:
- построен на Starlette (ASGI) и pydantic: аннотации параметров → валидация, сериализация и OpenAPI-схема
- **`async def` против `def`** эндпоинта: `async def` выполняется в цикле событий (внутри — только неблокирующие вызовы), `def` — в пуле потоков. Блокирующий вызов в `async def` замораживает весь воркер (урок 5.3)
- **`Depends`** — внедрение зависимостей: функция-зависимость (в том числе с `yield` для очистки, как сессия БД), граф зависимостей разрешается на каждый запрос, одна зависимость в одном запросе вычисляется **один раз**; `app.dependency_overrides` — подмена в тестах
- **pydantic v2**: ядро на Rust, `model_validate`, `model_dump`, `field_validator`, `ConfigDict(from_attributes=True)` для ORM-объектов
- `BackgroundTasks` — после ответа в том же процессе (не замена очереди), `lifespan` — ресурсы на время жизни приложения (пул БД, HTTP-клиент)

В Django-представлении `for order in Order.objects.all(): print(order.customer.name)`. Заказов 1000. Сколько запросов уйдёт в БД и как исправить?
- [ ] 1, Django всё кэширует
- [x] 1 001: один за заказами и по одному за покупателем на каждый заказ; `Order.objects.select_related("customer")` даст один запрос с JOIN

## Вопросы с собеседования по уроку:
::: quiz open q132-3 собес
Чем WSGI отличается от ASGI? Когда в FastAPI писать `async def`, а когда `def`?
--- answer
WSGI — синхронный интерфейс: приложение — функция `(environ, start_response)`, запрос целиком обрабатывается в одном воркере (процесс или поток), конкурентность — числом воркеров. Не подходит для долгих соединений (WebSocket, SSE, long polling) и плохо использует время ожидания I/O. ASGI — асинхронный интерфейс `async (scope, receive, send)` с обменом сообщениями: поддерживает HTTP, WebSocket и lifespan, один процесс держит тысячи соединений, пока они ждут I/O. Django поддерживает оба, FastAPI/Starlette — ASGI. В FastAPI `async def`-эндпоинт выполняется прямо в цикле событий: писать его, если внутри только неблокирующие вызовы (`await` асинхронных драйверов БД, httpx). Если используются синхронные библиотеки (requests, синхронная ORM, тяжёлые расчёты), — обычный `def`: FastAPI запустит его в пуле потоков, и цикл не заблокируется. Худший вариант — блокирующий вызов в `async def`: он останавливает обработку всех запросов воркера. CPU-тяжёлое — в процессы или очередь задач.
--- points
- WSGI: синхронный, воркер на запрос
- ASGI: события, WebSocket, lifespan, тысячи соединений
- async def — в цикле событий, только неблокирующее
- def — в пуле потоков для синхронных библиотек
- блокирующий вызов в async def — главная ошибка
:::

::: quiz open q132-4 собес
Как в Django избежать проблемы N+1? Чем `select_related` отличается от `prefetch_related`?
--- answer
N+1 — когда на каждый объект из списка уходит дополнительный запрос за связанным объектом: 1 запрос за списком + N за связями. В Django это происходит из-за ленивой загрузки связей. `select_related` делает SQL-JOIN и загружает связанные объекты одним запросом. Работает для «одиночных» связей — ForeignKey и OneToOne в прямую сторону. `prefetch_related` делает отдельный запрос на каждую связь (`WHERE id IN (...)`) и склеивает результаты в Python. Нужен для обратных ForeignKey (`author.books`) и ManyToMany, где JOIN размножил бы строки; объект `Prefetch` позволяет задать фильтр и `select_related` для вложенного запроса. Ещё приёмы: `only()`/`values()` — брать только нужные столбцы; `annotate` с агрегатами вместо подсчёта в цикле; обнаружение — django-debug-toolbar, логирование SQL, `assertNumQueries` в тестах, nplusone.
--- points
- определение N+1 и причина — ленивая загрузка
- select_related: JOIN, FK и OneToOne
- prefetch_related: отдельный запрос и склейка, обратные связи и M2M
- Prefetch, only, annotate
- как обнаруживать: debug-toolbar, assertNumQueries
:::
