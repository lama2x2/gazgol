# 5.1 Память, сборка мусора и GIL

## Как CPython управляет памятью:
1. **Подсчёт ссылок.** У каждого объекта счётчик `ob_refcnt`. Новая ссылка (присваивание, элемент списка, аргумент) увеличивает его, пропажа ссылки уменьшает. Дошёл до нуля — объект удаляется **сразу** и детерминированно
2. **Циклический сборщик (`gc`)** нужен для циклов: `a.b = b; b.a = a`. Счётчики никогда не станут нулём, поэтому периодически запускается сборщик, который ищет недостижимые группы объектов. В 3.12 и раньше — три поколения; в 3.14 — инкрементальный сборщик с двумя поколениями: молодые объекты проверяются часто, старые — реже
3. **Аллокатор `pymalloc`** — для маленьких объектов (≤ 512 байт): пулы и арены, чтобы не ходить в системный `malloc` за каждым int

- `sys.getrefcount(x)` — счётчик (на 1 больше: временная ссылка из аргумента)
- **бессмертные объекты** (3.12, PEP 683): `None`, `True`, малые int и другие синглтоны не меняют свой счётчик. Это убирает запись в память при каждом использовании, что важно для многоядерности. `getrefcount(None)` возвращает огромное фиксированное число
- **слабая ссылка** (`weakref.ref`, `WeakValueDictionary`) не увеличивает счётчик: кэш не держит объект живым

::: quiz output q51-1 собес
Что выведет программа?
```python
import gc, weakref

class Node:
    pass

gc.disable()
a, b = Node(), Node()
a.other, b.other = b, a
r = weakref.ref(a)
del a, b
print(r() is None)
gc.collect()
print(r() is None)
```
--- answer
False
True
--- why
После `del` объекты ссылаются друг на друга, их счётчики равны 1, и подсчёт ссылок их не удалит. Только циклический сборщик находит, что группа недостижима, и освобождает её. Отсюда практика: в деревьях ссылку на родителя делают слабой (`weakref.ref(parent)`), а `gc.disable()` в долгоживущих сервисах — путь к утечкам.
:::

## Где на самом деле утекает память в сервисе:
- растущие глобальные кэши и словари без лимита (`lru_cache` без `maxsize`, «временный» `dict` на уровне модуля)
- подписчики и колбэки, которые никто не отписывает
- `lru_cache` на методах (держит `self`), замыкания, захватившие большие объекты
- объекты с `__del__` в циклах (в старых версиях не собирались)
- C-расширения

Как искать: `tracemalloc` (снимки и разница по строкам кода), `objgraph`, `memray`, `gc.get_objects()`/`gc.get_referrers()`, график RSS процесса в мониторинге.

## GIL — Global Interpreter Lock:
**GIL** — мьютекс в CPython: в каждый момент **только один поток выполняет байткод Python** в одном интерпретаторе.
- **Зачем он нужен.** Защищает счётчики ссылок и внутренние структуры без тысячи мелких блокировок, а однопоточный код и C-расширения остаются простыми и быстрыми
- **Когда отпускается.** На блокирующем вводе-выводе (`socket.recv`, `file.read`, `time.sleep`), в C-коде, который сам его отпускает (NumPy, hashlib, zlib), и принудительно каждые ~5 мс (`sys.getswitchinterval()`), чтобы потоки чередовались
- **Что из этого следует:** для **I/O-bound** задач потоки работают хорошо — пока один ждёт сеть, другой выполняется. Для **CPU-bound** на чистом Python потоки не ускоряют, а иногда замедляют: нужны процессы (`multiprocessing`, `ProcessPoolExecutor`) или C-расширения
- **GIL не делает твой код потокобезопасным.** Переключение может случиться между любыми байткодами: `counter += 1` — это чтение, сложение и запись, и гонка возможна

::: py Что изменилось в 3.13–3.15
- **3.13** — экспериментальная **free-threaded** сборка без GIL (PEP 703, `python3.13t`)
- **3.14** — free-threaded сборка **официально поддерживается** (PEP 779), но по умолчанию GIL всё ещё есть. Однопоточный код в ней немного медленнее, C-расширения должны явно объявить совместимость. В стандартной библиотеке появились субинтерпретаторы (PEP 734, `concurrent.interpreters` и `InterpreterPoolExecutor`): у каждого свой GIL, параллельность — внутри одного процесса
- **3.15** — стабильный ABI для free-threaded сборок
На собесе хороший ответ: «GIL есть в стандартной сборке; с 3.13 есть сборка без него, с 3.14 она поддерживается официально, но экосистема переходит постепенно».
:::

Время уходит на ожидание сети, а не на вычисления. Потоки и asyncio дают конкурентность ожидания. Процессы тоже ускорят, но дороже: память, запуск, сериализация данных. А вот для разбора тысячи больших JSON или сжатия картинок (CPU) понадобились бы процессы.

## Производительность: как измерять, а не гадать
| Инструмент | Что показывает |
|---|---|
| `timeit` | время маленького фрагмента, много прогонов |
| `cProfile` + `pstats` / `snakeviz` | какие функции съели время (детерминированный профайлер, замедляет) |
| `py-spy`, `profiling.sampling` (3.15) | сэмплирующий профайлер: подключается к работающему процессу почти без накладных расходов |
| `tracemalloc`, `memray` | кто выделил память |
| `line_profiler` | время по строкам |

Типичные ускорения: правильная структура данных (`set` вместо `list` для `in`), убрать работу из цикла, встроенные функции и `join` вместо ручных циклов, кэширование, батчинг запросов к БД, асинхронность для I/O, `multiprocessing` или NumPy для CPU, PyPy. Почему Python не оптимизирует хвостовую рекурсию: Гвидо хотел полные трейсбеки, а рекурсия в Python неидиоматична — переписывай на цикл (лимит `sys.getrecursionlimit()`, по умолчанию 1000).

## Вопросы с собеседования по уроку:
::: quiz open q51-4 собес
Что такое GIL? Зачем он нужен и как с ним жить?
--- answer
GIL — глобальная блокировка интерпретатора CPython: в одном интерпретаторе байткод Python выполняет только один поток одновременно. Нужен, потому что управление памятью построено на подсчёте ссылок, который без GIL пришлось бы защищать атомарными операциями или блокировками на каждом объекте. Это сделало бы однопоточный код медленнее и усложнило бы C-расширения. GIL отпускается при блокирующем I/O, в C-коде, который сам его отпускает (NumPy, hashlib, zlib), и принудительно по таймеру (switch interval, ~5 мс). Следствия: потоки хороши для I/O-bound задач, бесполезны для CPU-bound на чистом Python; для CPU — `multiprocessing`/`ProcessPoolExecutor`, нативные расширения, векторизация. GIL не гарантирует потокобезопасности: составные операции (`+=`, проверка и вставка) требуют `Lock`. В 3.13 появилась экспериментальная free-threaded сборка без GIL (PEP 703), в 3.14 она официально поддерживается (PEP 779), но не по умолчанию; плюс субинтерпретаторы со своим GIL. Asyncio от GIL почти не зависит: он однопоточный и даёт конкурентность на ожидании I/O.
--- points
- определение: один поток выполняет байткод в интерпретаторе
- зачем: подсчёт ссылок, простота C-API
- когда отпускается: I/O, C-код, switch interval
- I/O-bound → потоки/asyncio, CPU-bound → процессы
- не даёт потокобезопасности
- free-threaded 3.13/3.14, субинтерпретаторы
:::

::: quiz open q51-5 собес
Как работает сборка мусора в Python? Как найти утечку памяти в продакшене?
--- answer
Основной механизм — подсчёт ссылок: объект удаляется сразу, как только счётчик падает до нуля, — детерминированно (на этом держится закрытие файлов при выходе из области видимости в CPython). Для циклических ссылок есть циклический сборщик `gc`, который периодически ищет недостижимые группы объектов. Он работает по поколениям: молодые объекты проверяет часто, переживших — реже; в 3.14 сборщик стал инкрементальным. Маленькие объекты выделяются через pymalloc. Утечка в Python — это почти всегда объекты, на которые кто-то всё ещё ссылается: глобальные кэши без лимита, неотписанные колбэки, `lru_cache` на методах, накопление в списках. Как искать: график памяти в мониторинге (растёт ли RSS под постоянной нагрузкой), `tracemalloc` — два снимка с интервалом и `compare_to` по строкам кода, `memray` или `py-spy dump` для работающего процесса, `objgraph.show_growth()` и `gc.get_referrers()` для поиска держателя ссылки. Лечение — лимиты и TTL у кэшей, `weakref`, явная отписка, воркеры, которые перезапускаются после N запросов (`max_requests` в gunicorn) как страховка.
--- points
- подсчёт ссылок, мгновенное удаление
- циклический сборщик и поколения
- утечка = лишняя ссылка: кэши, колбэки, глобальные структуры
- инструменты: tracemalloc со снимками, memray, objgraph
- лечение: лимиты, weakref, перезапуск воркеров
:::
