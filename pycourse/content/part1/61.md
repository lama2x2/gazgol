# 6.1 Аннотации типов, pytest и моки

## Аннотации типов:
Аннотации **не проверяются при выполнении** — интерпретатор их только сохраняет (`f.__annotations__`). Проверяют их статические анализаторы (mypy, pyright) в IDE и CI, а также библиотеки, которые читают аннотации сами: pydantic, FastAPI, dataclasses.

::: quiz output q61-1 собес
Что выведет программа?
```python
def double(x: int) -> int:
    return x * 2

print(double("ab"))
print(double.__annotations__["return"].__name__)
```
--- answer
abab
int
--- why
Аннотация `int` ничего не запрещает: строка умножилась на 2. Поймать такую ошибку может только mypy до запуска. Поэтому данные снаружи (HTTP, очереди) валидируют в рантайме — pydantic, а аннотации внутри кода — договор для людей и анализатора.
:::

| Конструкция | Пример |
|---|---|
| встроенные дженерики (3.9) | `list[int]`, `dict[str, list[User]]` |
| объединение (3.10) | `int \| None` вместо `Optional[int]` |
| дженерик-функция (3.12) | `def first[T](xs: list[T]) -> T: ...` |
| псевдоним типа (3.12) | `type UserId = int` |
| структурный интерфейс | `class Repo(Protocol): def get(self, id: int) -> User: ...` |
| словарь с ключами | `class Event(TypedDict): id: int; kind: Literal["a", "b"]` |
| вызываемые | `Callable[[int, str], bool]`; для декораторов — `ParamSpec`, чтобы сохранить сигнатуру |
| прочее | `Final`, `ClassVar`, `Self`, `@overload`, `TypeGuard`, `Annotated` (FastAPI `Depends`, pydantic `Field`) |

С 3.14 аннотации вычисляются **отложенно** (PEP 649/749): можно ссылаться на класс, объявленный ниже, без кавычек и `from __future__ import annotations`.

::: quiz choice q61-2 собес
Зачем аннотации типов, если Python их не проверяет?
- [ ] они ускоряют выполнение программы
- [x] статический анализ ловит ошибки до запуска, IDE даёт точные подсказки и рефакторинг, сигнатура документирует контракт, а фреймворки (FastAPI, pydantic) строят по ним валидацию и схемы
- [ ] без них не работает наследование
- [ ] они обязательны с Python 3.12
--- why
В CPython аннотации на скорость не влияют (mypyc и Cython — отдельная история). Ценность — в инструментах вокруг. Внедрять в большой проект лучше постепенно: начать со строгого режима для новых модулей и общих интерфейсов, `# type: ignore` с комментарием, где нужно, и проверкой в CI, которая не даёт добавлять новые ошибки.
:::

## Пирамида тестов:
- **юнит-тесты** — функция или класс в изоляции, миллисекунды, их больше всего
- **интеграционные** — с настоящей БД, очередью, HTTP-слоем (`TestClient` FastAPI, тестовая БД в контейнере, транзакция с откатом после каждого теста)
- **end-to-end** — систему целиком, через внешний API; их меньше всего, они медленные и хрупкие

## pytest — что спрашивают:
```python
import pytest

@pytest.fixture
def db():                       # фикстура: подготовка и уборка
    conn = connect(":memory:")
    yield conn                  # значение для теста
    conn.close()                # после теста, даже если он упал

@pytest.mark.parametrize("a, b, want", [(1, 2, 3), (-1, 1, 0)])
def test_add(a, b, want):
    assert add(a, b) == want

def test_bad_input():
    with pytest.raises(ValueError, match="отриц"):
        sqrt(-1)

def test_env(monkeypatch, tmp_path):
    monkeypatch.setenv("MODE", "test")   # встроенные фикстуры: monkeypatch, tmp_path, capsys, caplog
```
- **область фикстур** (`scope=`): `function` (по умолчанию), `class`, `module`, `session` — например, одна БД на всю сессию и транзакция на каждый тест
- `conftest.py` — общие фикстуры для каталога; фикстуры могут зависеть друг от друга
- `pytest` против `unittest`: голый `assert` с понятным выводом, фикстуры вместо `setUp`, параметризация, плагины

## Тестовые двойники и `unittest.mock`:
| Двойник | Что делает |
|---|---|
| **stub** | возвращает заготовленные ответы |
| **mock** | записывает вызовы, чтобы проверить взаимодействие |
| **fake** | рабочая упрощённая реализация (репозиторий на словаре) |
| **spy** | настоящий объект, вызовы которого записываются |

::: quiz output q61-3
Что выведет программа?
```python
from unittest.mock import Mock

m = Mock(return_value=3)
print(m(1, x=2))
print(m.call_count, m.call_args)
m.side_effect = [10, ValueError("boom")]
print(m())
try:
    m()
except ValueError as e:
    print("ValueError", e)
print(callable(m.anything.you_like))
```
--- answer
3
1 call(1, x=2)
10
ValueError boom
True
--- why
`side_effect`-список отдаёт значения по очереди, а исключение в нём бросается. Опасная часть — последняя строка: у `Mock` есть **любой** атрибут, поэтому опечатка в имени метода настоящего объекта тест не уронит, а опечатка в проверке (`m.assert_called_onse()`) до Python 3.5 молча проходила (теперь имена на `assert…` с опечатками запрещены). Лечится `Mock(spec=RealClass)` или `create_autospec`: двойник получает только настоящие методы с настоящими сигнатурами.
:::

::: warn Где патчить
`mock.patch` подменяет имя **там, где его ищут**, а не там, где оно определено. Если `app/service.py` делает `from app.clients import get_rate`, то патчить нужно `app.service.get_rate`. Патч `app.clients.get_rate` не подействует: в `service` уже лежит своя ссылка на оригинал. Ещё лучше — не патчить, а внедрять зависимость (урок 4.3) и передавать фейк.
:::

## Хороший тест:
- проверяет **поведение**, а не реализацию: после рефакторинга без смены поведения тест не должен падать
- один сценарий — один тест с говорящим именем: `test_promo_minus500_not_applied_below_threshold`
- **граничные значения**: если в коде `>=`, проверь ровно границу и на единицу меньше — именно там живут ошибки `>` против `>=`
- детерминированность: время, случайность, сеть — через параметры или фейки
- покрытие (coverage) показывает, какие строки выполнились, но не то, что их **проверили**. Строку `return total - 500 if total >= 3000 else total` покроет любой тест, а ошибку `>` вместо `>=` поймает только тест с суммой ровно 3000. Это измеряет **мутационное тестирование** (`mutmut`, `cosmic-ray`): в код вносятся маленькие ошибки, и смотрят, упадут ли тесты. Так устроена домашка этого урока

::: quiz choice q61-4
В коде `return 0 if total >= 5000 else 299`. Какой набор тестов ловит ошибку, если кто-то заменит `>=` на `>`?
- [ ] `delivery_cost(10000) == 0` и `delivery_cost(100) == 299`
- [x] `delivery_cost(5000) == 0` и `delivery_cost(4999) == 299`
- [ ] `delivery_cost(0) == 299`
- [ ] любой тест, лишь бы строка была покрыта
--- why
Значения далеко от границы проходят одинаково для `>=` и `>`. Только тест ровно на границе (5000) различает их, а 4999 подтверждает, что граница не сдвинута в другую сторону. Это «анализ граничных значений» — базовая техника тест-дизайна, о которой спрашивают на собесах.
:::

## Вопросы с собеседования по уроку:
::: quiz open q61-5 собес
Как ты тестируешь код? Что такое фикстуры и моки, когда мокать, а когда нет?
--- answer
Пирамида: много быстрых юнит-тестов на бизнес-логику, меньше интеграционных (настоящая БД в контейнере, HTTP-слой через `TestClient`, транзакция с откатом на каждый тест), немного end-to-end. Пишу на pytest. Фикстуры — функции подготовки окружения с уборкой после `yield`, со scope от функции до сессии, общие — в `conftest.py`; ещё использую `parametrize` для наборов случаев и `pytest.raises` для ошибок. Моки (`unittest.mock`) — для границ системы: внешние HTTP-API, платёжки, отправка писем, часы и случайность, — то, что медленно, недетерминированно или стоит денег. Мокать собственную логику и ORM обычно не стоит: тесты начинают проверять реализацию и ломаются при рефакторинге. Вместо патчей предпочитаю внедрять зависимости и передавать фейки. Мок — с `spec`/`autospec`, чтобы не разойтись с реальным интерфейсом; патчить там, где имя используется. Качество тестов оцениваю не только покрытием, но и тем, ловят ли они ошибки на границах; помогает мутационное тестирование.
--- points
- пирамида: юнит, интеграционные, e2e
- фикстуры: yield-уборка, scope, conftest
- parametrize и pytest.raises
- мокать границы системы, не свою логику
- spec/autospec, где патчить, DI вместо патчей
- покрытие ≠ качество, граничные значения, мутационное тестирование
:::
