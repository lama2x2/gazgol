# 5.2 Потоки и процессы

## Процесс против потока (вопрос в 34% интервью):
| | Процесс | Поток |
|---|---|---|
| память | своя, изолированная | общая с другими потоками процесса |
| создание | дорого (миллисекунды, мегабайты) | дёшево |
| обмен данными | через IPC: очереди, pipe, сокеты, shared memory — с сериализацией (pickle) | напрямую через общие объекты, но нужна синхронизация |
| падение | не роняет остальные процессы | необработанная ошибка в C-коде роняет весь процесс |
| GIL | у каждого процесса свой → настоящий параллелизм | один GIL на процесс → параллелен только I/O |
| для чего в Python | CPU-bound: расчёты, разбор, сжатие | I/O-bound: сеть, диск, БД |

**Конкурентность** — несколько задач продвигаются, перекрываясь во времени (можно на одном ядре, переключаясь). **Параллелизм** — задачи выполняются физически одновременно на разных ядрах.

## Проблемы общего состояния:
- **гонка данных (race condition)** — результат зависит от того, как чередовались потоки. `count += 1` — это три операции: прочитать, сложить, записать
- **check-then-act**: `if key not in cache: cache[key] = load()` — два потока одновременно не найдут ключ и оба загрузят
- **deadlock (взаимная блокировка)** — поток 1 держит A и ждёт B, поток 2 держит B и ждёт A. Лечится единым порядком захвата блокировок, таймаутами (`lock.acquire(timeout=…)`), меньшим числом блокировок
- **голодание и livelock** — поток никогда не получает ресурс или все бесконечно уступают друг другу

## Инструменты `threading`:
| Примитив | Зачем |
|---|---|
| `Lock` | взаимное исключение: `with lock:` |
| `RLock` | тот же поток может захватить повторно (рекурсия) |
| `Semaphore(n)` | не больше n одновременно (пул соединений) |
| `Event` | флаг «можно» / «стоп»: `wait()`, `set()` |
| `Condition` | ждать выполнения условия: `wait_for(pred)`, `notify()` |
| `Barrier(n)` | дождаться, пока соберутся n потоков |
| `queue.Queue(maxsize)` | потокобезопасная очередь с блокировкой; основа producer-consumer |
| `threading.local()` | свои данные в каждом потоке |

## `concurrent.futures` — высокоуровневый API:
```python
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor, as_completed

with ThreadPoolExecutor(max_workers=10) as ex:
    results = list(ex.map(download, urls))          # порядок как во входе
    futures = [ex.submit(download, u) for u in urls]
    for f in as_completed(futures):                  # по мере готовности
        print(f.result())                            # исключение из задачи поднимется здесь
```
`ProcessPoolExecutor` — тот же интерфейс, но функция и аргументы **сериализуются pickle** и передаются в другой процесс. Поэтому функция должна быть на уровне модуля (не лямбда и не вложенная), а данные — небольшими. Способ запуска процессов: `fork` (Linux, быстро, но опасно с потоками), `spawn` (macOS и Windows по умолчанию: новый интерпретатор импортирует модуль заново, отсюда обязательный `if __name__ == "__main__":`), `forkserver` (по умолчанию на Linux с 3.14).

Что выведет программа?
```python
from concurrent.futures import ThreadPoolExecutor
import time

def work(x):
    time.sleep(0.05 * (3 - x))
    return x * 10

with ThreadPoolExecutor(3) as ex:
    print(list(ex.map(work, [0, 1, 2])))
```
--- answer
[0, 10, 20]
--- why
`map` возвращает результаты **в порядке входных данных**, даже если быстрее завершилась последняя задача. Чтобы получать результаты по мере готовности, нужен `submit` + `as_completed`.

::: quiz bug q52-3 собес
Где здесь проблема?
```python
import threading

class Bank:
    def __init__(self):
        self.locks = {}            # счёт → Lock

    def transfer(self, a, b, amount):
        with self.locks[a]:
            with self.locks[b]:
                ...                # списать с a, зачислить на b
```
- [ ] вложенный `with` запрещён для блокировок
- [x] перевод a→b и одновременный перевод b→a захватывают блокировки в противоположном порядке — взаимная блокировка
- [ ] нужно использовать `RLock` вместо `Lock`
- [ ] блокировки в словаре не работают
--- why
Поток 1 взял `lock[a]` и ждёт `lock[b]`, поток 2 взял `lock[b]` и ждёт `lock[a]`. Оба ждут вечно. Решение — захватывать в **едином порядке**, например по возрастанию номера счёта: `first, second = sorted([a, b])`. В базах данных та же ошибка даёт deadlock между транзакциями, и лечится так же.

::: quiz choice q52-4
Почему код ниже может загрузить один и тот же ключ дважды, хотя есть GIL?
```python
def get(key):
    if key not in cache:
        cache[key] = load(key)     # load — долгий сетевой запрос
    return cache[key]
```
- [ ] GIL защищает словарь, поэтому не может
- [x] между проверкой `in` и присваиванием другой поток может выполнить ту же проверку; GIL атомарен только для отдельных операций, а не для «проверить и сделать»
- [ ] словари в Python не потокобезопасны вообще
- [ ] `load` вызывается в другом процессе
--- why
Это гонка check-then-act. Отдельные операции со словарём в CPython атомарны, но пара операций — нет, а во время `load` GIL вообще отпущен. Решения: блокировка (возможно, отдельная на ключ), `setdefault` с заглушкой-Future или singleflight («один загружает, остальные ждут его результат»).
:::

## Вопросы с собеседования по уроку:
::: quiz open q52-5 собес
Чем процесс отличается от потока? Когда в Python что использовать?
--- answer
Процесс — экземпляр программы с собственным адресным пространством, ресурсами ОС и, в Python, собственным интерпретатором и GIL. Поток — единица выполнения внутри процесса: потоки делят память и ресурсы процесса. Процессы изолированы: падение одного не роняет другие, данные передаются через IPC с сериализацией, создание дороже. Потоки создаются дёшево и обмениваются данными напрямую, но требуют синхронизации (гонки, deadlock). В CPython из-за GIL потоки не дают параллельного выполнения Python-кода, поэтому для I/O-bound задач (сеть, диск, БД) — потоки или asyncio, для CPU-bound (вычисления, парсинг, сжатие) — процессы (`ProcessPoolExecutor`, `multiprocessing`) или C-расширения, отпускающие GIL. На практике в вебе параллелизм по ядрам дают несколько процессов-воркеров (gunicorn/uvicorn workers), а внутри — потоки или asyncio. Тяжёлые фоновые задачи выносят в отдельные процессы (Celery-воркеры).
--- points
- память и изоляция: своя против общей
- стоимость создания и обмена данными (IPC, pickle)
- надёжность: падение процесса изолировано
- GIL: потоки для I/O, процессы для CPU
- практика: воркеры gunicorn/uvicorn, Celery
:::

::: quiz open q52-6 собес
Что такое race condition и deadlock? Как их избегать?
--- answer
Race condition — ошибка, при которой результат зависит от порядка выполнения конкурентных операций над общим состоянием: неатомарный `x += 1`, check-then-act (`if not exists: create`), чтение частично обновлённых данных. Избегать: не разделять изменяемое состояние (передавать сообщения через очереди), делать неизменяемые данные, защищать критические секции блокировкой, использовать атомарные операции хранилища (`INSERT … ON CONFLICT`, `UPDATE … SET x = x + 1`, `SETNX` в Redis). Deadlock — несколько потоков или транзакций ждут ресурсы, захваченные друг другом, и не продвигаются. Условия: взаимное исключение, удержание с ожиданием, отсутствие принудительного освобождения и циклическое ожидание. Избегать: единый порядок захвата блокировок, захват всего сразу, таймауты с повтором, минимальная длительность удержания, меньше вложенных блокировок. В БД — короткие транзакции, одинаковый порядок обновления строк, ретрай при ошибке deadlock.
--- points
- определение гонки и примеры (+=, check-then-act)
- способы: блокировки, очереди, неизменяемость, атомарные операции БД
- определение deadlock и циклическое ожидание
- единый порядок захвата, таймауты
- то же в базах данных
:::
