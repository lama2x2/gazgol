# 3.3 Контекстные менеджеры и исключения

## Исключения: как устроены
```text
BaseException
 ├── SystemExit, KeyboardInterrupt, GeneratorExit   ← не ловятся через except Exception
 ├── BaseExceptionGroup → ExceptionGroup
 └── Exception
      ├── ArithmeticError → ZeroDivisionError
      ├── LookupError → KeyError, IndexError
      ├── OSError → FileNotFoundError, ConnectionError, TimeoutError…
      ├── ValueError, TypeError, AttributeError, RuntimeError…
      └── твои исключения
```
- `except Exception` — так ловят «всё ожидаемое». Голый `except:` ловит и `KeyboardInterrupt`, и `SystemExit` — так делать не надо
- `else` выполняется, если в `try` **не было** исключения; `finally` — **всегда**, даже при `return` и `break`
- `raise NewError(...) from e` — явная цепочка (`__cause__`), трейсбек покажет обе ошибки. `from None` — скрыть исходную
- **EAFP** («проще просить прощения»: `try: d[k] except KeyError`) — питоничный стиль; **LBYL** (`if k in d`) — уместен, когда проверка дешёвая и исключение было бы частым

## Контекстный менеджер:
Объект с `__enter__` и `__exit__`. Конструкция `with` гарантирует очистку при любом выходе из блока: обычном, по `return` или по исключению.
```python
with open("a.txt") as f:      # f = mgr.__enter__()
    data = f.read()
# при выходе: mgr.__exit__(exc_type, exc, tb) — файл закрыт, даже если read() упал
```
`__exit__` получает тип, объект и трейсбек исключения (или три `None`). Если он вернёт **истинное значение**, исключение будет **подавлено**.

## Три способа написать свой:
```python
class Timer:                                  # 1. класс
    def __enter__(self):
        self.start = time.perf_counter()
        return self                           # то, что попадёт в `as`
    def __exit__(self, exc_type, exc, tb):
        self.elapsed = time.perf_counter() - self.start
        return False                          # не подавлять исключения

from contextlib import contextmanager
@contextmanager                               # 2. генератор
def cd(path):
    old = os.getcwd()
    os.chdir(path)
    try:
        yield                                 # здесь выполняется тело with
    finally:                                  # без try/finally очистка не выполнится при исключении!
        os.chdir(old)

from contextlib import ExitStack, suppress    # 3. готовые: suppress, ExitStack, closing, nullcontext
with ExitStack() as stack:
    files = [stack.enter_context(open(p)) for p in paths]   # переменное число ресурсов
```
Асинхронные версии — `async with`, `__aenter__`/`__aexit__`, `@asynccontextmanager`: например, подключение из пула или HTTP-сессия.

::: quiz output q33-3 собес
Что выведет программа?
```python
from contextlib import contextmanager

@contextmanager
def opened(name):
    print("open", name)
    yield name
    print("close", name)

try:
    with opened("a"):
        raise ValueError
except ValueError:
    print("поймали")
```
--- answer
open a
поймали
--- why
Исключение из тела `with` бросается внутрь генератора в точке `yield`. Код после `yield` не выполняется, если нет `try/finally`, и ресурс не закрывается. Это самая частая ошибка в самописных менеджерах на собесе.

```python
class Swallow:
    def __enter__(self):

    def __exit__(self, exc_type, exc, tb):

```

--- why
Первый `__exit__` вернул True для `KeyError` — исключение подавлено, программа идёт дальше. Для `IndexError` он вернул False — исключение пролетело наружу, и «после второго» не напечаталось.

## ExceptionGroup и `except*` (3.11+):
Когда параллельно падает несколько задач (`asyncio.TaskGroup`), нужно сообщить обо всех ошибках сразу. `ExceptionGroup` объединяет их, а `except*` обрабатывает каждый тип отдельно — сработать могут несколько веток.
```python
try:
    raise ExceptionGroup("batch", [ValueError("a"), TypeError("b"), ValueError("c")])
except* ValueError as eg:
    print("value:", len(eg.exceptions))     # value: 2
except* TypeError as eg:
    print("type:", len(eg.exceptions))      # type: 1
```
`e.add_note("контекст")` добавляет к исключению пояснение, которое появится в трейсбеке.

* `temp_attr` — через `@contextmanager` временно поставить атрибут объекту и вернуть как было {test_temp_attr}

* `parse_config` — разобрать строки `ключ=целое`; при ошибке бросить `ConfigError` с номером строки и цепочкой `from` {test_parse_config}
+ `for n, line in enumerate(text.splitlines(), 1)`, пустые строки и строки с `#` пропусти, `key, sep, value = line.partition("=")`. `int(value)` в `try`; при `ValueError` — `raise ConfigError(f"строка {n}: …") from e`. Строка без `=` — тоже `ConfigError` (без `from`).

## Вопросы с собеседования по уроку:
::: quiz open q33-6 собес
Что такое контекстный менеджер? Как написать свой? Где они используются в бэкенде?
--- answer
Объект, который управляет входом в блок и выходом из него через протокол `__enter__`/`__exit__`. `with` вызывает `__enter__` (результат — в `as`) и гарантирует вызов `__exit__` при любом выходе: обычном, `return`, исключении. `__exit__` получает информацию об исключении и может его подавить, вернув True. Написать можно классом с этими методами или генератором с `@contextlib.contextmanager`: код до `yield` — вход, после — выход, и обязательно `try/finally` вокруг `yield`, иначе очистка не выполнится при исключении. Для асинхронного кода — `__aenter__`/`__aexit__` и `@asynccontextmanager`. В бэкенде: файлы, соединения и сессии БД, транзакции (`with conn:` в sqlite3, `transaction.atomic()` в Django, `async with session.begin()` в SQLAlchemy), блокировки (`with lock:`), временные настройки в тестах (`mock.patch`), HTTP-клиенты (`async with httpx.AsyncClient()`), lifespan в FastAPI. В `contextlib` также есть `suppress`, `ExitStack`, `closing`, `nullcontext`.
--- points
- протокол `__enter__` / `__exit__`, гарантия очистки
- подавление исключения возвратом True
- класс или `@contextmanager` с try/finally вокруг yield
- асинхронные менеджеры
- примеры: файлы, транзакции, блокировки, сессии, mock.patch
:::

::: quiz open q33-7
Как ты строишь иерархию исключений в приложении и где их ловишь?
--- answer
Своё базовое исключение приложения (`class AppError(Exception)`) и от него доменные: `NotFoundError`, `ValidationError`, `PaymentDeclined`. Так вызывающий может поймать или конкретную ошибку, или всё прикладное разом, не задевая системные. Исключения нижних слоёв (драйвера БД, HTTP-клиента) на границе слоя оборачиваю в доменные через `raise … from e`, чтобы бизнес-логика не зависела от библиотек, а причина сохранилась в трейсбеке. Ловлю там, где могу осмысленно обработать: повторить, вернуть клиенту понятный HTTP-статус (обработчики исключений в FastAPI или middleware в Django), откатить транзакцию. В остальных местах — пропускаю наверх. Никаких голых `except:` и `except Exception: pass`: в крайнем случае логирую с трейсбеком (`logger.exception`) и пробрасываю дальше.
--- points
- базовое исключение приложения и доменные подклассы
- оборачивание чужих ошибок через from
- ловить там, где можешь обработать
- маппинг на HTTP-ответы в одном месте
- без голого except, логирование с трейсбеком
:::
