# 4.2 Наследование, MRO, дескрипторы и метаклассы

## Множественное наследование и MRO:
Python поддерживает множественное наследование. Порядок поиска методов — **MRO** (method resolution order), который вычисляется алгоритмом **C3-линеаризации**. Его гарантии:
- класс идёт раньше своих родителей
- родители — в том порядке, в котором перечислены в `class D(B, C)`
- порядок согласован для всех предков (иначе `TypeError: Cannot create a consistent MRO`)

`super()` — это **не «родитель»**, а «следующий класс в MRO объекта». Поэтому в ромбе каждый класс вызывается ровно один раз, если все методы зовут `super()` (кооперативное наследование).

::: quiz output q42-1 собес
Что выведет программа?
```python
class A:
    def hi(self):
        print("A")

class B(A):
    def hi(self):
        print("B")
        super().hi()

class C(A):
    def hi(self):
        print("C")
        super().hi()

class D(B, C):
    def hi(self):
        print("D")
        super().hi()

D().hi()
print([k.__name__ for k in D.__mro__])
```
--- answer
D
B
C
A
['D', 'B', 'C', 'A', 'object']
--- why
Ромб решается через MRO: `D → B → C → A → object`. `super()` внутри `B` для объекта типа `D` ведёт к `C`, а не к `A`, — хотя `B` про `C` ничего не знает. Поэтому `A.hi` вызывается один раз. Если бы `B` звал `A.hi(self)` напрямую, `C` был бы пропущен.
:::

## Миксины, ABC и Protocol:
- **миксин** — маленький класс с одной способностью (`JsonMixin`, `LoggingMixin`), его подмешивают через множественное наследование. Своего `__init__` обычно нет
- **ABC** (`abc.ABC`, `@abstractmethod`) — номинальный интерфейс: класс с нереализованными абстрактными методами нельзя создать, наследование явное
- **`typing.Protocol`** — структурный интерфейс («утиная типизация» для mypy): подходит любой класс с нужными методами, наследоваться не нужно. `@runtime_checkable` разрешает `isinstance` (он проверяет только наличие методов)

Что выбрать: Protocol — для зависимостей, которые описывает потребитель (репозиторий, клиент), особенно для чужих классов. ABC — если нужна общая реализация в базовом классе и защита от создания неполных реализаций.

## Дескрипторы — механизм под `property`, методами и ORM:
Дескриптор — объект-атрибут **класса** с методами `__get__`, `__set__` и/или `__delete__`.
- **data-дескриптор**: есть `__set__` или `__delete__` (`property`, поля ORM)
- **non-data-дескриптор**: только `__get__` (обычные функции → связанные методы, `classmethod`, `staticmethod`, `cached_property`)

Порядок поиска `obj.attr` (`object.__getattribute__`):
1. data-дескриптор в классе (по MRO) — побеждает всё
2. `obj.__dict__`
3. non-data-дескриптор или обычный атрибут класса
4. `__getattr__`, если определён, — **только когда ничего не нашлось**

```python
class Positive:
    def __set_name__(self, owner, name):       # 3.6+: узнать имя поля
        self.name = name
    def __get__(self, obj, owner):
        if obj is None:
            return self                        # доступ через класс
        return obj.__dict__[self.name]
    def __set__(self, obj, value):
        if value <= 0:
            raise ValueError(f"{self.name} должно быть > 0")
        obj.__dict__[self.name] = value

class Order:
    qty = Positive()
    def __init__(self, qty):
        self.qty = qty                         # → Positive.__set__
```

::: quiz output q42-2 собес
Что выведет программа?
```python
class NonData:
    def __get__(self, obj, owner):
        return "descriptor"

class Data(NonData):
    def __set__(self, obj, value):
        raise AttributeError("read-only")

class C:
    nd = NonData()
    d = Data()

c = C()
c.__dict__["nd"] = "instance"
c.__dict__["d"] = "instance"
print(c.nd, c.d)
```
--- answer
instance descriptor
--- why
Data-дескриптор стоит в цепочке **раньше** словаря экземпляра, а non-data — **после**. Именно поэтому `cached_property` работает: при первом обращении он кладёт значение в `obj.__dict__`, и дальше дескриптор уже не вызывается. А `property` нельзя «перекрыть» присваиванием в экземпляр.
:::

## `__getattr__` и `__getattribute__`:
- `__getattribute__` вызывается при **каждом** обращении к атрибуту. Переопределять опасно: легко уйти в бесконечную рекурсию (внутри — только `super().__getattribute__`)
- `__getattr__` вызывается, **только если атрибут не найден** обычным путём. Нужен для прокси, ленивой загрузки, обёрток над API

::: quiz output q42-3
Что выведет программа?
```python
class Lazy:
    x = 1
    def __getattr__(self, name):
        return f"нет {name}"

o = Lazy()
o.y = 2
print(o.x, o.y, o.z)
```
--- answer
1 2 нет z
--- why
`x` нашёлся в классе, `y` — в экземпляре, и `__getattr__` для них не вызывался. Для `z` обычный поиск провалился, сработал `__getattr__`.
:::

## `__slots__`:
`__slots__ = ("x", "y")` убирает у экземпляров `__dict__`: атрибуты хранятся в фиксированных слотах (это тоже дескрипторы). Экземпляр занимает меньше памяти, а доступ немного быстрее. Нельзя добавить атрибут, которого нет в списке. Нюанс: если родитель без `__slots__`, у потомка всё равно будет `__dict__`.

## Метаклассы:
Класс — объект; его тип — **метакласс**, по умолчанию `type`. Оператор `class` — это вызов `type(name, bases, namespace)`. Свой метакласс (наследник `type`) может вмешаться в создание класса: проверить, зарегистрировать, добавить методы. Применение — ORM (Django-модели), регистрация плагинов, `ABCMeta`, `EnumMeta`. Но в 90% случаев хватает `__init_subclass__` (3.6) или декоратора класса — это проще.

::: quiz output q42-4 собес
Что выведет программа?
```python
class Meta(type):
    def __new__(mcls, name, bases, ns):
        print("создаю класс", name)
        return super().__new__(mcls, name, bases, ns)

class C(metaclass=Meta):
    pass

print(type(C()).__name__, type(C).__name__, type(type).__name__)
print(isinstance(C, type), issubclass(Meta, type))
```
--- answer
создаю класс C
C Meta type
True True
--- why
Метакласс вызывается **при определении класса** (при импорте модуля). Тип экземпляра — `C`, тип класса — его метакласс `Meta`, тип `type` — сам `type`. `C` — экземпляр `type` (через `Meta`), но не наследник: это отношение «экземпляр — класс», а не «подкласс — класс».
:::

## `__init_subclass__` — регистрация без метаклассов:
```python
class Handler:
    registry = {}
    def __init_subclass__(cls, kind, **kwargs):
        super().__init_subclass__(**kwargs)
        Handler.registry[kind] = cls

class CsvHandler(Handler, kind="csv"): ...
Handler.registry      # {'csv': <class 'CsvHandler'>}
```

Как лучше всего сделать синглтон в Python?
- [ ] метакласс — это единственный правильный способ
- [x] чаще всего — просто модуль: он импортируется один раз, и объект на уровне модуля — уже единственный; если нужен именно класс — `__new__` или метакласс, плюс блокировка для потоков
- [ ] глобальная переменная внутри функции
- [ ] синглтоны в Python невозможны
--- why
Модуль кэшируется в `sys.modules`, поэтому `settings = Settings()` на уровне модуля — естественный синглтон. Классовые варианты (`__new__` с проверкой `cls._instance`, метакласс со словарём экземпляров, декоратор) спрашивают на собесах, и у всех одна ловушка: без `threading.Lock` два потока могут создать два экземпляра. И главный минус синглтонов — глобальное состояние мешает тестам. В приложениях лучше внедрять зависимость явно.
:::

::: hw 42
* `Positive` — дескриптор-валидатор: число больше нуля, иначе `ValueError`, не число — `TypeError` {test_positive}
+ `__set_name__` запоминает имя; `__set__` проверяет `isinstance(value, (int, float))` и `value > 0` (bool — не число!), кладёт в `obj.__dict__[name]`; `__get__` при `obj is None` возвращает сам дескриптор, иначе значение из `obj.__dict__`.
! Хранить значение в самом дескрипторе (`self.value`) нельзя: дескриптор один на класс, и все экземпляры будут делить одно значение. `True` — подкласс `int`, исключи его явно.
* `cached_prop` — свой `functools.cached_property`: вычислить один раз и сохранить в экземпляре {test_cached_prop}
+ Non-data-дескриптор: только `__get__`. При первом обращении вызови функцию, положи результат в `obj.__dict__[name]` и верни. Следующие обращения найдут значение в `__dict__` раньше дескриптора.
! Не добавляй `__set__`: тогда дескриптор станет data-дескриптором, и словарь экземпляра перестанет иметь приоритет — кэш не сработает. `del obj.attr` должен сбрасывать кэш.
* `Plugin` — базовый класс с регистрацией наследников через `__init_subclass__` {test_plugin}
+ `def __init_subclass__(cls, name=None, **kwargs)`: вызови `super().__init_subclass__(**kwargs)`, имя по умолчанию — `cls.__name__.lower()`. Если имя уже занято — `ValueError`. Сохрани в `Plugin.registry[name] = cls`. `Plugin.create(name, *args)` — `classmethod`, создающий экземпляр по имени (неизвестное имя — `KeyError`).
! Реестр должен быть **один** — на базовом классе. `cls.registry[name] = ...` внутри подкласса тоже работает (атрибут найдётся у базового класса), но легко случайно создать копию в подклассе через присваивание `cls.registry = {}`.
* `SingletonMeta ★` — метакласс: у каждого класса с ним — один экземпляр, `__init__` вызывается один раз, потокобезопасно {test_singleton}
+ Переопредели `__call__(cls, *args, **kwargs)`: словарь `_instances` на метаклассе, `threading.Lock`. Под блокировкой — если `cls` нет в словаре, `super().__call__(*args, **kwargs)` и сохранить. Вернуть экземпляр.
! `__call__` метакласса вызывается при `Cls()` — именно он запускает `__new__` и `__init__`, поэтому повторный вызов не должен доходить до `super().__call__`. Разные классы — разные экземпляры. Тест создаёт экземпляр из 20 потоков одновременно.

## Вопросы с собеседования по уроку:
::: quiz open q42-6 собес
Что такое MRO и как работает `super()` при множественном наследовании?
--- answer
MRO — порядок, в котором Python ищет атрибуты в иерархии классов (`Cls.__mro__`). Он строится алгоритмом C3-линеаризации: класс раньше родителей, родители — в порядке перечисления, порядок согласован для всех предков; если согласовать нельзя — `TypeError` при создании класса. `super()` возвращает прокси к следующему классу в MRO **объекта**, а не к родителю текущего класса. Поэтому в ромбе `D(B, C)`, где `B` и `C` наследуют `A`, цепочка `super()` пройдёт `D → B → C → A`, и `A` вызовется один раз. Для этого все классы должны вызывать `super()` и принимать `**kwargs`, передавая их дальше (кооперативное наследование). Практический совет: множественное наследование — для миксинов без состояния, а в остальных случаях лучше композиция.
--- points
- MRO — порядок поиска атрибутов, `__mro__`
- C3: класс раньше родителей, порядок перечисления, согласованность
- super() — следующий в MRO объекта, а не родитель
- ромб: каждый класс один раз при кооперативных super()
- миксины и композиция
:::

::: quiz open q42-7 собес
Что такое дескрипторы? Где они используются? Чем отличаются от декораторов?
--- answer
Дескриптор — объект, лежащий атрибутом класса и определяющий `__get__`, `__set__` или `__delete__`. Он перехватывает доступ к атрибуту экземпляра. Data-дескрипторы (с `__set__`/`__delete__`) приоритетнее словаря экземпляра, non-data (только `__get__`) — нет. На дескрипторах построены `property`, методы (функция — non-data-дескриптор, её `__get__` возвращает связанный метод, так появляется `self`), `classmethod`, `staticmethod`, `cached_property`, `__slots__`, поля ORM (Django и SQLAlchemy перехватывают присваивание и делают ленивую загрузку связей), валидаторы полей. Декоратор — другое: функция, которая оборачивает функцию или класс в момент определения. Они пересекаются: `@property` — декоратор, который создаёт дескриптор.
--- points
- протокол `__get__` / `__set__` / `__delete__`, атрибут класса
- data против non-data и приоритет над `__dict__`
- примеры: property, методы и self, classmethod, slots
- ORM и валидаторы
- отличие от декоратора и связь через @property
:::
