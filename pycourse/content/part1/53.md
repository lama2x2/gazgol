# 5.3 asyncio: event loop, задачи, отмена

## Как это работает:
**asyncio** — кооперативная многозадачность в **одном потоке**. Есть **цикл событий (event loop)**: он держит очередь готовых к выполнению задач и следит за сокетами и таймерами (через `epoll`/`kqueue`).
- `async def f()` — корутинная функция; вызов `f()` **ничего не выполняет**, а создаёт объект корутины
- `await x` — «выполни x; если ему надо ждать I/O, отдай управление циклу, а когда данные придут — продолжи меня». Переключение происходит **только в точках `await`**
- **Task** — корутина, поставленная в цикл: `asyncio.create_task(coro)`. Она начнёт выполняться, когда текущая задача отдаст управление
- `asyncio.run(main())` — создать цикл, выполнить `main`, закрыть цикл

Отсюда главные правила: **блокирующий вызов (`time.sleep`, `requests.get`, тяжёлый расчёт) останавливает весь цикл** — все остальные задачи ждут. И гонки в asyncio тоже бывают, но только «между `await`»: между двумя `await` код атомарен относительно других задач.

import asyncio

async def job(name, delay):

    await asyncio.sleep(delay)
    print("конец", name)
    return name

--- answer

конец A
['A', 'B']
--- why
`gather` оборачивает обе корутины в задачи и запускает конкурентно: обе стартуют, пока первая ждёт. B просыпается раньше. Но результаты `gather` возвращает **в порядке аргументов**, а не завершения.

## Последовательно или конкурентно:
```python
for url in urls:
    await fetch(url)                     # последовательно: каждый ждёт предыдущий

results = await asyncio.gather(*(fetch(u) for u in urls))   # конкурентно, порядок как во входе

async with asyncio.TaskGroup() as tg:    # 3.11: структурная конкурентность
    tasks = [tg.create_task(fetch(u)) for u in urls]
results = [t.result() for t in tasks]
```
| | `gather` | `TaskGroup` |
|---|---|---|
| одна задача упала | исключение уходит наружу, **остальные продолжают работать** (никто их не отменяет) | остальные **отменяются**, все ошибки собираются в `ExceptionGroup` |
| `return_exceptions=True` | ошибки возвращаются как результаты | — |
| «потерянные» задачи | возможны | нет: группа ждёт всех |

## Ограничение параллельности, таймауты, очереди:
```python
sem = asyncio.Semaphore(10)              # не больше 10 запросов одновременно
async def limited(url):
    async with sem:
        return await fetch(url)

async with asyncio.timeout(2):           # 3.11; раньше — asyncio.wait_for(coro, 2)
    data = await fetch(url)              # по истечении: отмена и TimeoutError

queue = asyncio.Queue(maxsize=100)       # producer-consumer с обратным давлением (backpressure)
```

## Отмена задач:
`task.cancel()` бросает `asyncio.CancelledError` внутрь задачи в точке `await`. Задача может сделать очистку в `finally`, но **не должна проглатывать** `CancelledError`: иначе ломаются таймауты и `TaskGroup`. Это наследник `BaseException`, поэтому `except Exception` его не ловит, и это правильно. `asyncio.shield(aw)` защищает операцию от отмены снаружи.

## Мостики между sync и async:
| Задача | Как |
|---|---|
| вызвать блокирующую функцию из async | `await asyncio.to_thread(f, *args)` или `loop.run_in_executor(pool, f)` |
| CPU-тяжёлое из async | `run_in_executor(ProcessPoolExecutor(), f)` |
| запустить async из sync-кода | `asyncio.run(coro)` (если цикла нет) |
| из другого потока в работающий цикл | `asyncio.run_coroutine_threadsafe(coro, loop)` |
| синхронная БД в FastAPI | эндпоинт `def` (не `async def`): FastAPI сам выполнит его в пуле потоков |

## Вопросы с собеседования по уроку:
::: quiz open q53-5 собес
Как работает asyncio? Чем асинхронность отличается от многопоточности?
--- answer
asyncio — однопоточная кооперативная многозадачность. Цикл событий держит очередь готовых задач и через системные механизмы (`epoll`, `kqueue`) следит за сокетами и таймерами. Корутина выполняется до `await` на операции, которая должна ждать; тогда она отдаёт управление, цикл запускает другую готовую задачу, а когда данные придут, возобновит первую. Переключение только явное, в точках `await`. Многопоточность — вытесняющая: ОС (и GIL в CPython) переключает потоки в любой момент, поэтому любые общие данные требуют блокировок. Отличия: asyncio масштабируется на десятки тысяч соединений (корутина — несколько килобайт, поток — мегабайты стека и переключения ядра), гонок меньше (код между `await` атомарен), но нужна вся экосистема асинхронной (асинхронные драйверы БД, HTTP-клиенты), а любой блокирующий вызов или тяжёлый расчёт замораживает весь цикл. Потоки работают с любыми синхронными библиотеками, но дороже и опаснее с общим состоянием. Оба способа не дают параллелизма для CPU в CPython: для него — процессы.
--- points
- один поток, цикл событий, epoll/kqueue
- корутины, await как точка переключения, задачи
- кооперативная против вытесняющей многозадачности
- масштабируемость и меньше гонок
- блокирующие вызовы останавливают цикл; to_thread
- CPU-bound — ни то ни другое, процессы
:::

::: quiz open q53-6 собес
Чем `asyncio.gather` отличается от `TaskGroup`? Что происходит, если одна из задач падает?
--- answer
`gather(*aws)` запускает корутины конкурентно и возвращает результаты в порядке аргументов. Если одна падает, `gather` сразу пробрасывает её исключение, но остальные задачи **не отменяются** и продолжают работать в фоне — их ошибки могут потеряться. С `return_exceptions=True` исключения возвращаются в списке результатов. `TaskGroup` (3.11) реализует структурную конкурентность: при выходе из `async with` группа ждёт все задачи; если одна упала, остальные отменяются, а все ошибки (кроме отмены) собираются в `ExceptionGroup`, который обрабатывают через `except*`. Задачи не «утекают» за пределы блока. Поэтому для новых проектов предпочтительнее `TaskGroup`, а `gather(return_exceptions=True)` — когда нужно собрать частичные результаты, несмотря на ошибки.
--- points
- порядок результатов в gather
- при падении: gather не отменяет остальных
- return_exceptions
- TaskGroup отменяет остальные и собирает ExceptionGroup
- except* и структурная конкурентность
:::
