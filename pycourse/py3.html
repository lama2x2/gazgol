11.1 Задачи «как в продакшене»

Чем практический лайвкод отличается от алгоритмического:

На платформенной секции (Авито, Ozon, Kaspersky, Т-Банк) часто дают не LeetCode, а маленькую рабочую задачу: кэш, разбор логов, синхронизация данных, ретраи. Алгоритм там обычно простой. Оценивают:

  • понимание требований: какие данные, сколько их, что делать с ошибками, нужна ли потокобезопасность
  • идиоматичный Python: collections, генераторы, контекстные менеджеры, dataclass, аннотации
  • инженерные вопросы: память на больших данных, сложность, граничные случаи, тестируемость (время и случайность — параметрами)
  • развитие решения: «а если данных в 100 раз больше?», «а если из нескольких потоков?», «а если упадёт посередине?»

Как отвечать на «а если…»

Не переписывай молча. Сначала назови, что сломается («Counter не влезет в память», «два потока одновременно пройдут проверку»), потом — варианты с компромиссами («разбить по хешу на файлы — точно, но медленно; Count-Min Sketch — приближённо и в фиксированной памяти»), потом спроси, что важнее. Это и есть сигнал middle+.

LRU-кэш — самая частая задача этого типа:

from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity):
        self.capacity = capacity
        self.data = OrderedDict()

    def get(self, key, default=None):
        if key not in self.data:
            return default
        self.data.move_to_end(key)            # стал самым свежим
        return self.data[key]

    def put(self, key, value):
        self.data[key] = value
        self.data.move_to_end(key)
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)     # выкинуть самый старый

Следующие вопросы интервьюера: «без OrderedDict» (словарь + двусвязный список, урок 8.2), «с TTL», «потокобезопасно» (threading.Lock вокруг операций), «чем functools.lru_cache отличается» (кэширует функцию по аргументам, без TTL, есть cache_info).

Синхронизация с «плохим» API (задача с собесов middle)

«Раз в час скачиваем JSON из 100 000+ объектов с первичным ключом. Нужно создать новые записи, обновить изменившиеся и пометить удалёнными те, которых нет в выгрузке».

*«Наивно — запрос в БД на каждую запись: 100 000 запросов. Лучше построить два словаря "id → данные": из выгрузки и из базы (или батчами по 1000 id), — и посчитать три множества: api - db создать, db - api удалить, пересечение с отличающимися данными — обновить. Это O(n). Запись — пакетно: executemany, INSERT … ON CONFLICT DO UPDATE, или загрузка во временную таблицу и три SQL-запроса. Если выгрузка не влезает в память — стримить JSON (ijson) и сравнивать батчами, отсортированными по id».*

def sync_diff(db: dict, api: dict):
    db_ids, api_ids = db.keys(), api.keys()
    create = sorted(api_ids - db_ids)
    delete = sorted(db_ids - api_ids)
    update = sorted(k for k in api_ids & db_ids if api[k] != db[k])
    return create, update, delete

dict.keys() поддерживает операции множеств — это часто забывают.

Вопрос с собесаКак бы ты сделал кэш для сервиса, который ходит в медленное внешнее API? Какие вопросы надо решить?

Эталонный ответ

Сначала требования: насколько свежими должны быть данные (TTL), объём и число ключей (память, вытеснение — LRU/LFU), один процесс или много (локальный кэш в памяти против общего Redis), допустимы ли устаревшие данные при недоступности API. Устройство: cache-aside — читаем кэш, при промахе идём в API и кладём результат с TTL. Проблемы и решения: cache stampede — когда горячий ключ истёк, тысяча запросов одновременно идёт в API; лечится блокировкой или singleflight («один загружает, остальные ждут»), ранним фоновым обновлением, случайным разбросом TTL. Инвалидация — по событию об изменении или по TTL. Отрицательное кэширование — кэшировать «не найдено» на короткое время. Отказ API — отдавать устаревшее значение (stale-while-revalidate), circuit breaker. Двухуровневый кэш: локальный LRU плюс Redis. Метрики: hit rate, задержки, размер. Сериализация и размер значений в Redis, а ключи — с версией схемы, чтобы безопасно выкатывать изменения формата.

11.2 Бизнес-логика: банкомат, уведомления, бронирование

Формат:

Яндекс на Python-позициях часто даёт не алгоритм, а бизнес-задачу: банкомат, заказ такси, фильтр уведомлений, бронирование. Оценивают чистоту кода, обработку ошибок и то, как кандидат рассуждает. Типичный провал из реального отзыва: потратить 20 минут на модели данных и не дойти до логики фильтра.

План на такую задачу:

  1. Сценарии и инварианты (3–5 минут): что система должна делать, что запрещено («нельзя выдать больше, чем есть в кассетах», «бронь не пересекается с другой»), что при ошибке
  2. Минимальная модель: dataclass для сущностей, Enum для статусов, один класс-сервис с публичными методами. Не строй иерархии «на будущее»
  3. Ядро логики — сначала счастливый путь, затем ошибки. Ошибки — своими исключениями, а не return False
  4. Атомарность: если операция не удалась, состояние не меняется (сначала вычисли, потом применяй)
  5. Тестируемость: время, случайность, хранилища — параметрами
  6. Расширения вслух: конкурентный доступ (блокировки, транзакции в БД), персистентность, масштабирование

Конечный автомат статусов заказа

Половина бизнес-задач — про допустимые переходы. Таблица переходов вместо россыпи if:

from enum import Enum

class Status(Enum):
    CREATED = "created"
    PAID = "paid"
    SHIPPED = "shipped"
    DELIVERED = "delivered"
    CANCELLED = "cancelled"

TRANSITIONS = {
    Status.CREATED: {Status.PAID, Status.CANCELLED},
    Status.PAID: {Status.SHIPPED, Status.CANCELLED},
    Status.SHIPPED: {Status.DELIVERED},
}

class InvalidTransition(Exception):
    pass

def move(current: Status, new: Status) -> Status:
    if new not in TRANSITIONS.get(current, set()):
        raise InvalidTransition(f"{current.value} → {new.value}")
    return new

Новый статус добавляется правкой таблицы, а не кода. Ту же таблицу можно отрисовать для документации и проверить тестом, что из каждого статуса достижим финальный.

11.2 Бизнес-логика: банкомат, уведомления, бронирование

Банкомат и почему жадность ломается:

Выдать сумму минимальным числом купюр, если купюр ограниченное количество. Жадно «берём крупную, пока можно» неверно: в кассетах 50 × 1 и 20 × 3, сумма 60. Жадно — взяли 50, осталось 10, выдать нельзя. А 20 + 20 + 20 — можно. Решение — перебор от крупных номиналов с откатом (номиналов мало, перебор быстрый) или динамика по сумме.

ВыбериВ withdraw банкомат посчитал, какие купюры выдать, но при выдаче второй кассеты случилась ошибка. Как должна быть устроена операция?· частый вопрос на собесе

Почему

Это атомарность на уровне объекта: «вычислить, потом применить». В реальной системе применение — транзакция в БД, а физическая выдача — отдельный шаг с компенсацией (если купюры не вышли, вернуть остатки и отменить списание). Интервьюер ждёт, что ты сам заговоришь о том, что будет при сбое посередине.

Фильтр уведомлений (задача из реального собеса Яндекса):

«Уведомление: id, тип (EMAIL/SMS/PUSH), получатель, отправитель, текст. Применить настройки получателя (разрешённые каналы, заблокированные отправители) и не отправлять дубликаты за 24 часа». Хранилище не нужно — только контракты и логика. Ждут работающий фильтр с тремя проверками. Ключ дедупликации — (получатель, канал, текст); окно — по времени отправки, часы передаются параметром.

bookings = []

def book(room, start, end, user):
    for b in bookings:
        if b["room"] == room and b["start"] < end and start < b["end"]:

Эталонный ответ
  • глобальное изменяемое состояние — модульный список: нельзя иметь два независимых экземпляра, тесты влияют друг на друга. Класс-сервис с хранилищем, переданным в конструктор

  • гонка: два параллельных запроса оба пройдут проверку и забронируют одно время → блокировка на комнату в памяти; в БД — EXCLUDE-ограничение PostgreSQL по диапазону времени или SELECT … FOR UPDATE

  • время: часовые пояса (хранить в UTC, datetime с tzinfo)
  • проверка пересечения b.start < end and start < b.end правильная (полуинтервалы), её стоит оставить и покрыть тестами на касание

11.3 Код-ревью и поиск ошибок

Формат:

Всё чаще вместо «напиши» дают «вот код, что с ним не так?»: Сбер, Wildberries, Ozon. Проверяют внимательность, знание подводных камней языка и инженерный кругозор. За 20 минут нужно найти как можно больше проблем и расставить приоритеты.

Чек-лист ревьюера — иди сверху вниз:

  1. Корректность: граничные случаи (пусто, один элемент, границы диапазонов), ошибки на единицу, неправильные условия, забытый return, изменение коллекции при обходе
  2. Ловушки Python: изменяемые аргументы по умолчанию, позднее связывание в замыканиях, is вместо ==, общий список через *, мутация входных данных, except: без типа, return в finally
  3. Безопасность: SQL-инъекции (f-строки в запросах), секреты в коде, пароли без хеширования, eval/pickle на недоверенных данных, отсутствие проверки прав
  4. Ресурсы и надёжность: незакрытые файлы и соединения (нет with), отсутствие таймаутов у сетевых вызовов, ретраи без backoff, проглоченные исключения
  5. Конкурентность: гонки check-then-act, блокирующие вызовы в async def, общее изменяемое состояние
  6. Производительность: N+1 запросы к БД, O(n²) там, где можно O(n), загрузка всего в память
  7. Дизайн и читаемость: имена, длина функций, дублирование, жёсткие зависимости, тестируемость

Как подавать замечания

Начни с самого опасного («здесь SQL-инъекция — это блокер»), отделяй блокеры от стиля, к каждому замечанию — почему это плохо и как исправить. «Здесь requests.get без таймаута: если сервис повиснет, повиснет и воркер. Добавить timeout=5 и ретраи с backoff».

Эталонный ответ

INNER JOIN оставляет только строки, для которых нашлась пара по условию соединения. LEFT JOIN оставляет все строки левой таблицы; если пары нет, столбцы правой — NULL. Индекс — как он устроен:

Обычный индекс в PostgreSQL и MySQL — B+-дерево: отсортированные ключи в широких узлах размером со страницу диска (8 КБ), листья связаны в список. Поиск по равенству и диапазону — O(log n) с очень маленькой высотой (3–4 уровня на миллионы строк), плюс последовательное чтение листьев для диапазона и ORDER BY. Цена — место на диске и замедление записи: каждый INSERT/UPDATE обновляет все индексы таблицы.

Составной индекс (a, b, c) и правило левого префикса:

Строки отсортированы по a, при равных a — по b, затем по c. Поэтому индекс помогает для условий на a, a и b, a и b и c, для a = ? ORDER BY b, но не для условия только на b или c. Столбцы с равенством — первыми, столбец диапазона или сортировки — после них.

Когда индекс не помогает (вопрос в 27% интервью):

  • функция или выражение над столбцом: WHERE lower(email) = …, WHERE created_at::date = … → нужен индекс по выражению или переписать условие диапазоном
  • LIKE '%текст' — с ведущим % (для поиска подстроки — триграммы pg_trgm или полнотекстовый поиск)
  • низкая селективность: WHERE status = 'active', когда активны 90% строк, — полное сканирование дешевле
  • условие не на левый префикс составного индекса
  • несовпадение типов, неявное приведение
  • OR по разным столбцам (иногда спасает Bitmap Or)
  • маленькая таблица — планировщику проще прочитать её целиком
  • устаревшая статистика — планировщик ошибается в оценках (ANALYZE)

Покрывающий индекс: если все нужные столбцы есть в индексе (INCLUDE (…) в PostgreSQL), база не ходит в таблицу — Index Only Scan.

  • PostgreSQL реализует изоляцию через MVCC: у строки несколько версий, читатель видит снимок и не блокирует писателя. Repeatable Read в нём — изоляция снимка. Serializable (SSI) может отменить транзакцию с ошибкой сериализации — приложение обязано повторить её

Блокировки:

  • SELECT … FOR UPDATE — заблокировать строки до конца транзакции (пессимистично). NOWAIT — сразу ошибка, если занято; SKIP LOCKED — пропустить занятые строки (очередь задач в таблице: каждый воркер берёт свои)
  • оптимистичная блокировка: столбец version, UPDATE … WHERE id = ? AND version = ?; обновилось 0 строк — кто-то успел раньше, перечитать и повторить. Хороша, когда конфликты редки
  • deadlock между транзакциями — база найдёт цикл и отменит одну. Лечится одинаковым порядком обновления строк и короткими транзакциями

ВыбериДва запроса одновременно покупают последний товар: SELECT stock …; if stock > 0: UPDATE products SET stock = stock - 1. На Read Committed что может произойти и как исправить?· частый вопрос на собесе

Почему

Read Committed не защищает от гонки «прочитал — решил — записал». Самое простое и быстрое решение — перенести проверку внутрь UPDATE: строка блокируется на время обновления, второй запрос дождётся и увидит stock = 0. Ограничение CHECK — страховка на уровне данных.

Вопрос с собесаРасскажи про уровни изоляции транзакций. Какие аномалии они предотвращают? Какой уровень по умолчанию в PostgreSQL?

Эталонный ответ

Стандарт SQL определяет четыре уровня по допускаемым аномалиям. Read Uncommitted допускает грязное чтение (видны незакоммиченные изменения других транзакций) — в PostgreSQL он ведёт себя как Read Committed. Read Committed (по умолчанию в PostgreSQL) — каждый запрос видит снимок на свой момент, поэтому возможны неповторяющееся чтение и фантомы, а также потерянное обновление при схеме «прочитал — изменил в приложении — записал». Repeatable Read — снимок на начало транзакции; в PostgreSQL это snapshot isolation, фантомов нет, но возможна аномалия write skew (две транзакции читают пересекающиеся данные и пишут разные строки, нарушая общий инвариант — например, «хотя бы один врач на дежурстве»); при конфликте записи одна транзакция получает ошибку сериализации. Serializable в PostgreSQL — SSI: результат эквивалентен последовательному выполнению, конфликтующие транзакции отменяются, и приложение должно их повторять. Реализация — MVCC: читатели не блокируют писателей. На практике — Read Committed плюс точечные средства: атомарные условные UPDATE, SELECT FOR UPDATE, оптимистичные версии, ограничения UNIQUE/CHECK, а Serializable — для сложных инвариантов с ретраями.

Эталонный ответ

Сессия: сервер хранит состояние (в Redis или БД), клиент получает cookie с непредсказуемым идентификатором (HttpOnly, Secure, SameSite). Для классического веб-приложения с браузером обычно проще и безопаснее сессии. Для API с мобильными клиентами и межсервисных вызовов — JWT (часто выпускаемые внешним Identity Provider по OAuth 2.0/OIDC), с коротким сроком жизни. 13.2 WSGI, ASGI, Django и FastAPI

WSGI и ASGI:

WSGI (PEP 3333) — синхронный контракт между веб-сервером и приложением: приложение — вызываемый объект app(environ, start_response), который возвращает итерируемое тело.

def app(environ, start_response):
    body = b'{"status": "ok"}'
    start_response("200 OK", [("Content-Type", "application/json"),
                              ("Content-Length", str(len(body)))])
    return [body]

Один запрос занимает воркер (процесс или поток) до конца: долгие соединения (WebSocket, стриминг) так не держат. Серверы — gunicorn, uWSGI. Фреймворки — Django (классически), Flask.

ASGI — асинхронный контракт: async def app(scope, receive, send). События приходят и уходят сообщениями: http.request (тело, возможно кусками с more_body), http.response.start, http.response.body, плюс websocket.* и lifespan.* (старт и остановка приложения). Серверы — uvicorn, hypercorn, granian. Фреймворки — FastAPI/Starlette, Django (с 3.0), Litestar.

Как запускают в продакшене:

  • gunicorn с N процессами-воркерами (обычно 2 × ядра + 1 для синхронных); для ASGI — uvicorn.workers.UvicornWorker или сам uvicorn --workers N

Вопрос с собесаЧем WSGI отличается от ASGI? Когда в FastAPI писать async def, а когда def?

Эталонный ответ

WSGI — синхронный интерфейс: приложение — функция (environ, start_response), запрос целиком обрабатывается в одном воркере (процесс или поток), конкурентность — числом воркеров. Если используются синхронные библиотеки (requests, синхронная ORM, тяжёлые расчёты), — обычный def: FastAPI запустит его в пуле потоков, и цикл не заблокируется. Худший вариант — блокирующий вызов в async def: он останавливает обработку всех запросов воркера. CPU-тяжёлое — в процессы или очередь задач.

Вопрос с собесаКак в Django избежать проблемы N+1? Чем select_related отличается от prefetch_related?

Эталонный ответ

N+1 — когда на каждый объект из списка уходит дополнительный запрос за связанным объектом: 1 запрос за списком + N за связями. В Django это происходит из-за ленивой загрузки связей. select_related делает SQL-JOIN и загружает связанные объекты одним запросом. Работает для «одиночных» связей — ForeignKey и OneToOne в прямую сторону. prefetch_related делает отдельный запрос на каждую связь (WHERE id IN (...)) и склеивает результаты в Python. Нужен для обратных ForeignKey (author.books) и ManyToMany, где JOIN размножил бы строки; объект Prefetch позволяет задать фильтр и select_related для вложенного запроса.   • Кэш ответов с TTL по допустимой свежести: профиль меняется редко — минуты и часы, рекомендации — десятки минут. Stale-while-revalidate: отдаём устаревшее и обновляем в фоне. Singleflight против stampede

Домашка 14.2

Как решать

Как решать. Алфавит 0-9a-zA-Z. Кодирование: пока n > 0 — n, r = divmod(n, 62), символы с конца, затем развернуть; ноль — "0". Декодирование: n = n * 62 + ALPHABET.index(ch) (или словарь «символ → цифра»).

Подвох. Отрицательное число и неизвестный символ — ValueError. Пустая строка — тоже ошибка. Тест проверяет обратимость на случайных числах до 2⁶⁴.

Как решать

Как решать. id = (ms - epoch) << 22 | node << 12 | seq. В той же миллисекунде — seq += 1; дошли до 4096 — подожди следующую миллисекунду (крути clock()); новая миллисекунда — seq = 0. Всё под threading.Lock. Номер узла — от 0 до 1023, иначе ValueError.

Подвох. Часы подменяются тестом. Если время пошло назад — ClockMovedBackwards: id не должны повторяться. id из 8 потоков одновременно — все уникальны.

Как решать

Как решать. Счётчик id → base62_encode. shorten(url, alias=None, ttl=None): проверь URL (urlsplit: схема http/https и непустой netloc), алиас — 3–32 символа из алфавита base62 и не занят.
