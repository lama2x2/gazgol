1.1 Этапы, форматы компаний и критерии оценки

Этапы в крупных компаниях:

  1. HR-скрининг — опыт, мотивация, ожидания по деньгам
  2. Технический скрининг — короткие вопросы с однозначными ответами: язык, базы, сеть
  3. Алгоритмическая секция — 1–2 задачи уровня LeetCode easy/medium, оценка сложности
  4. Платформенная (языковая) секция — вопросы по Python от простого к сложному плюс лайвкод
  5. System design — с уровня middle
  6. Встреча с командой — от неформального разговора до ещё одной технической секции

В небольших компаниях часто всё сжато до HR и одного длинного технического интервью, где перемешаны теория, лайвкод и SQL.

1.2 Как решать задачу на лайвкоде

Алгоритм на каждую задачу:

  1. Перескажи условие своими словами и разбери пример из условия руками
  2. Уточни ограничения: размер входа, диапазон чисел, могут ли быть пустые данные, повторы, отрицательные. Что вернуть, если ответа нет?
  3. Предложи простое решение (часто перебор) и назови его сложность. Это страховка: тебе уже есть что писать
  4. Улучши: где лишняя работа? Что можно запомнить в словаре? Можно ли отсортировать? Назови новую сложность
  5. Договорись с интервьюером и только потом пиши код, проговаривая крупные шаги
  6. Проверь сам: прогони пример строка за строкой, затем граничные случаи. Только после этого скажи «готово»

По времени на секции в час с двумя задачами: первая задача должна быть решена к 25–30-й минуте.

Граничные случаи, которые надо проверять всегда:

  • пустой ввод: [], "", 0
  • один элемент
  • все элементы одинаковые
  • уже отсортировано и отсортировано в обратном порядке
  • отрицательные числа и ноль
  • ответ в самом начале или в самом конце: здесь живут ошибки «на единицу» и «забыл последний отрезок»

Разбор задачи — как это звучит вслух:

Сжать список чисел в диапазоны (VK)

Условие: [1, 4, 5, 2, 3, 9, 8, 11, 0] → "0-5,8-9,11".

«Уточню: числа могут повторяться? Пустой список — пустая строка? Хорошо. Идея: отсортировать, затем один проход, в котором я держу начало текущего отрезка. Когда следующее число не продолжает отрезок — закрываю его. O(n log n) из-за сортировки, O(n) памяти на результат».

def compress(nums):
    if not nums:
        return ""
    nums = sorted(set(nums))
    parts = []
    start = prev = nums[0]
    for x in nums[1:]:
        if x == prev + 1:
            prev = x
            continue
        parts.append(f"{start}-{prev}" if start != prev else str(start))
        start = prev = x
    parts.append(f"{start}-{prev}" if start != prev else str(start))  # последний отрезок!
    return ",".join(parts)

«Проверяю на примере: после сортировки 0,1,2,3,4,5,8,9,11. Отрезок 0–5 закрывается на восьмёрке, 8–9 — на одиннадцати, 11 добавляется после цикла. Граничные: пустой — ""; один элемент — "7"; повторы убрал через set».

Типичные ошибки на этой задаче из реальных собесов: забыли отсортировать, потеряли последний отрезок, оставили лишнюю запятую, упали на пустом списке. Чистое решение за 12 минут — высшая оценка.

Найди багКандидат решил задачу «найти максимальное число в списке». Что не так?

def max_value(nums):
    best = 0
    for x in nums:
        if x > best:
            best = x
    return best
Почему

Начальное значение «0» — классическая ошибка. Нужно начинать с первого элемента (best = nums[0]) или с float("-inf"), а пустой список явно обработать: вернуть None или бросить ValueError, как это делает встроенная max([]). Об этом и стоит спросить интервьюера.

2.2 Коллекции изнутри: list, dict, set, collections

list — динамический массив:

Внутри — массив указателей на объекты (поэтому в списке могут лежать объекты разных типов). Когда место кончается, CPython выделяет новый массив с запасом (~12.5% сверху плюс константа) и переносит указатели. Поэтому:

  • append — O(1) амортизированно: редкие дорогие расширения размазываются по многим дешёвым вставкам
  • lst[i] — O(1): адрес вычисляется по индексу
  • insert(0, x) и pop(0) — O(n): сдвигаются все указатели
  • x in lst — O(n), линейный поиск

tuple — тоже массив указателей, но фиксированного размера: меньше памяти, хешируется, CPython кэширует маленькие кортежи.

dict — хеш-таблица:

  1. От ключа считается hash(key), по нему выбирается ячейка таблицы
  2. Если ячейка занята другим ключом (коллизия), CPython пробует следующие ячейки по псевдослучайной последовательности — это открытая адресация, а не цепочки списков
  3. Ключ сравнивается сначала по хешу, затем по is, затем по ==
  4. Когда таблица заполнена на 2/3, она увеличивается и все ключи перераскладываются

С Python 3.6 словарь компактный: отдельный разреженный массив индексов и плотный массив записей (hash, key, value) в порядке вставки. Отсюда экономия памяти и гарантированный (с 3.7) порядок вставки при обходе. set устроен так же, но без значений и без компактности — порядок у множеств не гарантирован.

«Как устроен словарь?» → «Какая сложность поиска? А в худшем случае?» (O(n), если все ключи с одним хешем) → «Почему ключ должен быть хешируемым?» → «Что будет, если изменить объект-ключ после вставки?» (хеш изменится, ключ «потеряется» в таблице) → «Почему порядок сохраняется?»

Декоратор:

Функции в Python — объекты первого класса: их можно передавать, возвращать, хранить в переменных. Декоратор — вызываемый объект, который принимает функцию и возвращает замену. @deco над def f — то же самое, что f = deco(f) сразу после определения.

import functools, time

def time_it(func):
    @functools.wraps(func)                 # переносит __name__, __doc__, __wrapped__…
    def wrapper(*args, **kwargs):          # любые аргументы
        start = time.perf_counter()
        try:
            return func(*args, **kwargs)   # не забыть вернуть результат
        finally:
            print(f"{func.__name__}: {time.perf_counter() - start:.3f} c")
    return wrapper

Декоратор с параметрами — три уровня:

def repeat(times):              # 1. фабрика: принимает параметры
    def decorator(func):        # 2. декоратор: принимает функцию
        @functools.wraps(func)
        def wrapper(*args, **kwargs):   # 3. обёртка: принимает аргументы вызова
            for _ in range(times - 1):
                func(*args, **kwargs)
            return func(*args, **kwargs)
        return wrapper
    return decorator

Множественное наследование и MRO:

Python поддерживает множественное наследование. Порядок поиска методов — MRO (method resolution order), который вычисляется алгоритмом C3-линеаризации. Его гарантии:

  • класс идёт раньше своих родителей
  • родители — в том порядке, в котором перечислены в class D(B, C)
  • порядок согласован для всех предков (иначе TypeError: Cannot create a consistent MRO)

super() — это не «родитель», а «следующий класс в MRO объекта». Поэтому в ромбе каждый класс вызывается ровно один раз, если все методы зовут super() (кооперативное наследование).

Миксины, ABC и Protocol:

  • миксин — маленький класс с одной способностью (JsonMixin, LoggingMixin), его подмешивают через множественное наследование. Своего __init__ обычно нет
  • ABC (abc.ABC, @abstractmethod) — номинальный интерфейс: класс с нереализованными абстрактными методами нельзя создать, наследование явное
  • **typing.Protocol** — структурный интерфейс («утиная типизация» для mypy): подходит любой класс с нужными методами, наследоваться не нужно. @runtime_checkable разрешает isinstance (он проверяет только наличие методов)

Что выбрать: Protocol — для зависимостей, которые описывает потребитель (репозиторий, клиент), особенно для чужих классов. ABC — если нужна общая реализация в базовом классе и защита от создания неполных реализаций.

Вопрос с собесаЧто такое MRO и как работает super() при множественном наследовании?

Эталонный ответ

MRO — порядок, в котором Python ищет атрибуты в иерархии классов (Cls.__mro__). Он строится алгоритмом C3-линеаризации: класс раньше родителей, родители — в порядке перечисления, порядок согласован для всех предков; если согласовать нельзя — TypeError при создании класса. super() возвращает прокси к следующему классу в MRO объекта, а не к родителю текущего класса. Поэтому в ромбе D(B, C), где B и C наследуют A, цепочка super() пройдёт D → B → C → A, и A вызовется один раз. Для этого все классы должны вызывать super() и принимать **kwargs, передавая их дальше (кооперативное наследование). Практический совет: множественное наследование — для миксинов без состояния, а в остальных случаях лучше композиция.

5.1 Память, сборка мусора и GIL

Как CPython управляет памятью:

  1. Подсчёт ссылок. У каждого объекта счётчик ob_refcnt. Новая ссылка (присваивание, элемент списка, аргумент) увеличивает его, пропажа ссылки уменьшает. Дошёл до нуля — объект удаляется сразу и детерминированно
  2. **Циклический сборщик (gc)** нужен для циклов: a.b = b; b.a = a. Счётчики никогда не станут нулём, поэтому периодически запускается сборщик, который ищет недостижимые группы объектов. В 3.12 и раньше — три поколения; в 3.14 — инкрементальный сборщик с двумя поколениями: молодые объекты проверяются часто, старые — реже
  3. **Аллокатор pymalloc** — для маленьких объектов (≤ 512 байт): пулы и арены, чтобы не ходить в системный malloc за каждым int
  • sys.getrefcount(x) — счётчик (на 1 больше: временная ссылка из аргумента)
  • бессмертные объекты (3.12, PEP 683): None, True, малые int и другие синглтоны не меняют свой счётчик. Это убирает запись в память при каждом использовании, что важно для многоядерности. getrefcount(None) возвращает огромное фиксированное число
  • слабая ссылка (weakref.ref, WeakValueDictionary) не увеличивает счётчик: кэш не держит объект живым

GIL — Global Interpreter Lock:

GIL — мьютекс в CPython: в каждый момент только один поток выполняет байткод Python в одном интерпретаторе.

  • Зачем он нужен. Защищает счётчики ссылок и внутренние структуры без тысячи мелких блокировок, а однопоточный код и C-расширения остаются простыми и быстрыми
  • Когда отпускается. На блокирующем вводе-выводе (socket.recv, file.read, time.sleep), в C-коде, который сам его отпускает (NumPy, hashlib, zlib), и принудительно каждые ~5 мс (sys.getswitchinterval()), чтобы потоки чередовались
  • Что из этого следует: для I/O-bound задач потоки работают хорошо — пока один ждёт сеть, другой выполняется. Для CPU-bound на чистом Python потоки не ускоряют, а иногда замедляют: нужны процессы (multiprocessing, ProcessPoolExecutor) или C-расширения
  • GIL не делает твой код потокобезопасным. Переключение может случиться между любыми байткодами: counter += 1 — это чтение, сложение и запись, и гонка возможна

Что изменилось в 3.13–3.15

  • 3.13 — экспериментальная free-threaded сборка без GIL (PEP 703, python3.13t)
  • 3.14 — free-threaded сборка официально поддерживается (PEP 779), но по умолчанию GIL всё ещё есть. Однопоточный код в ней немного медленнее, C-расширения должны явно объявить совместимость. В стандартной библиотеке появились субинтерпретаторы (PEP 734, concurrent.interpreters и InterpreterPoolExecutor): у каждого свой GIL, параллельность — внутри одного процесса
  • 3.15 — стабильный ABI для free-threaded сборок

На собесе хороший ответ: «GIL есть в стандартной сборке; с 3.13 есть сборка без него, с 3.14 она поддерживается официально, но экосистема переходит постепенно».

Эталонный ответ

GIL — глобальная блокировка интерпретатора CPython: в одном интерпретаторе байткод Python выполняет только один поток одновременно. GIL не гарантирует потокобезопасности: составные операции (+=, проверка и вставка) требуют Lock. В 3.13 появилась экспериментальная free-threaded сборка без GIL (PEP 703), в 3.14 она официально поддерживается (PEP 779), но не по умолчанию; плюс субинтерпретаторы со своим GIL. Asyncio от GIL почти не зависит: он однопоточный и даёт конкурентность на ожидании I/O.

  • deadlock (взаимная блокировка) — поток 1 держит A и ждёт B, поток 2 держит B и ждёт A. Лечится единым порядком захвата блокировок, таймаутами (lock.acquire(timeout=…)), меньшим числом блокировок

Эталонный ответ

Процесс — экземпляр программы с собственным адресным пространством, ресурсами ОС и, в Python, собственным интерпретатором и GIL. Вопрос с собесаЧто такое race condition и deadlock? Как их избегать?

Эталонный ответ

Race condition — ошибка, при которой результат зависит от порядка выполнения конкурентных операций над общим состоянием: неатомарный x += 1, check-then-act (if not exists: create), чтение частично обновлённых данных. Избегать: не разделять изменяемое состояние (передавать сообщения через очереди), делать неизменяемые данные, защищать критические секции блокировкой, использовать атомарные операции хранилища (INSERT … ON CONFLICT, UPDATE … SET x = x + 1, SETNX в Redis). Deadlock — несколько потоков или транзакций ждут ресурсы, захваченные друг другом, и не продвигаются. Условия: взаимное исключение, удержание с ожиданием, отсутствие принудительного освобождения и циклическое ожидание. Избегать: единый порядок захвата блокировок, захват всего сразу, таймауты с повтором, минимальная длительность удержания, меньше вложенных блокировок. В БД — короткие транзакции, одинаковый порядок обновления строк, ретрай при ошибке deadlock.

5.3 asyncio: event loop, задачи, отмена

Как это работает:

asyncio — кооперативная многозадачность в одном потоке. Есть цикл событий (event loop): он держит очередь готовых к выполнению задач и следит за сокетами и таймерами (через epoll/kqueue).

  • async def f() — корутинная функция; вызов f() ничего не выполняет, а создаёт объект корутины
  • await x — «выполни x; если ему надо ждать I/O, отдай управление циклу, а когда данные придут — продолжи меня». Переключение происходит **только в точках await**
  • Task — корутина, поставленная в цикл: asyncio.create_task(coro). Она начнёт выполняться, когда текущая задача отдаст управление
  • asyncio.run(main()) — создать цикл, выполнить main, закрыть цикл

Отсюда главные правила: **блокирующий вызов (time.sleep, requests.get, тяжёлый расчёт) останавливает весь цикл** — все остальные задачи ждут. И гонки в asyncio тоже бывают, но только «между await»: между двумя await код атомарен относительно других задач.

Вопрос с собесаКак работает asyncio? Чем асинхронность отличается от многопоточности?

Эталонный ответ

asyncio — однопоточная кооперативная многозадачность. Цикл событий держит очередь готовых задач и через системные механизмы (epoll, kqueue) следит за сокетами и таймерами. Корутина выполняется до await на операции, которая должна ждать; тогда она отдаёт управление, цикл запускает другую готовую задачу, а когда данные придут, возобновит первую. Переключение только явное, в точках await. Многопоточность — вытесняющая: ОС (и GIL в CPython) переключает потоки в любой момент, поэтому любые общие данные требуют блокировок. Отличия: asyncio масштабируется на десятки тысяч соединений (корутина — несколько килобайт, поток — мегабайты стека и переключения ядра), гонок меньше (код между await атомарен), но нужна вся экосистема асинхронной (асинхронные драйверы БД, HTTP-клиенты), а любой блокирующий вызов или тяжёлый расчёт замораживает весь цикл. Потоки работают с любыми синхронными библиотеками, но дороже и опаснее с общим состоянием. Оба способа не дают параллелизма для CPU в CPython: для него — процессы.

Вопрос с собесаЧем asyncio.gather отличается от TaskGroup? Что происходит, если одна из задач падает?

Эталонный ответ

gather(*aws) запускает корутины конкурентно и возвращает результаты в порядке аргументов. Если одна падает, gather сразу пробрасывает её исключение, но остальные задачи не отменяются и продолжают работать в фоне — их ошибки могут потеряться. Задачи не «утекают» за пределы блока. Поэтому для новых проектов предпочтительнее TaskGroup, а gather(return_exceptions=True) — когда нужно собрать частичные результаты, несмотря на ошибки.

Где патчить

mock.patch подменяет имя там, где его ищут, а не там, где оно определено. Если app/service.py делает from app.clients import get_rate, то патчить нужно app.service.get_rate. Патч app.clients.get_rate не подействует: в service уже лежит своя ссылка на оригинал. Ещё лучше — не патчить, а внедрять зависимость (урок 4.3) и передавать фейк.

Хороший тест:

  • проверяет поведение, а не реализацию: после рефакторинга без смены поведения тест не должен падать
  • один сценарий — один тест с говорящим именем: test_promo_minus500_not_applied_below_threshold
  • граничные значения: если в коде >=, проверь ровно границу и на единицу меньше — именно там живут ошибки > против >=
  • детерминированность: время, случайность, сеть — через параметры или фейки
  • покрытие (coverage) показывает, какие строки выполнились, но не то, что их проверили. Строку return total - 500 if total >= 3000 else total покроет любой тест, а ошибку > вместо >= поймает только тест с суммой ровно 3000. Это измеряет мутационное тестирование (mutmut, cosmic-ray): в код вносятся маленькие ошибки, и смотрят, упадут ли тесты. Так устроена домашка этого урока

ВыбериВ коде return 0 if total >= 5000 else 299. Какой набор тестов ловит ошибку, если кто-то заменит >= на >?

Почему

Значения далеко от границы проходят одинаково для >= и >. Только тест ровно на границе (5000) различает их, а 4999 подтверждает, что граница не сдвинута в другую сторону. Это «анализ граничных значений» — базовая техника тест-дизайна, о которой спрашивают на собесах.

Пирамида: много быстрых юнит-тестов на бизнес-логику, меньше интеграционных (настоящая БД в контейнере, HTTP-слой через TestClient, транзакция с откатом на каждый тест), немного end-to-end.
