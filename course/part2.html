7.1 Массивы, слайсы и строки изнутри

Зачем знать, как это устроено:

В первой части ты пользовался срезами как списками из Python. На собеседовании спрашивают другое: почему код ведёт себя так, а не иначе. Вопросы «как устроен слайс», «как растёт capacity» и «что будет, если передать слайс в функцию» входят в топ-10 вопросов на Go-собесах. Ещё важнее, что на этих местах ошибаются в рабочем коде.

Массив — значение фиксированной длины:

var a [3]int          // [0 0 0]
b := [...]int{1, 2, 3} // длину посчитает компилятор
c := b                // КОПИЯ всех трёх элементов
c[0] = 100            // b не изменился
  • длина — часть типа: [3]int и [4]int — разные типы, их нельзя присвоить друг другу
  • массив передаётся и присваивается целиком, как число
  • массивы можно сравнивать через ==

В коде массивы встречаются редко. Зато под каждым слайсом лежит массив.

Слайс — окно в массив:

Слайс — это маленькая структура из трёх полей, её называют заголовком (slice header):

type slice struct {
    array unsafe.Pointer // указатель на первый элемент окна
    len   int            // сколько элементов видно
    cap   int            // сколько помещается до конца массива
}

Копируя слайс, ты копируешь эти три поля, а массив под ними остаётся общим. Поэтому две переменные-слайса могут менять одни и те же данные.

Что выведет?Массив или слайс?

package main

import "fmt"

func main() {
	a := [3]int{1, 2, 3}
	b := a
	b[0] = 100

	s := []int{1, 2, 3}
	t := s
	t[0] = 100

	fmt.Println(a[0], s[0])
}
Вывод
1 100

b := a копирует массив целиком, поэтому a не меняется. t := s копирует только заголовок: t и s смотрят в один массив, и запись через t видна через s.

7.1 Массивы, слайсы и строки изнутри

Срез среза: len и cap

s := []int{0, 1, 2, 3, 4, 5}   // len 6, cap 6
t := s[2:4]                    // [2 3], len 2, cap 4 — до конца массива
u := s[2:4:4]                  // [2 3], len 2, cap 2 — полное выражение s[low:high:max]

cap нового среза считается от его начала до конца исходного массива. Третье число в s[low:high:max] ограничивает capacity. Тогда append к такому срезу не сможет залезть в чужие элементы.

append: в тот же массив или в новый

  • если len < cap, элемент пишется в тот же массив и становится виден всем, кто на этот массив смотрит
  • если места нет, Go выделяет новый массив, копирует туда элементы и возвращает слайс на него. Старые слайсы продолжают смотреть в старый массив

Поэтому результат append всегда присваивают: s = append(s, x).

Что выведет?Что станет с исходным слайсом?· частый вопрос на собесе

package main

import "fmt"

func main() {
	s := []int{0, 1, 2, 3, 4, 5}
	t := s[2:4]
	fmt.Println(t, len(t), cap(t))

	t = append(t, 99)
	fmt.Println(s)
}
Вывод
[2 3] 2 4
[0 1 2 3 99 5]

У t capacity 4 (от индекса 2 до конца массива), поэтому append не выделяет новый массив, а пишет 99 на место s[4]. Это частая причина багов: функция «только добавила элемент к своему кусочку», а данные испортились у вызывающего. Защита — s[2:4:4] или копия.

Как растёт capacity:

Когда место кончается, append выделяет массив с запасом, чтобы следующие добавления были дешёвыми:

  • пока слайс маленький (до 256 элементов), capacity растёт вдвое
  • дальше рост плавно замедляется примерно до ×1.25, чтобы не тратить лишнюю память
  • итог округляется вверх до класса размера аллокатора, поэтому точные числа бывают «странными»: 1, 2, 4, 8 … 512, 848, 1280

В среднем добавление элемента стоит O(1) (амортизированно). Если размер известен заранее, выделяй сразу: make([]T, 0, n). Тогда перевыделений не будет совсем.

Что выведет?Слайс передали в функцию:· частый вопрос на собесе

package main

import "fmt"

func add(s []int) {
	s[0] = 100
	s = append(s, 4)
	s[1] = 200
}

func main() {
	s := []int{1, 2, 3}
	add(s)
	fmt.Println(s)
}
Вывод
[100 2 3]

Функция получила копию заголовка. s[0] = 100 пишет в общий массив, и это видно снаружи. У слайса len 3 и cap 3, поэтому append создаёт новый массив, и локальная s теперь смотрит в него. s[1] = 200 меняет уже новый массив, вызывающий этого не видит. А сам элемент 4 снаружи не виден никогда: у внешнего s len остался 3.

Что выведет?Два append от одного слайса:

package main

import "fmt"

func main() {
	a := make([]int, 3, 10)
	b := append(a, 1)
	c := append(a, 2)
	fmt.Println(b[3], c[3])
}
Вывод
2 2

Места в массиве хватает (cap 10), поэтому оба append пишут в один и тот же элемент общего массива — с индексом 3. Второй перезаписывает первый, и b с c видят одно значение. Отсюда правило: не делай несколько append от одного слайса, если результаты должны жить независимо.

7.1 Массивы, слайсы и строки изнутри

nil-слайс и пустой слайс:

var a []int     // nil: заголовок {nil, 0, 0}
b := []int{}    // не nil: указатель на пустой массив, len 0
  • оба можно читать, обходить через range и передавать в append: append(nil, 1) работает
  • len, cap и range у nil-слайса ведут себя как у пустого
  • разница видна в JSON: nil кодируется как null, пустой как []. Для API это важно, фронтенд часто ждёт []

Что выведет?nil или не nil:

package main

import "fmt"

func main() {
	var a []int
	b := []int{}
	fmt.Println(a == nil, b == nil, len(a), len(b))

	a = append(a, 1)
	fmt.Println(a)
}
Вывод
true false 0 0
[1]

var a []int — нулевое значение слайса, то есть nil. []int{} — пустой, но не nil. append к nil-слайсу работает: он просто выделяет массив.

copy и пакет slices:

dst := make([]int, len(src))
n := copy(dst, src)              // копирует min(len(dst), len(src)) элементов

slices.Contains(s, 3)            // есть ли элемент
slices.Index(s, 3)               // индекс или -1
slices.Sort(s)                   // сортировка на месте
c := slices.Clone(s)             // независимая копия
slices.Equal(a, b)               // сравнение — через == слайсы сравнивать нельзя

7.1 Массивы, слайсы и строки изнутри

Строки изнутри:

Строка — это неизменяемая последовательность байтов. Её заголовок похож на слайс, но без cap: указатель и длина.

  • len(s) — количество байтов. Кириллица в UTF-8 занимает 2 байта, эмодзи — 4
  • s[i] — байт (byte, то есть uint8), а не символ
  • for i, r := range s идёт по рунам: r — символ (rune, то есть int32), i — номер байта, с которого он начинается
  • utf8.RuneCountInString(s) — количество символов
  • []byte(s) и string(b) копируют данные, потому что строка неизменяема

Что выведет?Байты, руны, индексы:· частый вопрос на собесе

package main

import (
	"fmt"
	"unicode/utf8"
)

func main() {
	s := "Go, привет"
	fmt.Println(len(s), utf8.RuneCountInString(s))

	for i, r := range "ёж" {
		fmt.Println(i, string(r))
	}

	fmt.Println(s[4])
}
Вывод
16 10
0 ё
2 ж
208

«Go, » — 4 байта, «привет» — 6 букв по 2 байта, итого 16 байтов и 10 символов. range отдаёт индекс байта, где начинается руна, поэтому ж на позиции 2. s[4] — первый байт буквы «п» в UTF-8 (0xD0 = 208), а не буква.

Склейка строк:

Каждая s += x создаёт новую строку и копирует в неё всё старое содержимое. В цикле получается O(n²). Правильно так:

var b strings.Builder
b.Grow(64)                 // если примерный размер известен — одна аллокация
for _, w := range words {
    b.WriteString(w)
}
result := b.String()       // без лишнего копирования

Для пары строк a + b и fmt.Sprintf нормальны. Builder нужен в циклах.

Домашка 7.1

Как решать

Как решать. Переведи строку в []rune. Если символов не больше n, верни строку как есть. Иначе верни string(r[:n]) + "…".

Подвох. Нельзя резать s[:n]: это байты, и посреди буквы получится битый UTF-8.

Как решать

Как решать. Создай новый слайс make([]int, 0, len(s)-1) и добавь в него всё до i и всё после: append(res, s[:i]...), затем append(res, s[i+1:]...).

Подвох. Привычное append(s[:i], s[i+1:]...) портит исходный слайс: сдвигает элементы в общем массиве. Тест это проверяет.

Как решать

Как решать. Цикл с шагом size, правая граница — min(i+size, len(s)). Кусок бери полным выражением s[i:j:j].

Подвох. С s[i:j] у куска есть запас capacity, и append к первому куску перезапишет начало второго. Тест делает именно такой append.

Как решать

Как решать. Посчитай итоговую длину заранее (сумма len слов плюс разделители), вызови b.Grow(n) и пиши через WriteString.

Подвох. Тест меряет аллокации через testing.AllocsPerRun, допускается не больше одной. Без Grow Builder будет перевыделять буфер.

Как решать

Как решать. Два индекса: w — куда писать, i — что читаешь. Пиши s[w] = s[i] только если элемент отличается от последнего записанного. Верни s[:w].

Подвох. Новый слайс создавать нельзя: тест требует 0 аллокаций. В этом и смысл — переиспользовать массив.

Вопрос с собесаЧем слайс отличается от массива?

Эталонный ответ

Массив — значение фиксированной длины. Длина входит в тип ([3]int ≠ [4]int), при присваивании и передаче в функцию массив копируется целиком, массивы можно сравнивать через ==.

Слайс — заголовок из трёх полей: указатель на элемент массива, длина и вместимость. Он ссылается на массив и может расти через append, при нехватке места выделяется новый массив. Копирование слайса копирует только заголовок, данные остаются общими. Нулевое значение — nil. Сравнивать слайсы можно только с nil.

Вопрос с собесаКак работает append и как растёт capacity?

Эталонный ответ

Если len < cap, append записывает элемент в существующий массив и возвращает слайс с увеличенной длиной. Если места нет, выделяется новый массив большего размера, старые элементы копируются, и возвращается слайс на новый массив. Поэтому результат append нужно присваивать.

Рост: для небольших слайсов (до 256 элементов) capacity удваивается, дальше коэффициент плавно уменьшается примерно до 1.25. Итоговый размер округляется до класса размера аллокатора. Амортизированная сложность добавления — O(1). Если размер известен, лучше сразу make([]T, 0, n).

Отметь, что было в твоём ответе

Вопрос с собесаЧто произойдёт, если передать слайс в функцию и изменить его внутри?

Эталонный ответ

В функцию передаётся копия заголовка, а массив общий. Поэтому изменение существующих элементов (s[i] = x) видно у вызывающего. А append внутри функции меняет только локальный заголовок: вызывающий не увидит новую длину, а если произошло перевыделение, не увидит и дальнейших изменений. Чтобы изменения длины дошли, функция возвращает новый слайс (s = f(s)) или принимает указатель на слайс.

7.2 Map, интерфейсы и дженерики изнутри

Map — хеш-таблица:

map[K]V хранит пары в хеш-таблице. Чтобы найти ключ, Go считает от него хеш и по хешу сразу определяет, в какой ячейке искать. Поэтому поиск, вставка и удаление в среднем работают за O(1).

Классическое устройство (до Go 1.24) до сих пор спрашивают на собесах:

  • таблица — массив бакетов, в каждом до 8 пар ключ-значение
  • младшие биты хеша выбирают бакет, старшие (tophash) хранятся в бакете для быстрой проверки
  • если бакет полон, к нему цепляется overflow-бакет. Так решаются коллизии
  • когда в среднем больше 6.5 элементов на бакет, таблица растёт вдвое. Элементы переезжают постепенно (эвакуация), понемногу при каждой записи, чтобы не было длинной паузы

С Go 1.24 — Swiss Tables: элементы лежат в группах по 8 слотов с управляющим словом, по которому можно проверить сразу 8 кандидатов. Большая map состоит из нескольких независимых таблиц, и растёт каждая по отдельности. Снаружи поведение то же, только быстрее и экономнее по памяти.

Правила, которые из этого следуют:

  • ключ должен быть сравнимым (==): числа, строки, указатели, каналы, массивы и структуры из сравнимых полей. Слайсы, map и функции ключом быть не могут
  • порядок обхода случайный, и Go специально перемешивает его на каждом range. Нужен порядок — отсортируй ключи
  • nil-map можно читать (вернётся нулевое значение), но запись в неё вызывает panic
  • взять адрес значения нельзя: &m[k] не скомпилируется, ведь при росте таблицы значения переезжают. По той же причине нельзя m[k].Price = 10 для структур — храни указатели или перезаписывай целиком
  • map не потокобезопасна: одновременная запись из двух горутин даёт fatal error: concurrent map writes. Это не panic, recover её не поймает. Защищай мьютексом
  • map передаётся «по ссылке»: внутри лежит указатель на таблицу, поэтому добавленный в функции ключ виден снаружи
  • множество (set) делают через map[T]struct{}: пустая структура занимает 0 байт

Что выведет?Map в функции:

package main

import "fmt"

func add(m map[string]int) {
	m["b"] = 2
}

func reset(m map[string]int) {
	m = map[string]int{}
	m["c"] = 3
}

func main() {
	m := map[string]int{"a": 1}
	add(m)
	reset(m)
	fmt.Println(len(m), m["b"], m["c"])
}
Вывод
2 2 0

Переменная map — это указатель на таблицу, и копия указателя ведёт в ту же таблицу. Поэтому add добавляет ключ в общую map. reset перезаписывает свою локальную переменную новой map, а исходная остаётся без изменений. m["c"] — отсутствующий ключ, вернётся 0.

Интерфейсы изнутри:

Значение интерфейсного типа — пара из двух слов:

type iface struct {
    tab  *itab          // какой конкретный тип внутри + таблица его методов
    data unsafe.Pointer // указатель на само значение
}

У пустого интерфейса any вместо itab просто указатель на тип. При вызове метода через интерфейс Go берёт адрес функции из таблицы. Это динамическая диспетчеризация: такой вызов чуть дороже прямого, и компилятор не может его встроить.

Интерфейс равен nil, только если оба слова — nil. Если положить в интерфейс nil-указатель, тип уже известен, и интерфейс не nil. Это самая известная ловушка Go.

Что выведет?Ловушка с nil:· частый вопрос на собесе

package main

type MyErr struct{}

func (*MyErr) Error() string { return "boom" }

func check(fail bool) error {
	var e *MyErr
	if fail {
		e = &MyErr{}
	}
	return e
}

func main() {
	err := check(false)
	fmt.Println(err == nil)
	fmt.Printf("%T\n", err)
}
Вывод

check возвращает интерфейс error, внутри которого лежит тип *MyErr и значение nil. Тип не пуст, поэтому err != nil, и вызывающий решит, что произошла ошибка. Правило: если ошибки нет, пиши явно return nil, а не переменную конкретного типа.

Как правильно работать с интерфейсами:

  • объявляй интерфейс там, где он нужен (у потребителя), а не рядом с реализацией. Хендлеру нужен AdStore с двумя методами — вот он и объявляет AdStore
  • маленькие интерфейсы: io.Reader — один метод. Чем меньше интерфейс, тем больше типов его реализуют
  • принимай интерфейсы, возвращай структуры: func NewService(s AdStore) *Service
  • проверка на этапе компиляции, что тип реализует интерфейс: var _ AdStore = (*PostgresStore)(nil)
  • интерфейсы встраиваются: type ReadWriter interface { Reader; Writer }

Почему

В Go реализация не объявляет, что «implements», поэтому интерфейс может жить у потребителя. Так api зависит только от нужных ему методов, в тестах легко подставить фейк, а postgres не знает о своих потребителях. Общий пакет interfaces — антипаттерн: он связывает всех со всеми.

ООП в Go — коротко для собеса:

  • инкапсуляция — через пакеты: заглавная буква экспортирует, строчная скрывает
  • полиморфизм — через интерфейсы с неявной реализацией (утиная типизация, проверяемая компилятором)
  • наследования нет — вместо него встраивание (композиция): методы встроенного типа поднимаются наверх, но тип-обёртка не становится встроенным типом
  • методы можно объявить у любого своего типа, не только у структуры: type Rubles int

Дженерики:

С Go 1.18 функции и типы могут иметь параметры типа:

func Max[T cmp.Ordered](a, b T) T {   // T — любой упорядочиваемый тип
    if a > b {
        return a
    }
    return b
}

type Set[T comparable] map[T]struct{}  // обобщённый тип
  • ограничение (constraint) — интерфейс, описывающий допустимые типы: any, comparable, cmp.Ordered или свой: interface{ ~int | ~float64 }
  • ~int значит «int и любые типы на его основе», например type Rubles int
  • тип обычно выводится сам: Max(3, 7), а не Max[int](3, 7)
  • у методов не может быть своих параметров типа, только у типа целиком

Когда нужны: контейнеры и алгоритмы, одинаковые для разных типов (slices, maps, кэш, множество). Когда не нужны: если разным типам нужно разное поведение, это работа интерфейсов.

Что выведет?Какой тип выведется?

package main

import (
	"cmp"
	"fmt"
)

func Max[T cmp.Ordered](a, b T) T {
	if a > b {
		return a
	}
	return b
}

func main() {
	fmt.Println(Max(3, 7), Max("go", "python"))
	fmt.Println(Max(3, 2.5))
}
Вывод
7 python
3

Строки сравниваются лексикографически: «p» > «g». Во втором вызове оба аргумента — нетипизированные константы, поэтому Go выбирает общий тип float64, и Max(3.0, 2.5) возвращает 3. Будь там переменная x := 3 типа int, код бы не скомпилировался.

Паттерн functional options:

Как сделать конструктор с кучей необязательных параметров, если нет значений по умолчанию и именованных аргументов? Через функции-опции:

type Client struct {
    timeout time.Duration
    retries int
}

type Option func(*Client)

func WithTimeout(d time.Duration) Option {
    return func(c *Client) { c.timeout = d }
}

func NewClient(opts ...Option) *Client {
    c := &Client{timeout: 5 * time.Second, retries: 3} // значения по умолчанию
    for _, opt := range opts {
        opt(c)
    }
    return c
}

c := NewClient(WithTimeout(time.Second))

Новую настройку можно добавить, не ломая уже написанные вызовы. Так устроены gRPC, zap и многие другие библиотеки.

Вопрос с собесаКак устроена map в Go?

Эталонный ответ

Map — хеш-таблица. От ключа считается хеш, младшие биты выбирают бакет, старшие (tophash) хранятся в бакете для быстрого сравнения. В бакете до 8 пар, при переполнении цепляется overflow-бакет — так обрабатываются коллизии. Когда средняя загрузка превышает 6.5 элемента на бакет, таблица растёт вдвое, а элементы переносятся постепенно при последующих операциях (эвакуация). С Go 1.24 используются Swiss Tables: группы по 8 слотов с управляющими байтами и несколько независимо растущих таблиц. Поиск в среднем O(1), в худшем случае при множестве коллизий — O(n). Порядок обхода случайный, map не потокобезопасна.

Вопрос с собесаКакие типы могут быть ключом map? Можно ли взять указатель на значение в map?

Эталонный ответ

Ключом может быть любой сравнимый тип: числа, строки, bool, указатели, каналы, интерфейсы, массивы и структуры, все поля которых сравнимы. Нельзя использовать слайсы, map и функции. Если ключ — интерфейс, а внутри лежит несравнимый тип (например, слайс), будет panic во время выполнения.

Вопрос с собесаПочему интерфейс может быть не равен nil, хотя внутри лежит nil-указатель?

Эталонный ответ

Значение интерфейса состоит из двух частей: информации о типе (itab или type) и указателя на данные. Интерфейс равен nil, только если обе части nil. 8.1 Ошибки как следует

Три вида ошибок в Go:

В первой части ты возвращал errors.New и проверял err != nil. В настоящем сервисе ошибки путешествуют через несколько слоёв: БД → хранилище → бизнес-логика → HTTP-хендлер. На каждом шаге нужно решать, что с ошибкой делать. Для этого их делят на три вида.

ВидПримерКак проверять
sentinel — заранее объявленное значениеio.EOF, sql.ErrNoRows, ErrNotFounderrors.Is(err, ErrNotFound)
типизированная — свой тип с полями*ValidationError{Field: "price"}errors.As(err, &target)

Обёртка: %w строит цепочку

var ErrNotFound = errors.New("not found")

func (s *Store) Get(id int) (Ad, error) {
    ad, ok := s.ads[id]
    if !ok {
        return Ad{}, fmt.Errorf("ad %d: %w", id, ErrNotFound) // добавили контекст
    }
    return ad, nil
}

%w кладёт исходную ошибку внутрь новой. Получается цепочка: handler: get ad 42: not found. errors.Is и errors.As проходят по всей цепочке через Unwrap(). С %v вместо %w текст тот же, но цепочка рвётся, и errors.Is уже ничего не найдёт.

Сравнивать текст ошибок нельзя никогда: err.Error() == "not found" сломается от первой правки сообщения.

Что выведет?%w против %v:· частый вопрос на собесе

package main

import (
	"errors"
	"fmt"
)

var ErrNotFound = errors.New("not found")

func find() error {
	return fmt.Errorf("find ad 42: %w", ErrNotFound)
}

func main() {
	err := fmt.Errorf("handler: %w", find())
	fmt.Println(err)
	fmt.Println(errors.Is(err, ErrNotFound), err == ErrNotFound)

	err2 := fmt.Errorf("handler: %v", find())
	fmt.Println(errors.Is(err2, ErrNotFound))
}
Вывод
handler: find ad 42: not found
true false
false

errors.Is разворачивает цепочку и находит ErrNotFound на дне. == сравнивает только внешнюю ошибку, поэтому false. В err2 использован %v: текст тот же, но исходная ошибка превратилась в строку, и цепочки больше нет.

errors.As — достать ошибку нужного типа:

type ValidationError struct {
    Field string
    Msg   string
}

func (e *ValidationError) Error() string { return e.Field + ": " + e.Msg }

var ve *ValidationError
if errors.As(err, &ve) {          // ищет в цепочке *ValidationError
    fmt.Println("плохое поле:", ve.Field)
}

Вторым аргументом передаётся указатель на переменную нужного типа. Если такая ошибка нашлась в цепочке, As положит её в переменную.

errors.Join — несколько ошибок сразу:

Валидация формы находит сразу три проблемы. Возвращать только первую неудобно для пользователя.

var errs []error

    errs = append(errs, &ValidationError{Field: "title", Msg: "обязательное поле"})

Где обрабатывать ошибку:

Ошибку обрабатывают один раз. Либо ты её обработал (залогировал, вернул пользователю статус, повторил запрос), либо вернул наверх с контекстом. «Залогировал и вернул» — антипаттерн: одна проблема попадает в лог пять раз, по разу на каждом слое.

// плохо
if err != nil {
    log.Printf("ошибка: %v", err)
    return err
}

// хорошо: нижние слои добавляют контекст...
if err != nil {
    return fmt.Errorf("load ad %d: %w", id, err)
}
// ...а решение принимает верхний слой — HTTP-хендлер

panic — только для багов:

  • error — ожидаемые ситуации: нет записи, неверный ввод, сеть отвалилась
  • panic — «так не может быть»: нарушен инвариант, программист ошибся, приложение не может стартовать без конфига (regexp.MustCompile, template.Must)
  • recover ставят на границах: middleware HTTP-сервера, обработчик задачи в воркере. Тогда один сломанный запрос не роняет весь сервис
  • log.Fatal и os.Exit — только в main: они не выполняют defer

При передаче наверх ошибку оборачивают с контекстом через fmt.Errorf("...: %w", err), и получается цепочка. errors.Is(err, target) проверяет, есть ли в цепочке конкретное значение (sentinel-ошибка вроде sql.ErrNoRows). errors.As(err, &target) ищет в цепочке ошибку определённого типа и записывает её в target, чтобы достать поля. Для нескольких ошибок есть errors.Join. Сравнивать текст ошибок нельзя.

Вопрос с собесаКак работает defer и в каком порядке выполняются отложенные вызовы? Когда уместен panic?

Эталонный ответ

defer откладывает вызов до выхода из функции: при обычном return, при panic, при любом пути. Отложенные вызовы выполняются в обратном порядке (LIFO). Аргументы вычисляются в момент объявления defer, а не выполнения. Отложенная функция может изменить именованные результаты, и на этом построен перехват паники через recover. recover работает только внутри отложенной функции.

Panic уместен для программных ошибок и невозможных состояний (нарушен инвариант, не удалось инициализировать обязательный ресурс при старте, Must-функции). Для ожидаемых ошибок — error. recover ставят на границах (HTTP-middleware, воркер), чтобы один сбой не ронял весь процесс.

Middleware — обёртка вокруг хендлера:

Логирование, восстановление после паники, проверка токена, метрики нужны каждому запросу. Копировать их в каждый хендлер — плохая идея. Middleware — функция, которая принимает хендлер и возвращает новый, с дополнительным поведением до и/или после:

func Logging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r)                                   // вызываем обёрнутый хендлер
        log.Printf("%s %s %v", r.Method, r.URL.Path, time.Since(start))
    })
}

handler := Logging(Recover(mux)) // запрос идёт: Logging → Recover → mux

Это паттерн «декоратор». Он работает, потому что http.Handler — интерфейс из одного метода.

Как узнать статус ответа в middleware:

http.ResponseWriter не умеет говорить, какой статус записали. Поэтому его оборачивают:

type statusRecorder struct {

    status int
}

func (r *statusRecorder) WriteHeader(code int) {
    r.status = code
    r.ResponseWriter.WriteHeader(code)
}

rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK} // 200 — если WriteHeader не вызовут

log.Println(rec.status)

Вопрос с собесаЧто такое graceful shutdown и как его сделать в Go?

Эталонный ответ

Graceful shutdown — корректное завершение: при получении SIGTERM/SIGINT сервис перестаёт принимать новые соединения, дожидается завершения текущих запросов (с ограничением по времени), закрывает ресурсы (БД, брокеры, сбрасывает буферы) и только потом выходит. Вопрос с собесаКак устроен JWT и чем он отличается от сессий? Как хранить пароли?

Пароли хранят только как хеш медленной функцией с солью (bcrypt, argon2id) и сравнивают специальной функцией. MD5 и SHA быстрые, поэтому для паролей не годятся.

SELECT по шагам:

SELECT u.city, COUNT(*) AS ads_count, AVG(a.price) AS avg_price
FROM ads a
JOIN users u ON u.id = a.user_id      -- 1. соединяем таблицы
WHERE a.status = 'active'             -- 2. фильтруем СТРОКИ
GROUP BY u.city                       -- 3. группируем
HAVING COUNT(*) >= 10                 -- 4. фильтруем ГРУППЫ
ORDER BY ads_count DESC               -- 5. сортируем
LIMIT 5;                              -- 6. отрезаем

Порядок выполнения отличается от порядка записи: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Поэтому в WHERE нельзя сослаться на COUNT(*): группировки ещё не было.

ВыбериЧем WHERE отличается от HAVING?· частый вопрос на собесе

Почему

WHERE price > 1000 отбрасывает строки до подсчёта. HAVING COUNT(*) > 5 отбрасывает группы, в которых меньше 6 строк. Если условие не про агрегат, ставь его в WHERE: тогда меньше строк попадёт в группировку.

JOIN:

  • JOIN (INNER) — только пары, у которых нашлось совпадение
  • LEFT JOIN — все строки левой таблицы. Если пары нет, справа NULL. Так ищут «пользователей без объявлений»: LEFT JOIN ads ... WHERE ads.id IS NULL
  • то же можно сделать через подзапрос: WHERE NOT EXISTS (SELECT 1 FROM ads WHERE ads.user_id = users.id)

Индексы:

Без индекса WHERE category = 'мебель' читает всю таблицу (sequential scan). Индекс — отдельная структура, обычно B-дерево: отсортированные значения с указателями на строки. Поиск по нему — O(log n).

CREATE INDEX ads_category_price_idx ON ads (category, price);
  • составной индекс работает по принципу «левого префикса»: (category, price) помогает для WHERE category = ? и для WHERE category = ? AND price < ?, но не для WHERE price < ? без категории. Это как телефонный справочник, отсортированный по фамилии, потом по имени
  • индекс помогает и ORDER BY по тем же колонкам: строки уже лежат отсортированными
  • индекс не бесплатный: замедляет INSERT и UPDATE, занимает место
  • индекс не поможет, если на колонку надета функция (WHERE lower(title) = ...; нужен индекс по выражению), при LIKE '%шкаф' с процентом в начале и когда условию соответствует большая часть таблицы
  • EXPLAIN ANALYZE запрос показывает план: используется ли индекс и где время

ВыбериЧастый запрос: SELECT * FROM ads WHERE category = $1 AND status = 'active' ORDER BY price LIMIT 20. Какой индекс подойдёт лучше всего?· частый вопрос на собесе

Почему

Равенства — в начале составного индекса, колонка сортировки — в конце. Тогда база находит нужный «кусок» индекса и читает первые 20 строк уже в порядке цены, без сортировки. Индекс, начинающийся с price, для фильтра по категории почти бесполезен.

Вопрос с собесаЧто такое индекс, как он устроен и когда не помогает?

N+1 — когда для списка из N сущностей делается 1 запрос за списком и ещё N запросов за связанными данными (по одному на элемент). Находят по логам SQL или APM-трейсам: много одинаковых запросов в одном HTTP-запросе.

type Context interface {

    Err() error                  // nil, пока не отменён; потом Canceled или DeadlineExceeded
    Deadline() (time.Time, bool)
    Value(key any) any
}

Fan-in: слить несколько каналов в один

Классика лайвкодинга: «есть N каналов, сделай один, из которого читаются все значения».

func Merge(ctx context.Context, ins ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    for _, in := range ins {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for v := range in {
                select {
                case out <- v:
                case <-ctx.Done():
                    return            // никто не читает — выходим, а не висим
                }
            }
        }()
    }
    go func() {
        wg.Wait()                     // все писатели закончили —
        close(out)                    // можно закрывать
    }()
    return out
}

Три важные детали: по горутине на вход, закрытие после wg.Wait() в отдельной горутине, отправка в select с ctx.Done().

Data race — одновременный доступ двух горутин к одной области памяти, где хотя бы один доступ — запись, без синхронизации. Это неопределённое поведение: значения теряются, структуры (например, map) повреждаются. Находится детектором -race в тестах и на стенде. Предотвращается мьютексами, атомиками, передачей владения через каналы. Race condition — логическая ошибка, когда результат зависит от порядка или времени выполнения операций. Например, check-then-act: проверили остаток, потом списали, а между этим кто-то успел списать. Она возможна и без data race, и детектор её не найдёт. Решается атомарностью операции на нужном уровне: одна критическая секция на проверку и изменение, условный UPDATE в БД, транзакции, блокировки.

Эталонный ответ

Каналы — для передачи данных и сигналов между горутинами (владение данными переходит вместе с ними). sync.Mutex — защита общего состояния короткой критической секцией. sync.RWMutex — когда чтений много, а записей мало: читатели не блокируют друг друга. sync.WaitGroup — дождаться группу горутин. sync.Once — однократная инициализация. sync/atomic — счётчики и флаги без блокировок, CAS. sync.Cond — ожидание условия, используется редко. sync.Map — для кэшей, где ключи записываются один раз и много читаются, или где горутины работают с разными ключами. sync.Pool — переиспользование временных объектов. Вопрос с собесаЧто такое Docker? Чем контейнер отличается от виртуальной машины и образ — от контейнера?

Эталонный ответ

Docker упаковывает приложение со всеми зависимостями в образ и запускает его в изолированном контейнере одинаково на любой машине. Образ — неизменяемый шаблон из слоёв файловой системы и метаданных (команда запуска, переменные). Контейнер — запущенный экземпляр образа с собственным записываемым слоем, процессами и сетью. В отличие от виртуальной машины, контейнер не эмулирует железо и не содержит своего ядра: процессы работают на ядре хоста, а изоляция обеспечивается namespaces (pid, net, mnt…) и ограничения ресурсов — cgroups. Поэтому контейнеры лёгкие и стартуют за доли секунды, но изоляция у них слабее, чем у ВМ. Для Go характерны multi-stage сборки и минимальные образы (distroless/scratch).

Принцип fail fast: неверная конфигурация должна обнаружиться при запуске, до того как сервис получит трафик. Значение по умолчанию для адреса базы на проде — путь к тихой катастрофе.
