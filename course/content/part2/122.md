# 12.2 Сервис, готовый к продакшену

## Структура проекта:
Общепринятая раскладка Go-сервиса:
```text
barakholka/
├── cmd/api/main.go          # точка входа: собрать зависимости, запустить, дождаться сигнала
├── internal/                # код, который нельзя импортировать из других модулей (правило компилятора)
│   ├── config/              # чтение конфигурации
│   ├── ad/                  # предметная область: модель, сервис, ошибки
│   ├── storage/postgres/    # реализация хранилища
│   └── httpapi/             # хендлеры, middleware, роутер
├── migrations/              # SQL-миграции
├── Dockerfile, compose.yaml, Makefile, .github/workflows/
└── go.mod
```
`main.go` должен быть коротким: прочитать конфиг, создать логгер, подключиться к БД, собрать сервисы, запустить HTTP-сервер, дождаться сигнала, корректно остановиться. Вся логика — в `internal`. Никаких глобальных переменных с БД: зависимости передаются через конструкторы.

## Конфигурация — из окружения (12-factor):
Одинаковый образ запускается локально, на стенде и на проде. Различается только окружение:
```go
type Config struct {
    Port            int
    DatabaseURL     string
    LogLevel        string
    ShutdownTimeout time.Duration
}
```
- значения по умолчанию для необязательного, явная ошибка для обязательного: сервис без `DATABASE_URL` должен **упасть при старте**, а не через час
- валидируй сразу и сообщай обо *всех* проблемах (`errors.Join`)
- секреты — тоже из окружения (а в Kubernetes — из Secret), никогда не в коде и не в репозитории

## Структурированные логи — log/slog:
Логи читает не человек глазами, а система сбора (Loki, ELK). Им нужен JSON с полями, а не строки:
```go
logger := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: slog.LevelInfo}))
logger.Info("ad created", "ad_id", 42, "user_id", 7)
// {"time":"…","level":"INFO","msg":"ad created","ad_id":42,"user_id":7}

reqLog := logger.With("request_id", rid)   // логгер с полями, общими для запроса
reqLog.Error("db query failed", "err", err)
```
- уровни: `Debug` — подробности для отладки, `Info` — значимые события, `Warn` — странно, но работаем, `Error` — операция провалилась
- сообщение — постоянная строка, детали — в полях. Так по логам можно искать и строить графики
- не логируй пароли, токены и персональные данные

::: quiz choice q122-1
Какая запись лога лучше?
- [ ] `log.Printf("ошибка при создании объявления %d пользователем %d: %v", adID, userID, err)`
- [x] `logger.Error("create ad failed", "ad_id", adID, "user_id", userID, "err", err)`
- [ ] `fmt.Println("ERROR!!!", err)`
- [ ] `logger.Info(fmt.Sprintf("create ad failed %v %v %v", adID, userID, err))`
--- why
Постоянное сообщение плюс поля позволяют найти все такие ошибки одним запросом и посчитать их по `user_id`. Из склеенной строки поля потом приходится вытаскивать регулярками. `Info` для ошибки — неправильный уровень.
:::

## Пробы здоровья:
```go
mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)          // liveness: процесс жив и отвечает
})
mux.HandleFunc("GET /readyz", func(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), time.Second)
    defer cancel()
    if err := db.PingContext(ctx); err != nil {
        http.Error(w, "db unavailable", http.StatusServiceUnavailable) // readiness: не готов
        return
    }
    w.WriteHeader(http.StatusOK)
})
```

## main.go целиком:
```go
func main() {
    if err := run(); err != nil {
        fmt.Fprintln(os.Stderr, err)
        os.Exit(1)
    }
}

func run() error {
    cfg, err := config.Load(os.Getenv)
    if err != nil {
        return fmt.Errorf("config: %w", err)
    }
    logger := newLogger(os.Stdout, cfg.LogLevel)

    ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
    defer stop()

    db, err := storage.Open(ctx, cfg.DatabaseURL)
    if err != nil {
        return fmt.Errorf("db: %w", err)
    }
    defer db.Close()

    api := httpapi.New(ad.NewService(db), logger)
    ln, err := net.Listen("tcp", fmt.Sprintf(":%d", cfg.Port))
    if err != nil {
        return err
    }
    logger.Info("listening", "port", cfg.Port)
    return serve(ctx, ln, api, cfg.ShutdownTimeout) // вернётся после graceful shutdown
}
```
Почему `run() error`, а не всё в `main`: `defer` выполнятся до `os.Exit`, ошибки возвращаются обычным способом, и функцию можно вызвать из теста.

## Makefile и линтеры:
```makefile
.PHONY: run test lint
run:
	go run ./cmd/api
test:
	go test -race -count=1 ./...
lint:
	golangci-lint run
```
`golangci-lint` объединяет десятки линтеров: `errcheck` (проигнорированные ошибки), `staticcheck`, `govet`, `bodyclose` (незакрытый `resp.Body`), `sqlclosecheck`. Его ставят в CI, и половина замечаний ревьюера исчезает до ревью.

## Микросервисы и монолит:
**Монолит** — одно приложение и один деплой. **Микросервисы** — набор небольших сервисов, каждый со своей ответственностью, своей базой и своим деплоем, общаются по сети (HTTP/gRPC, брокеры сообщений).

| | Плюсы | Минусы |
|---|---|---|
| Монолит | просто разрабатывать, отлаживать и деплоить; транзакции внутри одной БД; нет сетевых задержек | большая кодовая база, долгий деплой, масштабируется только целиком, одна ошибка роняет всё |
| Микросервисы | независимые деплой и масштабирование, команды не мешают друг другу, разные технологии, изоляция сбоев | сеть ненадёжна, распределённые транзакции, сложная отладка (нужна трассировка), инфраструктура (Kubernetes, CI на каждый сервис), консистентность данных между сервисами |

Честный ответ на собесе: стартовать стоит с модульного монолита и выделять сервисы, когда для этого есть причина (нагрузка, команды, разные требования к надёжности). Go популярен именно в микросервисах: быстрый старт, маленькие образы, хорошая сеть и конкурентность из коробки.

::: quiz open q122-2 собес
Что такое микросервисы? Какие у них преимущества и недостатки по сравнению с монолитом?
--- answer
Микросервисная архитектура — система из небольших независимо разворачиваемых сервисов, каждый отвечает за свою бизнес-возможность, владеет своими данными (своя БД) и общается с другими через API (REST/gRPC) или сообщения (Kafka/RabbitMQ). Преимущества: независимый деплой и масштабирование отдельных частей, изоляция отказов, автономия команд, свобода в выборе технологий, меньшая кодовая база каждого сервиса. Недостатки: сетевые вызовы медленнее и ненадёжны (нужны таймауты, ретраи, circuit breaker), нет общих транзакций (саги, outbox, eventual consistency), сложнее отладка и мониторинг (нужны распределённая трассировка, централизованные логи и метрики), дороже инфраструктура и DevOps, версионирование контрактов между сервисами. Монолит проще на старте, часто разумно начинать с модульного монолита.
--- points
- независимые сервисы со своими данными и деплоем
- общение через API или брокер
- плюсы: независимые деплой и масштабирование, изоляция сбоев, автономия команд
- минусы: сеть, распределённые транзакции, консистентность
- минусы: наблюдаемость, инфраструктура, контракты
- монолит проще на старте
:::

Сервис стартовал без переменной `DATABASE_URL`. Как правильно?
- [ ] подставить `localhost:5432` по умолчанию и работать
- [ ] запуститься, а при первом запросе вернуть 500
- [x] упасть при старте с понятной ошибкой: оркестратор и человек сразу увидят проблему
- [ ] записать предупреждение в лог и продолжить без базы
--- why
Принцип fail fast: неверная конфигурация должна обнаружиться при запуске, до того как сервис получит трафик. Значение по умолчанию для адреса базы на проде — путь к тихой катастрофе.
:::

::: hw 122
* `LoadConfig` — конфигурация из окружения со значениями по умолчанию {TestLoadConfig}
+ Функция получает `getenv` — так её легко тестировать без настоящего окружения. Для каждого поля: пустое значение → значение по умолчанию, иначе разбор (`strconv.Atoi`, `time.ParseDuration`) с проверкой. Ошибки копи в слайс и верни `errors.Join`.
! `DATABASE_URL` обязателен. Порт — от 1 до 65535. Уровень — только `debug|info|warn|error`. Тест передаёт сразу несколько ошибок и проверяет, что упомянуты все.
* `NewLogger` — JSON-логгер с уровнем {TestNewLogger}
+ `slog.New(slog.NewJSONHandler(w, &slog.HandlerOptions{Level: lvl}))`. Строку уровня переведи в `slog.Level` через `switch` или `lvl.UnmarshalText`.
* `Health` — /healthz и /readyz {TestHealth}
+ `/healthz` всегда 200. `/readyz`: создай контекст с таймаутом 1 секунда и вызови `check(ctx)`. При ошибке ответь 503 с JSON `{"status": "unavailable", "error": "..."}`, иначе 200 и `{"status": "ok"}`.
! Тест передаёт зависающую проверку и ждёт ответ 503 примерно через секунду, а не вечно.
* `Serve` — HTTP-сервер с graceful shutdown {TestServe}
+ `srv := &http.Server{Handler: h, ReadHeaderTimeout: 5 * time.Second}`. Запусти `srv.Serve(ln)` в горутине, результат — в канал с буфером 1. Дальше `select`: ошибка сервера — вернуть её; `ctx.Done()` — `srv.Shutdown` с контекстом на `timeout`, потом вернуть nil.
! `Serve` после `Shutdown` возвращает `http.ErrServerClosed` — это не ошибка. Тест отправляет медленный запрос, отменяет `ctx` посреди запроса и ждёт, что ответ всё-таки придёт.
* `AccessLog ★` — middleware со структурным логом запроса {TestAccessLog}
+ Объедини 9.2 и slog: `statusRecorder`, замер времени, затем `logger.Info("request", "method", ..., "path", ..., "status", ..., "duration_ms", ...)`. Статус 5xx логируй уровнем `Error`.
:::

- `main` короткий, вся логика в `internal/`, нет глобального состояния

## Вопросы с собеседования по уроку:
::: quiz open q122-4 собес
Как бы ты организовал структуру Go-сервиса и его запуск?
--- answer
`cmd/<имя>/main.go` — точка входа с минимумом логики: загрузка конфигурации из окружения с валидацией, создание логгера (slog JSON), подключение к БД и другим зависимостям, сборка слоёв через конструкторы (dependency injection вручную), запуск HTTP-сервера с таймаутами, ожидание сигнала через `signal.NotifyContext` и graceful shutdown с таймаутом, закрытие ресурсов в обратном порядке. Код — в `internal/`, разделённый по слоям или доменам: транспорт (хендлеры, middleware), бизнес-логика (сервисы, доменные ошибки), хранилище (репозитории). Интерфейсы объявляются у потребителя. Рядом — миграции, Dockerfile, compose, Makefile, CI, линтеры (golangci-lint). Глобальных переменных нет, `main` вызывает `run() error`.
--- points
- cmd/ для точки входа, internal/ для кода
- конфиг из env с валидацией, fail fast
- DI через конструкторы, без глобальных переменных
- слои: транспорт, сервис, хранилище
- graceful shutdown, логи, пробы
- миграции, Docker, CI, линтеры
:::
