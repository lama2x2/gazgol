# 10.2 Go и база данных: database/sql

## database/sql — общий интерфейс к любым базам:
Стандартный пакет `database/sql` описывает работу с SQL, а **драйвер** знает конкретную базу: `pgx` для PostgreSQL, `modernc.org/sqlite` для SQLite. Код почти не меняется, если сменить базу.
```go
import (
    "database/sql"
    _ "github.com/jackc/pgx/v5/stdlib"   // драйвер регистрирует себя в init(); _ — импорт ради побочного эффекта
)

db, err := sql.Open("pgx", "postgres://user:pass@localhost:5432/barakholka")
if err != nil { ... }
defer db.Close()
if err := db.PingContext(ctx); err != nil { ... } // Open ничего не подключает — проверяем Ping
```
`*sql.DB` — не соединение, а **пул соединений**. Он потокобезопасный: создаётся один раз при старте и передаётся всем, кому нужен.
```go
db.SetMaxOpenConns(25)                  // больше не откроет: защищает БД от перегруза
db.SetMaxIdleConns(25)                  // сколько держать открытыми в простое
db.SetConnMaxLifetime(30 * time.Minute) // переоткрывать старые (балансировщики их рвут)
```

## Три метода на все случаи:
```go
// одна строка
var title string
err := db.QueryRowContext(ctx, "SELECT title FROM ads WHERE id = $1", id).Scan(&title)
if errors.Is(err, sql.ErrNoRows) {          // строки нет — это не авария, а 404
    return Ad{}, ErrNotFound
}

// много строк
rows, err := db.QueryContext(ctx, "SELECT id, title FROM ads WHERE user_id = $1", userID)
if err != nil { return nil, err }
defer rows.Close()                          // ОБЯЗАТЕЛЬНО: иначе соединение не вернётся в пул
for rows.Next() {
    var ad Ad
    if err := rows.Scan(&ad.ID, &ad.Title); err != nil { return nil, err }
    ads = append(ads, ad)
}
if err := rows.Err(); err != nil { return nil, err } // ошибка могла случиться посреди чтения

// изменение
res, err := db.ExecContext(ctx, "UPDATE ads SET status = 'sold' WHERE id = $1", id)
n, _ := res.RowsAffected()                  // сколько строк задело — 0 значит «не нашли»
```
- плейсхолдеры: `$1, $2` в PostgreSQL, `?` в SQLite и MySQL
- всегда `...Context`: если клиент ушёл или истёк таймаут, запрос к БД отменится

::: quiz bug q102-1 собес
Сервис работает час, потом все запросы к БД начинают висеть. В логах: соединения кончились. Где утечка?
```go
func (s *Store) Titles(ctx context.Context) ([]string, error) {
    rows, err := s.db.QueryContext(ctx, "SELECT title FROM ads")
    if err != nil {
        return nil, err
    }
    var res []string
    for rows.Next() {
        var t string
        if err := rows.Scan(&t); err != nil {
            return nil, err
        }
        res = append(res, t)
    }
    return res, nil
}
```
- [ ] `QueryContext` нужно заменить на `Query`
- [x] нет `defer rows.Close()`: при выходе по ошибке Scan соединение не возвращается в пул
- [ ] нужно вызывать `s.db.Close()` в конце функции
- [ ] слайс `res` держит соединение
--- why
Если цикл дочитал всё до конца, `rows` закрывается сам. Но при раннем `return` (ошибка Scan, `break`) соединение остаётся занятым навсегда. Пул исчерпывается, и новые запросы ждут. Правило: `defer rows.Close()` сразу после проверки ошибки `QueryContext`. И не забывай `rows.Err()`.
:::

## Транзакции в Go:
```go
func (s *Store) Buy(ctx context.Context, adID, buyerID int64) (err error) {
    tx, err := s.db.BeginTx(ctx, nil)       // можно задать &sql.TxOptions{Isolation: sql.LevelSerializable}
    if err != nil {
        return err
    }
    defer tx.Rollback()                     // после Commit ничего не делает — безопасно всегда

    var price int64
    err = tx.QueryRowContext(ctx,           // ВСЕ запросы — через tx, а не s.db!
        "SELECT price FROM ads WHERE id = ? AND status = 'active'", adID).Scan(&price)
    if errors.Is(err, sql.ErrNoRows) {
        return ErrAlreadySold
    }
    ...
    return tx.Commit()
}
```
- `defer tx.Rollback()` — главный приём: при любом раннем `return` транзакция откатится
- внутри транзакции все запросы идут через `tx`. Запрос через `db` пойдёт по *другому* соединению и транзакцию не увидит. При маленьком пуле он ещё и зависнет, ожидая свободное соединение
- держи транзакции короткими: никаких HTTP-запросов наружу посреди транзакции

## Проверка в UPDATE вместо гонки:
Две покупки одновременно: обе прочитали `status = 'active'`, обе продали. Надёжнее совместить проверку и изменение в одном запросе:
```sql
UPDATE ads SET status = 'sold' WHERE id = $1 AND status = 'active'
```
и проверить `RowsAffected() == 1`. Если 0, кто-то успел раньше. В PostgreSQL можно ещё заблокировать строку: `SELECT ... FOR UPDATE`.

## Проблема N+1:
Показать 20 объявлений с именами продавцов:
```go
ads := store.ListAds(ctx, 20)              // 1 запрос
for i := range ads {
    ads[i].Seller = store.GetUser(ctx, ads[i].UserID) // + 20 запросов
}
```
21 запрос вместо одного. На 20 объявлениях не заметно, на 1000 — секунды. Лечится `JOIN` или вторым запросом `WHERE id = ANY($1)` с последующей склейкой в Go. ORM ловят в эту ловушку особенно часто: в SQLAlchemy ты, вероятно, видел `selectinload` и `joinedload` — это как раз про неё.

## Чем ходить в базу в реальных проектах:
| Инструмент | Что это | Когда |
|---|---|---|
| `database/sql` + `pgx` | чистый SQL | везде, базовый навык |
| `pgx` / `pgxpool` напрямую | нативный драйвер PostgreSQL, быстрее, поддерживает типы PG | сервисы только на PG — частый выбор |
| `sqlx` | `database/sql` + сканирование в структуры по тегам | меньше ручного `Scan` |
| `sqlc` | генерирует типобезопасный Go-код из SQL-файлов | любят за проверку на этапе сборки |
| GORM, ent | ORM | реже, чем SQLAlchemy в Python |

**Миграции** — версионированные SQL-файлы (`goose`, `golang-migrate`), как Alembic. Схему никогда не меняют руками на проде.

::: quiz open q102-3 собес
Что такое проблема N+1 и как её решить?
--- answer
N+1 — когда для списка из N сущностей делается 1 запрос за списком и ещё N запросов за связанными данными (по одному на элемент). Число запросов растёт линейно, время — тоже, база перегружается мелкими запросами. Решения: один запрос с JOIN; или два запроса — список, потом все связанные одним запросом `WHERE id IN (...)` / `= ANY($1)` с последующей склейкой в памяти (batch loading); в ORM — eager loading (joinedload/selectinload в SQLAlchemy, Preload в GORM). Находят по логам SQL или APM-трейсам: много одинаковых запросов в одном HTTP-запросе.
--- points
- 1 запрос за списком + N за связанными данными
- растёт с размером списка
- JOIN
- пакетная загрузка через IN / ANY
- eager loading в ORM, поиск по логам и трейсам
:::

## Вопросы с собеседования по уроку:
::: quiz open q102-4 собес
Как работать с транзакциями в Go и какие тут типичные ошибки?
--- answer
`tx, err := db.BeginTx(ctx, opts)` (в опциях можно задать уровень изоляции), сразу `defer tx.Rollback()` — после успешного Commit он ничего не делает, а при любом раннем выходе откатит изменения. Все запросы внутри — через `tx.QueryContext/ExecContext`, в конце `tx.Commit()` с проверкой ошибки. Типичные ошибки: запросы через `db` вместо `tx` (идут в другом соединении, не видят изменений, могут зависнуть при исчерпании пула); забытый Rollback (соединение зависает в транзакции); долгие транзакции с внешними вызовами внутри (держат блокировки); гонка «проверил, потом обновил» — лучше условие в UPDATE с проверкой RowsAffected или SELECT FOR UPDATE; отсутствие повторов при ошибках сериализации на Serializable.
--- points
- BeginTx + defer Rollback + Commit
- все запросы через tx
- не держать транзакции долго, без внешних вызовов
- гонка check-then-act: условие в UPDATE / FOR UPDATE
- повтор при serialization failure
:::

::: quiz open q102-5 собес
Как устроен пул соединений в database/sql и какие у него настройки?
--- answer
`*sql.DB` — потокобезопасный пул соединений, создаётся один раз на приложение. Соединения открываются лениво при первом запросе и возвращаются в пул после завершения запроса (для Query — после закрытия rows, для транзакции — после Commit или Rollback). Настройки: `SetMaxOpenConns` — максимум открытых соединений (защищает БД, лишние запросы ждут свободное соединение), `SetMaxIdleConns` — сколько держать в простое, `SetConnMaxLifetime` / `SetConnMaxIdleTime` — время жизни, чтобы переоткрывать соединения, которые мог закрыть балансировщик или pgbouncer. `db.Stats()` показывает, сколько ждали соединения. Если не закрывать rows, соединения утекают и пул исчерпывается.
--- points
- sql.DB — пул, один на приложение, потокобезопасный
- ленивое открытие, возврат после rows.Close / Commit
- MaxOpenConns, MaxIdleConns, ConnMaxLifetime
- утечка из-за незакрытых rows
:::
