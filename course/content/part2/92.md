# 9.2 Middleware, авторизация, таймауты

## Middleware — обёртка вокруг хендлера:
Логирование, восстановление после паники, проверка токена, метрики нужны *каждому* запросу. Копировать их в каждый хендлер — плохая идея. Middleware — функция, которая принимает хендлер и возвращает новый, с дополнительным поведением до и/или после:
```go
func Logging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r)                                   // вызываем обёрнутый хендлер
        log.Printf("%s %s %v", r.Method, r.URL.Path, time.Since(start))
    })
}

handler := Logging(Recover(mux)) // запрос идёт: Logging → Recover → mux
```
Это паттерн «декоратор». Он работает, потому что `http.Handler` — интерфейс из одного метода.

```go
package main

import (

	"net/http"
	"net/http/httptest"

		fmt.Println("хендлер")
	})

}
```
--- answer

до B

после B
после A
--- why
Внешний middleware — A, он первым получает запрос и последним заканчивает. Похоже на матрёшку или стек вызовов. Поэтому Recover ставят как можно ближе к внешнему краю: он должен поймать панику в любом слое под ним.

## Как узнать статус ответа в middleware:
`http.ResponseWriter` не умеет говорить, какой статус записали. Поэтому его оборачивают:
```go
type statusRecorder struct {
    http.ResponseWriter       // встраивание: все методы проходят насквозь
    status int
}

func (r *statusRecorder) WriteHeader(code int) {
    r.status = code
    r.ResponseWriter.WriteHeader(code)
}

rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK} // 200 — если WriteHeader не вызовут
next.ServeHTTP(rec, r)
log.Println(rec.status)
```
Встраивание из 5.2 в деле: переопределяем один метод, остальные достаются даром.

## Данные запроса — в context:
Middleware узнал пользователя по токену — как передать его хендлеру? Через контекст запроса:
```go
type ctxKey string                       // свой тип ключа: никто случайно не перезапишет

ctx := context.WithValue(r.Context(), ctxKey("user"), user)
next.ServeHTTP(w, r.WithContext(ctx))

// в хендлере:
user, ok := r.Context().Value(ctxKey("user")).(User)
```
В контекст кладут только данные *запроса*: id запроса, пользователя, trace id. Зависимости (БД, логгер) передают через структуры. Подробнее о context — в модуле 11.

## Аутентификация и авторизация:
- **аутентификация** — «кто ты?»: проверить токен или пароль. Не получилось — **401 Unauthorized**
- **авторизация** — «что тебе можно?»: ты Гоша, но объявление чужое. Нельзя — **403 Forbidden**

::: quiz choice q92-2 собес
Пользователь с валидным токеном пытается удалить чужое объявление. Какой статус?
- [ ] 400 Bad Request
- [ ] 401 Unauthorized
- [x] 403 Forbidden
- [ ] 404 Not Found
--- why
Кто он, мы знаем (токен валиден), поэтому не 401. Права нет — 403. Иногда сознательно отвечают 404, чтобы не раскрывать, что объявление существует. Это допустимо, если так решили для безопасности.
:::

## Сессии и JWT:
| | Сессия | JWT |
|---|---|---|
| Что у клиента | случайный id в cookie | подписанный токен с данными |
| Где правда | в хранилище сервера (Redis, БД) | в самом токене |
| Проверка | поход в хранилище | проверка подписи, без похода в хранилище |
| Отозвать сразу | удалить сессию | нельзя до истечения срока |

JWT состоит из трёх частей в base64url через точку: `header.payload.signature`. Payload **не зашифрован**, его прочитает любой, поэтому пароли и персональные данные туда не кладут. Подпись (HMAC или RSA/ECDSA) гарантирует, что токен не подделан. Обычно делают короткий access-токен (минуты) и длинный refresh-токен, который хранится на сервере и может быть отозван.

## Пароли:
- никогда не хранить открытым текстом и никогда не хешировать MD5/SHA-256: они быстрые, их перебирают миллиардами в секунду
- использовать **медленные** функции с солью: `bcrypt` (`golang.org/x/crypto/bcrypt`) или `argon2id`
- сравнение — только через `bcrypt.CompareHashAndPassword`

::: quiz choice q92-3
Что верно про JWT? Выбери все правильные утверждения.
- [x] содержимое payload может прочитать любой, у кого есть токен
- [ ] JWT зашифрован, поэтому туда можно положить номер телефона
- [x] отозвать выданный токен до истечения срока без дополнительного хранилища нельзя
- [x] сервер проверяет токен по подписи, не обращаясь к базе
--- why
JWT подписан, но не зашифрован (base64 — кодировка, а не шифр). Его сильная сторона — проверка без хранилища, слабая — отзыв. Поэтому access-токены живут недолго.

## Таймауты сервера:
`http.ListenAndServe` создаёт сервер **без таймаутов**. Медленный клиент может держать соединение вечно (атака Slowloris).
```go
srv := &http.Server{
    Addr:              ":4000",
    Handler:           handler,
    ReadHeaderTimeout: 5 * time.Second,  // успеть прислать заголовки
    ReadTimeout:       10 * time.Second, // весь запрос
    WriteTimeout:      15 * time.Second, // успеть отдать ответ
    IdleTimeout:       60 * time.Second, // keep-alive простаивающих соединений
}
```
`r.Context()` отменяется, когда клиент отключился. Передавай его в запросы к БД, чтобы не делать работу для того, кто уже ушёл.

## Graceful shutdown:
При деплое процессу шлют SIGTERM. Если просто умереть, оборвутся запросы в процессе. Правильно — перестать принимать новые, доделать текущие и выйти:
```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()

go func() {
    if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
        log.Fatal(err)
    }
}()

<-ctx.Done()                                                  // пришёл сигнал
shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
if err := srv.Shutdown(shutdownCtx); err != nil {             // ждём текущие запросы
    log.Printf("не успели: %v", err)
}
// закрыть БД, сбросить буферы логов
```

## Вопросы с собеседования по уроку:
::: quiz open q92-5 собес
Что такое graceful shutdown и как его сделать в Go?
--- answer
Graceful shutdown — корректное завершение: при получении SIGTERM/SIGINT сервис перестаёт принимать новые соединения, дожидается завершения текущих запросов (с ограничением по времени), закрывает ресурсы (БД, брокеры, сбрасывает буферы) и только потом выходит. В Go: `signal.NotifyContext` ловит сигнал, сервер работает в горутине, по сигналу вызывается `srv.Shutdown(ctx)` с контекстом-таймаутом. `ListenAndServe` при этом возвращает `http.ErrServerClosed`, это не ошибка. Фоновые воркеры останавливают через отмену контекста и ждут через WaitGroup. В Kubernetes ещё учитывают, что под исключается из балансировки не мгновенно, поэтому перед Shutdown иногда делают паузу или переводят readiness-пробу в состояние «не готов».
--- points
- реакция на SIGTERM/SIGINT
- перестать принимать новые, доделать текущие
- signal.NotifyContext + srv.Shutdown(ctx с таймаутом)
- ErrServerClosed — не ошибка
- закрыть ресурсы и остановить воркеры
:::

::: quiz open q92-6 собес
Как устроен JWT и чем он отличается от сессий? Как хранить пароли?
--- answer
JWT — три части в base64url через точку: header (алгоритм), payload (claims: sub, exp, роли) и signature — подпись header+payload секретом (HMAC) или приватным ключом (RSA/ECDSA). Сервер проверяет подпись и срок, не обращаясь к хранилищу, поэтому JWT удобен для stateless-сервисов. Payload не зашифрован. Отозвать токен до истечения срока нельзя без чёрного списка, поэтому access-токены делают короткими, а длинный refresh-токен хранят на сервере. Сессия — случайный идентификатор в cookie, все данные лежат на сервере (Redis/БД). Её легко отозвать, но каждая проверка требует похода в хранилище.

Пароли хранят только как хеш медленной функцией с солью (bcrypt, argon2id) и сравнивают специальной функцией. MD5 и SHA быстрые, поэтому для паролей не годятся.
--- points
- header.payload.signature в base64url
- подпись, а не шифрование: payload читаем
- проверка без хранилища, но сложно отозвать
- короткий access + refresh
- сессия: id в cookie, данные на сервере
- пароли: bcrypt/argon2 с солью, не MD5/SHA
:::
