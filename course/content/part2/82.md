# 8.2 Тестирование

## Тесты в Go — без фреймворков:
Всё нужное есть в стандартной библиотеке: пакет `testing` и команда `go test`. Тесты лежат рядом с кодом в файлах `*_test.go`, тестовая функция называется `TestXxx(t *testing.T)`.
```bash
go test ./...                    # все пакеты
go test -v -run 'TestShipping' . # подробно и только нужные тесты
go test -count=1 ./...           # без кэша результатов
go test -race ./...              # с детектором гонок
go test -cover ./...             # процент покрытия
```
В индустрии часто добавляют `testify` (`require.NoError(t, err)`, `assert.Equal(t, want, got)`): короче писать, а смысл тот же. В курсе пишем на чистом `testing`, чтобы ты видел, что происходит.

## Table-driven тесты и t.Run:
Главный приём Go-тестов — таблица случаев и один цикл:
```go
func TestTruncate(t *testing.T) {
    tests := []struct {
        name string
        in   string
        n    int
        want string
    }{
        {"короче лимита", "Диван", 10, "Диван"},
        {"ровно лимит", "Диван", 5, "Диван"},
        {"кириллица режется по буквам", "Велосипед", 3, "Вел…"},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {   // подтест со своим именем
            if got := Truncate(tt.in, tt.n); got != tt.want {
                t.Errorf("Truncate(%q, %d) = %q, want %q", tt.in, tt.n, got, tt.want)
            }
        })
    }
}
```
- новый случай — одна строка в таблице
- `t.Run` даёт подтесту имя: в выводе видно, какой случай упал, и его можно запустить отдельно: `-run 'TestTruncate/ровно'`
- хорошее сообщение об ошибке: *что вызвали, что получили, что ждали*

## Полезные методы t:
| Метод | Что делает |
|---|---|
| `t.Errorf` | отмечает провал, тест **продолжается** |
| `t.Fatalf` | отмечает провал и **останавливает** тест (дальше нет смысла: например, `nil` вместо объекта) |
| `t.Helper()` | в функции-помощнике: ошибка покажет строку вызова, а не строку внутри помощника |
| `t.Cleanup(f)` | выполнить f после теста (закрыть БД, удалить файлы) |
| `t.TempDir()` | временная папка, удалится сама |
| `t.Parallel()` | тест можно гонять параллельно с другими |

::: quiz choice q82-1
Тест проверяет `ad, err := store.Get(1)`, а дальше обращается к `ad.Title`. Что использовать для проверки `err`?
- [ ] `t.Errorf`: пусть тест покажет все ошибки сразу
- [x] `t.Fatalf`: при ошибке дальше проверять нечего
- [ ] `t.Logf`: просто запишем в лог
- [ ] `panic(err)`: тест всё равно упадёт
--- why
Если `Get` вернул ошибку, проверки полей бессмысленны и дадут поток ложных сообщений. `Fatalf` останавливает тест. `Logf` тест не валит вообще, а `panic` уронит весь прогон пакета, и остальные тесты не выполнятся.
:::

## Что тестировать — техника тест-дизайна:
Тестировщики давно придумали, как выбирать случаи. Это то самое «надо уметь думать».
- **классы эквивалентности**: разбей входы на группы, где программа ведёт себя одинаково (бесплатная зона / платная / ошибка), и возьми по представителю
- **граничные значения**: баги живут на краях. Если правило «до 5 км включительно», проверь 5 и 6. Если «больше 10 кг» — 10 и 10.1
- **ошибки**: каждая ветка `return ..., err` должна быть проверена, и через `errors.Is`, а не по тексту
- **сочетания правил**: «экспресс» и «тяжёлая» по отдельности работают, а вместе?

::: quiz choice q82-2
Правило: «доставка бесплатна на расстояние до 5 км включительно». Какие значения обязательно проверить? Выбери все нужные.
- [ ] 1 км и 100 км — этого достаточно
- [x] 5 км — ровно граница
- [x] 6 км — первое значение за границей
- [ ] 5.5 км — расстояние в целых километрах, такого не бывает
- [x] отрицательное расстояние — должна быть ошибка
--- why
1 и 100 — представители классов, но они не заметят, что программист написал `< 5` вместо `<= 5`. Граница и соседнее с ней значение ловят именно такие ошибки. Некорректный ввод — отдельный класс.
:::

::: quiz choice q82-3 собес
Покрытие тестами — 100%. Что это гарантирует?
- [ ] что в коде нет багов
- [ ] что все граничные случаи проверены
- [x] только то, что каждая строка кода хоть раз выполнилась во время тестов
- [ ] что тесты проверяют результат каждой функции
--- why
Покрытие считает выполненные строки, а не проверенные утверждения. Тест может вызвать функцию и ничего не проверить, и покрытие будет 100%. Честнее измерять, ловят ли тесты баги. Этим и занимается **мутационное тестирование**: в код подкладывают ошибки и смотрят, упадут ли тесты. Именно так устроена домашка этого урока.
:::

::: quiz bug q82-4
Этот тест никогда не падает. Почему?
```go
func TestPrice(t *testing.T) {
    for _, tt := range cases {
        got := Price(tt.in)
        if got != tt.want {
            t.Logf("Price(%v) = %v, want %v", tt.in, got, tt.want)
        }
    }
}
```
- [ ] `range` по таблице копирует случаи
- [x] `t.Logf` только пишет в лог и не отмечает тест как проваленный
- [ ] нужен `t.Run`, без него ошибки не считаются
- [ ] сравнивать через `!=` нельзя, нужен `reflect.DeepEqual`
--- why
Тест падает только после `t.Error*`/`t.Fatal*` (или panic). Опечатка `Logf` вместо `Errorf` делает тест бесполезным. Поэтому полезно один раз увидеть, как твой тест *падает* на сломанном коде.
:::

## Тестовые двойники:
Как тестировать код, который ходит в базу или платёжку? Подменить зависимость. Отсюда правило из 7.2: код зависит от **интерфейса**, а в тесте подставляется своя реализация.
```go
type AdStore interface {
    Get(ctx context.Context, id int) (Ad, error)
}

type fakeStore struct{ ads map[int]Ad }   // фейк: простая рабочая реализация в памяти

func (f *fakeStore) Get(_ context.Context, id int) (Ad, error) {
    ad, ok := f.ads[id]
    if !ok {
        return Ad{}, ErrNotFound
    }
    return ad, nil
}

svc := NewService(&fakeStore{ads: map[int]Ad{1: {Title: "Шкаф"}}})
```
| Двойник | Что это |
|---|---|
| **stub** | возвращает заготовленный ответ |
| **fake** | упрощённая, но рабочая реализация (map вместо БД) |
| **mock** | проверяет, *как* его вызвали: сколько раз, с какими аргументами. Часто генерируется (`gomock`, `mockery`) |
| **spy** | stub, который запоминает вызовы, чтобы потом их проверить |

Совет: предпочитай фейки. Тесты на моках проверяют реализацию и ломаются при любом рефакторинге.

## Пирамида тестов:
- **юнит-тесты** — много, быстрые, с двойниками
- **интеграционные** — с настоящей БД (в Docker, через `testcontainers-go`), проверяют SQL и транзакции
- **e2e** — немного, через настоящий HTTP

## Бенчмарки и фаззинг:
```go
func BenchmarkJoin(b *testing.B) {
    words := []string{"a", "b", "c"}
    for b.Loop() {             // Go 1.24+; раньше: for i := 0; i < b.N; i++
        Join(words, ", ")
    }
}
// go test -bench=Join -benchmem    → нс/операцию, байт/операцию, аллокаций/операцию

func FuzzTruncate(f *testing.F) {
    f.Add("Велосипед", 3)
    f.Fuzz(func(t *testing.T, s string, n int) {
        if !utf8.ValidString(Truncate(s, n)) { // свойство, которое должно выполняться всегда
            t.Error("битый UTF-8")
        }
    })
}
```
Фаззинг сам генерирует входы и ищет те, на которых нарушается свойство.

## Вопросы с собеседования по уроку:
::: quiz open q82-5 собес
Как тестировать код, который ходит в базу данных или во внешний API?
--- answer
Отделить логику от зависимостей: код зависит от интерфейса (хранилища, клиента API), а не от конкретной реализации. В юнит-тестах подставляются двойники: фейк (in-memory реализация), stub или mock (часто сгенерированный через gomock/mockery). Для HTTP-клиентов удобен `httptest.Server`, который поднимает локальный сервер с нужными ответами. SQL и транзакции проверяют интеграционными тестами с настоящей БД, поднятой в Docker (testcontainers-go или docker-compose), с миграциями и очисткой между тестами. Итог — пирамида: много быстрых юнит-тестов, меньше интеграционных, немного e2e.
--- points
- зависимость через интерфейс (DI)
- фейки, стабы, моки
- httptest для внешних HTTP-API
- интеграционные тесты с реальной БД в Docker
- пирамида тестов
:::

::: quiz open q82-6 собес
Что такое table-driven тесты и зачем нужен t.Run?
--- answer
Table-driven тест — это слайс структур со входными данными и ожидаемым результатом плюс один цикл, который прогоняет каждый случай через одну и ту же проверку. Новый случай добавляется одной строкой, логика проверки не дублируется. `t.Run(name, func)` запускает каждый случай как именованный подтест: в выводе видно, какой случай упал, его можно запустить отдельно через `-run 'TestX/имя'`, `Fatal` в подтесте останавливает только его, а подтесты можно распараллелить через `t.Parallel()`.
--- points
- таблица случаев + один цикл
- легко добавлять случаи
- t.Run — именованные подтесты
- запуск одного подтеста через -run
- Fatal останавливает только подтест
:::
