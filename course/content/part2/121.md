# 12.1 Git, Linux, Docker, CI

## Git — как работают в команде:
Ты уже пользуешься Git. В команде к этому добавляется процесс:
1. от свежего `main` создаёшь ветку под задачу: `git switch -c feat/ad-search`
2. мелкие осмысленные коммиты: `feat: поиск объявлений по городу`, `fix: 404 для удалённых`
3. пушишь и открываешь **pull request**: CI гоняет тесты, коллеги делают ревью
4. после одобрения — merge в `main`, и CI/CD выкатывает

| | merge | rebase |
|---|---|---|
| что делает | создаёт коммит слияния, история как была | переносит твои коммиты поверх чужих, история линейная |
| чем опасен | «паутина» в истории | переписывает историю: нельзя делать с веткой, которую уже взяли другие |

Никогда не коммить секреты (пароли, токены, `.env`). Если всё-таки закоммитил, секрет считается утёкшим, даже после удаления коммита: его надо менять.

## Linux, который нужен бэкендеру:
```bash
ps aux | grep barakholka        # процессы
kill -TERM 1234                 # вежливо попросить завершиться (SIGTERM)
kill -9 1234                    # убить (SIGKILL) — перехватить нельзя, defer не выполнится
ss -tlnp | grep 4000            # кто слушает порт (или lsof -i :4000)
curl -i localhost:4000/healthz  # проверить HTTP руками
tail -f app.log | grep ERROR    # смотреть логи
env | grep DATABASE             # переменные окружения
df -h; free -m; top             # диск, память, нагрузка
```
**Сигналы:** `SIGINT` — Ctrl+C, `SIGTERM` — «пожалуйста, завершись» (так останавливают Docker и Kubernetes), `SIGKILL` — убийство без права на последнее слово. Graceful shutdown из 9.2 реагирует на первые два.

::: quiz choice q121-1
Kubernetes отправил поду SIGTERM, подождал 30 секунд и отправил SIGKILL. Что успеет сделать сервис с graceful shutdown?
- [ ] ничего: SIGTERM нельзя перехватить
- [x] на SIGTERM — перестать принимать запросы, доделать текущие, закрыть БД; если не уложится в 30 секунд, SIGKILL оборвёт всё
- [ ] SIGKILL тоже перехватывается через `signal.Notify`
- [ ] сервис получит только SIGKILL
--- why
SIGTERM — обычный сигнал, его ловит `signal.NotifyContext`. SIGKILL ядро выполняет само, процесс о нём не узнает. Поэтому таймаут Shutdown в коде должен быть меньше, чем `terminationGracePeriodSeconds`.
:::

## Docker: образ и контейнер
- **образ** — неизменяемый шаблон: файловая система из слоёв + команда запуска. Как класс
- **контейнер** — запущенный экземпляр образа со своим процессом, сетью и записываемым слоем. Как объект
- контейнер — не виртуальная машина: он использует ядро хоста, а изолирован средствами ядра Linux (namespaces — что процесс видит, cgroups — сколько ресурсов может взять). Поэтому стартует за доли секунды

## Dockerfile для Go — multi-stage:
Go компилируется в один статический бинарник. Компилятор в итоговом образе не нужен: собираем в одном образе, запускаем в другом, крошечном.
```dockerfile
# --- стадия сборки ---
FROM golang:1.26 AS build
WORKDIR /src
# сначала только зависимости: этот слой закэшируется и не будет пересобираться
COPY go.mod go.sum ./
RUN go mod download
# а код меняется часто — копируем его потом
COPY . .
# статический бинарник без libc
RUN CGO_ENABLED=0 go build -o /app ./cmd/api

# --- итоговый образ: ~2 МБ, ни shell, ни пакетного менеджера ---
FROM gcr.io/distroless/static-debian12
COPY --from=build /app /app
# не root: меньше ущерб при взломе
USER nonroot:nonroot
EXPOSE 8080
# exec-форма: процесс получит SIGTERM напрямую
ENTRYPOINT ["/app"]
```
Комментарии в Dockerfile — только отдельной строкой: `#` в конце инструкции станет частью её аргументов.
- **кэш слоёв**: Docker пересобирает слой, только если изменились его входные данные. Поэтому `go.mod` копируют раньше кода
- `.dockerignore` (`.git`, `*.md`, локальные бинарники) уменьшает контекст сборки
- **exec-форма** `["/app"]` против shell-формы `/app`: в shell-форме PID 1 — это `/bin/sh`, он не передаёт SIGTERM приложению, и graceful shutdown не работает

::: quiz choice q121-2 собес
Почему в Dockerfile сначала копируют `go.mod` и `go.sum`, делают `go mod download` и только потом `COPY . .`?
- [ ] иначе `go build` не найдёт зависимости
- [x] чтобы слой с зависимостями кэшировался: при правке кода он не пересобирается, и сборка идёт секунды, а не минуты
- [ ] так требует синтаксис Dockerfile
- [ ] чтобы `go.sum` не попал в итоговый образ
--- why
Каждая инструкция — слой, и Docker переиспользует слой, пока не изменились его входы. Зависимости меняются редко, код — постоянно. При `COPY . .` в начале любая правка в коде инвалидировала бы и скачивание модулей.
:::

## Docker Compose — сервис и база локально:
```yaml
services:
  postgres:
    image: postgres:17
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: barakholka
    volumes:
      - pgdata:/var/lib/postgresql/data   # данные переживут пересоздание контейнера
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 2s
      retries: 10
  api:
    build: .
    ports:
      - "8080:8080"                       # хост:контейнер
    environment:
      DATABASE_URL: postgres://app:secret@postgres:5432/barakholka?sslmode=disable
    depends_on:
      postgres:
        condition: service_healthy        # ждать, пока база реально готова, а не просто запущена
volumes:
  pgdata:
```

::: quiz bug q121-3 собес
В compose сервис `api` не может подключиться к базе: `connection refused`. На ноутбуке без Docker всё работало. В чём дело?
```yaml
  api:
    environment:
      DATABASE_URL: postgres://app:secret@localhost:5432/barakholka
```
- [ ] нужно открыть порт 5432 через `ports`
- [x] `localhost` внутри контейнера — это сам контейнер `api`; базу нужно искать по имени сервиса: `postgres:5432`
- [ ] Postgres не принимает пароль `secret`
- [ ] нужен `network_mode: host` во всех случаях
--- why
У каждого контейнера своя сеть и свой localhost. Compose создаёт общую сеть, где контейнеры доступны по именам сервисов через встроенный DNS. `ports` нужен только для доступа *с хоста*.
:::

## CI/CD:
**CI** (continuous integration) — на каждый push и PR автоматически: сборка, линтеры, тесты. Сломанный код не попадает в `main`. **CD** — автоматическая выкладка: собрать образ, отправить в registry, обновить сервис.
```yaml
# .github/workflows/ci.yml
name: ci
on:
  push:
    branches: [main]
  pull_request:
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
      - run: go vet ./...
      - run: go test -race -count=1 ./...
      - uses: golangci/golangci-lint-action@v6
```

## Kubernetes — минимум для собеса:
| Сущность | Что это |
|---|---|
| **Pod** | минимальная единица: один или несколько контейнеров с общей сетью |
| **Deployment** | «держи N одинаковых подов этой версии»; делает rolling update |
| **Service** | постоянный адрес и балансировка на поды |
| **Ingress** | вход снаружи: домены и пути → сервисы |
| **ConfigMap / Secret** | конфигурация и секреты, подставляются как env или файлы |
| **liveness-проба** | «жив ли процесс». Не отвечает — под перезапускают |
| **readiness-проба** | «готов ли принимать трафик». Не готов — его убирают из балансировки, но не убивают |

::: quiz choice q121-4 собес
Сервис стартует 20 секунд: прогревает кэш и ждёт базу. Какая проба не даст отправлять на него запросы раньше времени?
- [ ] liveness
- [x] readiness
- [ ] обе одинаково
- [ ] никакая, Kubernetes сам знает
--- why
Readiness управляет трафиком. Если повесить проверку базы на liveness, при проблемах с БД Kubernetes начнёт перезапускать здоровые поды по кругу, и станет только хуже. Liveness проверяет «процесс не завис», readiness — «готов работать».
:::

## Вопросы с собеседования по уроку:
::: quiz open q121-5 собес
Что такое Docker? Чем контейнер отличается от виртуальной машины и образ — от контейнера?
--- answer
Docker упаковывает приложение со всеми зависимостями в образ и запускает его в изолированном контейнере одинаково на любой машине. Образ — неизменяемый шаблон из слоёв файловой системы и метаданных (команда запуска, переменные). Контейнер — запущенный экземпляр образа с собственным записываемым слоем, процессами и сетью. В отличие от виртуальной машины, контейнер не эмулирует железо и не содержит своего ядра: процессы работают на ядре хоста, а изоляция обеспечивается namespaces (pid, net, mnt…) и ограничения ресурсов — cgroups. Поэтому контейнеры лёгкие и стартуют за доли секунды, но изоляция у них слабее, чем у ВМ. Для Go характерны multi-stage сборки и минимальные образы (distroless/scratch).
--- points
- упаковка приложения с зависимостями
- образ — слои, шаблон; контейнер — запущенный экземпляр
- общее ядро хоста, namespaces и cgroups
- ВМ эмулирует железо и имеет своё ядро
- multi-stage и маленькие образы для Go
:::

::: quiz open q121-6 собес
Что такое Kubernetes и из каких основных сущностей он состоит?
--- answer
Kubernetes — оркестратор контейнеров: по декларативному описанию (YAML) он поддерживает нужное состояние кластера — запускает контейнеры на узлах, перезапускает упавшие, масштабирует, обновляет версии без простоя, балансирует трафик. Основные сущности: Pod — минимальная единица запуска (контейнеры с общей сетью и томами); Deployment — описание N реплик пода и стратегии обновления (через ReplicaSet); Service — стабильный адрес и балансировка на поды; Ingress — маршрутизация внешнего HTTP-трафика; ConfigMap и Secret — конфигурация; Namespace — разделение ресурсов; HPA — автомасштабирование. Для приложения важны пробы liveness/readiness/startup, лимиты ресурсов (requests/limits) и корректная обработка SIGTERM.
--- points
- оркестрация: декларативное желаемое состояние
- Pod, Deployment, Service, Ingress
- ConfigMap, Secret
- liveness и readiness пробы
- масштабирование, rolling update, SIGTERM
:::
