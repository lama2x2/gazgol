# 11.2 Паттерны конкурентности: что дают на лайвкодинге

## Каналы: таблица, которую надо знать наизусть
| Операция | nil-канал | закрытый канал | открытый канал |
|---|---|---|---|
| отправка `ch <- v` | блокируется навсегда | **panic** | ждёт получателя (или место в буфере) |
| получение `<-ch` | блокируется навсегда | сразу нулевое значение, `ok == false` | ждёт значение |
| `close(ch)` | **panic** | **panic** | закрывает |

Правила, которые из неё следуют:
- **закрывает канал только отправитель**, и только когда точно больше не будет отправлять. Получатель канал не закрывает
- если отправителей несколько, закрывают после того, как все закончили: `wg.Wait()`, потом `close`
- закрывать канал не обязательно: его соберёт GC. Закрытие — это *сигнал* «данных больше не будет» для `range`
- nil-канал полезен в `select`: присвой каналу nil, и этот case «выключится»

::: quiz output q112-1 собес
Чтение из закрытого канала:
```go
package main

import "fmt"

func main() {
	ch := make(chan int, 2)
	ch <- 1
	ch <- 2
	close(ch)

	for i := 0; i < 4; i++ {
		v, ok := <-ch
		fmt.Println(v, ok)
	}
}
```
--- answer
1 true
2 true
0 false
0 false
--- why
После закрытия из канала сначала вычитываются оставшиеся в буфере значения, а потом сразу возвращаются нулевые с `ok == false`. Блокировки нет. По этому признаку `for v := range ch` понимает, что пора выходить.
:::

::: quiz choice q112-3 verify=panic
А так?
```go
package main

func main() {
	ch := make(chan int, 1)
	close(ch)
	ch <- 1
}
```
- [ ] значение запишется в буфер
- [ ] отправка заблокируется навсегда
- [x] `panic: send on closed channel`
- [ ] ничего не произойдёт

Отправка в закрытый канал — всегда паника, даже если в буфере есть место. Поэтому закрывает только отправитель, и только когда он точно последний.

::: quiz output q112-4
nil-канал в select:
```go
package main

import "fmt"

func main() {
	a := make(chan int)
	close(a)
	var b chan int

	select {
	case <-b:
		fmt.Println("b")
	case v, ok := <-a:
		fmt.Println("a", v, ok)
	}
}
```
--- answer
a 0 false
--- why
Из nil-канала нельзя прочитать никогда, поэтому этот case просто не участвует. Закрытый `a` готов сразу. Этот приём используют в merge: когда вход закрылся, его переменную обнуляют, и select перестаёт его слушать.

## Fan-in: слить несколько каналов в один
Классика лайвкодинга: «есть N каналов, сделай один, из которого читаются все значения».
```go
func Merge(ctx context.Context, ins ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    for _, in := range ins {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for v := range in {
                select {
                case out <- v:
                case <-ctx.Done():
                    return            // никто не читает — выходим, а не висим
                }
            }
        }()
    }
    go func() {
        wg.Wait()                     // все писатели закончили —
        close(out)                    // можно закрывать
    }()
    return out
}
```
Три важные детали: по горутине на вход, закрытие после `wg.Wait()` в отдельной горутине, отправка в `select` с `ctx.Done()`.

## Конвейер с отменой:
```go
func Square(ctx context.Context, in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for v := range in {
            select {
            case out <- v * v:
            case <-ctx.Done():
                return
            }
        }
    }()
    return out
}
// gen → Square → Square → Merge: каждая стадия — горутина, ctx останавливает всё
```

## Ограничение частоты (rate limiting):
Внешний API разрешает 10 запросов в секунду. Самый простой способ — тикер:
```go
tick := time.NewTicker(100 * time.Millisecond)
defer tick.Stop()
for _, req := range requests {
    <-tick.C                // не чаще раза в 100 мс
    go call(req)
}
```
Гибче **token bucket** (`golang.org/x/time/rate`): в ведре до `burst` жетонов, они пополняются со скоростью `rate`, и каждый запрос забирает жетон. Короткий всплеск пропускается сразу, а средняя скорость ограничена. В домашке ты напишешь такой лимитер сам.

## Примитивы синхронизации:
| Примитив | Когда |
|---|---|
| канал | передать данные или сигнал между горутинами |
| `sync.WaitGroup` | дождаться группу горутин |
| `sync.Mutex` | защитить общее состояние |
| `sync.RWMutex` | много читателей, редкие писатели: `RLock` пускает читателей параллельно |
| `sync.Once` | выполнить ровно один раз (ленивая инициализация) |
| `sync/atomic` | счётчики и флаги без блокировки: `atomic.Int64`, `CompareAndSwap` |
| `sync.Cond` | ждать условия (редко: обычно хватает каналов) |
| `sync.Map` | map с особым профилем: ключи пишутся один раз, читаются много |
| `errgroup`, `semaphore` | из `golang.org/x/sync` |

## Race condition и data race — не одно и то же:
- **data race** — две горутины одновременно обращаются к одной памяти, и хотя бы одна пишет, без синхронизации. Это неопределённое поведение. Его находит `go test -race`
- **race condition** — результат зависит от порядка событий. Бывает и без data race: «проверили, что объявление активно, потом продали» — между проверкой и продажей успел другой покупатель, хотя каждое действие защищено мьютексом

::: quiz choice q112-5 собес verify=race
Что не так с этим счётчиком?
```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	views := 0
	var wg sync.WaitGroup
	for range 1000 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			views++
		}()
	}
	wg.Wait()
	fmt.Println(views)
}
```
- [ ] всё правильно, `WaitGroup` синхронизирует горутины
- [x] data race: `views++` — это чтение, сложение и запись, и горутины перетирают друг друга; результат может быть меньше 1000
- [ ] будет deadlock
- [ ] не скомпилируется: замыкание не может менять внешнюю переменную
--- why
`WaitGroup` только дожидается завершения, но не защищает `views`. Исправить можно мьютексом или `atomic.Int64` с `views.Add(1)`. Детектор гонок `-race` показывает это сразу.
:::

::: quiz design q112-6
Спроектируй (словами или псевдокодом): сервис должен разослать уведомления 100 000 подписчиков. Внешний API рассылки выдерживает не больше 50 запросов в секунду и 20 одновременных соединений, иногда отвечает 503. Как устроить отправку?
--- answer
Пул из 20 воркеров читает задачи из канала (ограничение одновременности). Перед каждым запросом воркер берёт жетон у общего rate limiter на 50 запросов в секунду (token bucket, `rate.Limiter.Wait(ctx)`). На 503 и таймауты — повтор с экспоненциальной паузой и случайным разбросом (jitter), с ограничением числа попыток. Неудачные после всех попыток пишутся в отдельную очередь или таблицу для повторной обработки. Всё управляется одним `ctx` для остановки при shutdown. Прогресс сохраняется (кому уже отправлено), чтобы после рестарта не слать повторно. В идеале задачи лежат в очереди (Kafka или RabbitMQ), а не в памяти. Время: 100 000 / 50 в секунду ≈ 33 минуты — это ограничение API, быстрее не выйдет.
--- points
- пул воркеров ограничивает одновременность (20)
- rate limiter ограничивает частоту (50/с)
- повторы с backoff и jitter на 503
- учёт отправленных, повторная обработка неудачных
- отмена через context
- оценка времени по лимиту
:::

::: hw 112
* `Merge` — слить каналы в один {TestMerge}
+ Схема из теории: горутина на вход, `WaitGroup`, закрытие `out` в отдельной горутине после `wg.Wait()`, отправка через `select` с `ctx.Done()`.
! Если закрыть `out` раньше, чем закончат все писатели, будет panic «send on closed channel». Если не слушать `ctx` при отправке, после отмены горутины зависнут. Тест считает горутины.
* `Map` — обобщённая стадия конвейера {TestMap}
+ `Map[T, U any](ctx, in <-chan T, f func(T) U) <-chan U`: новый канал, горутина с `defer close(out)`, цикл `for v := range in` и отправка в `select` с `ctx.Done()`.
* `Limiter` — token bucket {TestLimiter}
+ Храни `tokens float64` и время последнего пополнения. В `Allow`: прибавь `elapsed.Seconds() * rate` жетонов (не больше `burst`), обнови время. Если жетонов `>= 1`, отними один и верни true.
! Время бери только из переданного `now()`: тест подменяет часы, иначе он был бы медленным и нестабильным. Защити поля мьютексом: `Allow` зовут из многих горутин.
* `Lazy` — вычислить один раз, даже если просят сто горутин {TestLazy}
+ Поля `once sync.Once`, `val T`, `err error`. `Get` вызывает `l.once.Do(func() { l.val, l.err = l.f() })` и возвращает сохранённое.
* `Batch ★` — собирать элементы в пачки по размеру или по времени {TestBatch}
+ Цикл с `select` по входу и таймеру. Первый элемент пачки запускает таймер на `wait`. Пачка уходит, когда набралось `size` элементов или сработал таймер. При закрытии входа отправь остаток и закрой выход.
! Пока пачка пуста, таймер не нужен: в select подставь nil-канал вместо `timer.C`. Это тот самый приём с nil-каналом.
:::

## Вопросы с собеседования по уроку:
::: quiz open q112-7 собес
Что будет при чтении, записи и закрытии nil-канала и закрытого канала? Чем отличаются буферизованные каналы от небуферизованных?
--- answer
Небуферизованный канал синхронизирует: отправка ждёт получателя, получение ждёт отправителя (рандеву). Буферизованный хранит до cap значений: отправка блокируется только при полном буфере, получение — при пустом. Nil-канал: отправка и получение блокируются навсегда, close вызывает panic. Закрытый канал: получение сразу отдаёт оставшиеся в буфере значения, потом нулевое значение и ok == false; отправка — panic; повторный close — panic. Закрывает канал отправитель, сигнализируя «данных больше не будет». `range` по каналу завершается после закрытия и опустошения буфера.
--- points
- небуферизованный — синхронная передача
- буферизованный блокирует при полном/пустом буфере
- nil: блокировка навсегда, close — panic
- закрытый: чтение даёт остаток, потом zero и ok=false
- запись в закрытый и повторный close — panic
- закрывает отправитель
:::

::: quiz open q112-8 собес
Что такое race condition и data race? Как их находить и предотвращать?
--- answer
Data race — одновременный доступ двух горутин к одной области памяти, где хотя бы один доступ — запись, без синхронизации. Это неопределённое поведение: значения теряются, структуры (например, map) повреждаются. Находится детектором `-race` в тестах и на стенде. Предотвращается мьютексами, атомиками, передачей владения через каналы. Race condition — логическая ошибка, когда результат зависит от порядка или времени выполнения операций. Например, check-then-act: проверили остаток, потом списали, а между этим кто-то успел списать. Она возможна и без data race, и детектор её не найдёт. Решается атомарностью операции на нужном уровне: одна критическая секция на проверку и изменение, условный UPDATE в БД, транзакции, блокировки.
--- points
- data race: одновременный доступ с записью без синхронизации
- -race детектор
- mutex / atomic / каналы
- race condition: зависимость от порядка, check-then-act
- бывает без data race, лечится атомарностью операции
:::

::: quiz open q112-9 собес
Какие примитивы синхронизации есть в Go и когда что использовать?
--- answer
Каналы — для передачи данных и сигналов между горутинами (владение данными переходит вместе с ними). `sync.Mutex` — защита общего состояния короткой критической секцией. `sync.RWMutex` — когда чтений много, а записей мало: читатели не блокируют друг друга. `sync.WaitGroup` — дождаться группу горутин. `sync.Once` — однократная инициализация. `sync/atomic` — счётчики и флаги без блокировок, CAS. `sync.Cond` — ожидание условия, используется редко. `sync.Map` — для кэшей, где ключи записываются один раз и много читаются, или где горутины работают с разными ключами. `sync.Pool` — переиспользование временных объектов. Из `golang.org/x/sync`: errgroup и semaphore. Правило: «не общайтесь через общую память, делитесь памятью через общение», но мьютекс проще канала, если нужно просто защитить поле.
--- points
- каналы — передача данных и сигналов
- Mutex и RWMutex
- WaitGroup и Once
- atomic
- sync.Map, Pool, Cond
- errgroup и semaphore
:::
