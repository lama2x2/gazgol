# 10.1 SQL: запросы, индексы, транзакции

## Реляционная модель — на примере Барахолки:
Данные лежат в таблицах, связанных ключами:
```sql
CREATE TABLE users (
    id    INTEGER PRIMARY KEY,           -- первичный ключ: уникален, не NULL
    name  TEXT NOT NULL,
    city  TEXT NOT NULL
);

CREATE TABLE ads (
    id       INTEGER PRIMARY KEY,
    user_id  INTEGER NOT NULL REFERENCES users(id), -- внешний ключ: продавец должен существовать
    title    TEXT NOT NULL,
    price    INTEGER NOT NULL CHECK (price >= 0),
    category TEXT NOT NULL,
    status   TEXT NOT NULL DEFAULT 'active'          -- 'active' или 'sold'
);

CREATE TABLE deals (
    id       INTEGER PRIMARY KEY,
    ad_id    INTEGER NOT NULL REFERENCES ads(id),
    buyer_id INTEGER NOT NULL REFERENCES users(id),
    price    INTEGER NOT NULL
);
```
Ограничения (`NOT NULL`, `CHECK`, `REFERENCES`, `UNIQUE`) — последняя линия защиты: база не даст записать мусор, даже если в Go-коде баг.

Ты уже работал с PostgreSQL через SQLAlchemy. Здесь пишем SQL руками: на собесах дают задачи на SQL, а в Go-проектах ORM используют реже, чем в Python.

## SELECT по шагам:
```sql
SELECT u.city, COUNT(*) AS ads_count, AVG(a.price) AS avg_price
FROM ads a
JOIN users u ON u.id = a.user_id      -- 1. соединяем таблицы
WHERE a.status = 'active'             -- 2. фильтруем СТРОКИ
GROUP BY u.city                       -- 3. группируем
HAVING COUNT(*) >= 10                 -- 4. фильтруем ГРУППЫ
ORDER BY ads_count DESC               -- 5. сортируем
LIMIT 5;                              -- 6. отрезаем
```
Порядок *выполнения* отличается от порядка *записи*: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Поэтому в `WHERE` нельзя сослаться на `COUNT(*)`: группировки ещё не было.

::: quiz choice q101-1 собес
Чем WHERE отличается от HAVING?
- [ ] ничем, это синонимы
- [x] WHERE фильтрует строки до группировки, HAVING — группы после неё, и в HAVING можно использовать агрегаты
- [ ] HAVING работает быстрее, потому что использует индекс
- [ ] WHERE нельзя использовать вместе с GROUP BY
--- why
`WHERE price > 1000` отбрасывает строки до подсчёта. `HAVING COUNT(*) > 5` отбрасывает группы, в которых меньше 6 строк. Если условие не про агрегат, ставь его в `WHERE`: тогда меньше строк попадёт в группировку.
:::

## JOIN:
- `JOIN` (INNER) — только пары, у которых нашлось совпадение
- `LEFT JOIN` — все строки левой таблицы. Если пары нет, справа NULL. Так ищут «пользователей без объявлений»: `LEFT JOIN ads ... WHERE ads.id IS NULL`
- то же можно сделать через подзапрос: `WHERE NOT EXISTS (SELECT 1 FROM ads WHERE ads.user_id = users.id)`

::: quiz choice q101-2
В таблице `users` 10 пользователей, у 7 из них есть объявления (у кого-то по несколько, всего 20 объявлений). Сколько строк вернёт `SELECT * FROM users u LEFT JOIN ads a ON a.user_id = u.id`?
- [ ] 10
- [ ] 20
- [x] 23
- [ ] 200
--- why
Каждый из 7 пользователей с объявлениями даёт столько строк, сколько у него объявлений, — всего 20. Трое без объявлений дают по одной строке с NULL справа. 20 + 3 = 23. Обычный `JOIN` вернул бы 20. Это частая причина «раздутых» сумм после JOIN.
:::

## Индексы:
Без индекса `WHERE category = 'мебель'` читает всю таблицу (*sequential scan*). Индекс — отдельная структура, обычно **B-дерево**: отсортированные значения с указателями на строки. Поиск по нему — O(log n).
```sql
CREATE INDEX ads_category_price_idx ON ads (category, price);
```
- **составной индекс** работает по принципу «левого префикса»: `(category, price)` помогает для `WHERE category = ?` и для `WHERE category = ? AND price < ?`, но не для `WHERE price < ?` без категории. Это как телефонный справочник, отсортированный по фамилии, потом по имени
- индекс помогает и `ORDER BY` по тем же колонкам: строки уже лежат отсортированными
- индекс **не бесплатный**: замедляет INSERT и UPDATE, занимает место
- индекс не поможет, если на колонку надета функция (`WHERE lower(title) = ...`; нужен индекс по выражению), при `LIKE '%шкаф'` с процентом в начале и когда условию соответствует большая часть таблицы
- `EXPLAIN ANALYZE запрос` показывает план: используется ли индекс и где время

::: quiz choice q101-3 собес
Частый запрос: `SELECT * FROM ads WHERE category = $1 AND status = 'active' ORDER BY price LIMIT 20`. Какой индекс подойдёт лучше всего?
- [ ] `(price)`
- [ ] три отдельных индекса: `(category)`, `(status)`, `(price)`
- [x] `(category, status, price)`
- [ ] `(price, status, category)`
--- why
Равенства — в начале составного индекса, колонка сортировки — в конце. Тогда база находит нужный «кусок» индекса и читает первые 20 строк уже в порядке цены, без сортировки. Индекс, начинающийся с `price`, для фильтра по категории почти бесполезен.
:::

## Транзакции и ACID:
Покупка — это несколько изменений: списать деньги, начислить продавцу, отметить «продано», записать сделку. Они должны выполниться **все или ни одного**:
```sql
BEGIN;
UPDATE users SET balance = balance - 5000 WHERE id = 7;
UPDATE users SET balance = balance + 5000 WHERE id = 3;
UPDATE ads SET status = 'sold' WHERE id = 42 AND status = 'active';
INSERT INTO deals (ad_id, buyer_id, price) VALUES (42, 7, 5000);
COMMIT;   -- или ROLLBACK при ошибке
```
- **A**tomicity — всё или ничего
- **C**onsistency — после транзакции все ограничения выполнены
- **I**solation — параллельные транзакции не мешают друг другу (насколько именно — задаёт уровень изоляции)
- **D**urability — после COMMIT данные не пропадут даже при падении сервера (журнал WAL)

## Уровни изоляции — вопрос №1 по базам на собесах:
Когда транзакции идут параллельно, возможны **аномалии**:
| Аномалия | Что происходит |
|---|---|
| **грязное чтение** | читаем то, что другая транзакция записала, но ещё не закоммитила (и может откатить) |
| **неповторяющееся чтение** | читаем строку дважды и получаем разные значения: между чтениями её изменили и закоммитили |
| **фантомное чтение** | повторяем запрос с условием и получаем другой *набор* строк: кто-то добавил подходящую |
| **аномалия сериализации** | каждая транзакция по отдельности корректна, а вместе получается результат, невозможный ни при каком последовательном порядке |

Стандарт SQL определяет уровни по тому, какие аномалии они запрещают:
| Уровень | Грязное | Неповторяющееся | Фантомы | Сериализация |
|---|---|---|---|---|
| Read Uncommitted | возможно | возможно | возможно | возможно |
| **Read Committed** | нет | возможно | возможно | возможно |
| Repeatable Read | нет | нет | возможно (*в PG — нет*) | возможно |
| Serializable | нет | нет | нет | нет |

**PostgreSQL:** по умолчанию Read Committed. Грязного чтения в нём не бывает никогда (Read Uncommitted работает как Read Committed). Repeatable Read работает на снимке данных и не пропускает фантомы. На Serializable транзакция может упасть с ошибкой сериализации, и её нужно **повторить**. За это отвечает код приложения.

**Потерянное обновление** — классика: две транзакции читают баланс 100, обе прибавляют 50 и пишут 150 вместо 200. Решения: атомарный `UPDATE ... SET balance = balance + 50`, блокировка строки `SELECT ... FOR UPDATE` или оптимистичная блокировка с колонкой `version`.

::: quiz choice q101-4 собес

- [ ] грязное чтение
- [x] неповторяющееся чтение
- [ ] фантомное чтение
- [ ] потерянное обновление
--- why
Изменённое значение уже закоммичено, поэтому это не грязное чтение. Изменилась *та же строка*, а не набор строк, поэтому не фантом. Repeatable Read бы это предотвратил: транзакция видела бы снимок на момент первого чтения.
:::

## Вопросы с собеседования по уроку:
::: quiz open q101-6 собес
Что такое транзакция? Расшифруй ACID.
--- answer
Транзакция — группа операций, которая выполняется как единое целое: либо все изменения фиксируются (COMMIT), либо ни одно (ROLLBACK). ACID: Atomicity — атомарность, всё или ничего; Consistency — согласованность, после транзакции соблюдены все ограничения и инварианты; Isolation — изолированность, параллельные транзакции не видят промежуточных состояний друг друга в пределах выбранного уровня изоляции; Durability — долговечность, закоммиченные данные сохраняются даже после сбоя, обеспечивается журналом (WAL в PostgreSQL). Пример — перевод денег между счетами.
--- points
- группа операций как единое целое, COMMIT/ROLLBACK
- атомарность
- согласованность (ограничения)
- изолированность и уровни изоляции
- долговечность (WAL)
:::

::: quiz open q101-7 собес
Какие есть уровни изоляции транзакций и какие аномалии они предотвращают?
--- answer
Аномалии: грязное чтение (видны незакоммиченные изменения), неповторяющееся чтение (повторное чтение строки даёт другое значение), фантомное чтение (повторный запрос возвращает другой набор строк), аномалия сериализации (результат параллельных транзакций невозможен ни при каком последовательном порядке). Уровни по стандарту: Read Uncommitted допускает всё; Read Committed запрещает грязное чтение; Repeatable Read — ещё и неповторяющееся; Serializable — все аномалии. В PostgreSQL уровень по умолчанию Read Committed, грязного чтения нет вообще, Repeatable Read основан на снимке и не допускает фантомов, а Serializable реализован через SSI и может завершать транзакции ошибкой сериализации, которые приложение должно повторять. Чем выше уровень, тем меньше аномалий, но больше конфликтов и откатов. Отдельно стоит упомянуть потерянное обновление и способы с ним бороться: атомарный UPDATE, SELECT FOR UPDATE, оптимистичная блокировка.
--- points
- четыре аномалии и их смысл
- четыре уровня и что каждый запрещает
- PostgreSQL: по умолчанию Read Committed
- в PG нет грязного чтения, RR без фантомов (снимок)
- Serializable требует повторов транзакций
- компромисс: изоляция ↔ производительность
:::

::: quiz open q101-8 собес
Что такое индекс, как он устроен и когда не помогает?
--- answer
Индекс — дополнительная структура данных, ускоряющая поиск строк. Чаще всего это B-дерево: сбалансированное дерево отсортированных значений с указателями на строки. Поиск, диапазоны и сортировка по нему работают за O(log n) вместо полного сканирования. Бывают и другие: hash (только равенство), GIN (массивы, jsonb, полнотекстовый поиск), GiST, BRIN. Составной индекс используется по левому префиксу. Покрывающий индекс содержит все нужные колонки, и в таблицу можно не ходить. Цена индекса — замедление вставок и обновлений и место на диске. Не помогает при низкой селективности (условию подходит большая часть таблицы), при функции над колонкой без индекса по выражению, при `LIKE '%...'`, при условии не по левому префиксу составного индекса, на маленьких таблицах. Проверяют через `EXPLAIN ANALYZE`.
--- points
- ускоряет поиск, B-дерево, O(log n)
- другие типы: hash, GIN, GiST
- составной индекс и левый префикс
- цена: медленнее запись, место
- когда не помогает: селективность, функции, LIKE '%…'
- EXPLAIN ANALYZE
:::
