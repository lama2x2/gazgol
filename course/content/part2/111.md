%% 11 | Конкурентность на практике
# 11.1 context: отмена, таймауты, errgroup

## Зачем нужен context:
Пользователь открыл страницу объявления. Хендлер параллельно идёт в БД, в сервис отзывов и в сервис рекомендаций. Пользователь закрыл вкладку: всю эту работу нужно остановить. Сервис рекомендаций тормозит: через 300 мс надо перестать ждать. Обе задачи решает `context.Context`. Это сигнал отмены и дедлайн, которые передаются по всей цепочке вызовов.
```go
type Context interface {
    Done() <-chan struct{}       // закрывается при отмене — можно ждать в select
    Err() error                  // nil, пока не отменён; потом Canceled или DeadlineExceeded
    Deadline() (time.Time, bool)
    Value(key any) any
}
```

## Дерево контекстов:
```go
ctx := context.Background()                                  // корень: в main, тестах, на старте
ctx, cancel := context.WithCancel(parent)                    // отменить вручную
ctx, cancel := context.WithTimeout(parent, 300*time.Millisecond)
ctx, cancel := context.WithDeadline(parent, time.Now().Add(time.Second))
ctx = context.WithValue(parent, key, value)                  // данные запроса
ctx = context.WithoutCancel(parent)                          // те же значения, но без отмены родителя (1.21+)
defer cancel()                                               // ВСЕГДА: иначе утечёт таймер и ресурсы
```
Каждый `With...` создаёт **дочерний** контекст. Отмена родителя отменяет всех потомков, а отмена ребёнка на родителя не влияет. Дедлайн ребёнка не может быть позже родительского: возьмётся ближайший.

::: quiz output q111-1 собес
Отмена по дереву:
```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

func main() {
	parent, cancel := context.WithCancel(context.Background())
	child, cancelChild := context.WithTimeout(parent, time.Hour)

	<-child.Done()
	fmt.Println(child.Err())
	fmt.Println(errors.Is(child.Err(), context.Canceled))
}
```
--- answer
context canceled
true
--- why
Таймаут ребёнка — час, но родителя отменили, и отмена прошла вниз по дереву сразу. Причина — `Canceled`, а не `DeadlineExceeded`.

## Правила работы с context:
- `ctx` — **первый параметр** функции: `func (s *Store) Get(ctx context.Context, id int64)`
- не храни `ctx` в структуре: он живёт столько же, сколько запрос, а структура — дольше
- никогда не передавай `nil`. Если не знаешь, какой передать, — `context.TODO()`
- в долгих циклах и при ожидании проверяй `ctx.Done()` через `select`
- в HTTP-хендлере бери `r.Context()`: он отменится, если клиент отключится
- `WithValue` — только для данных *запроса* (request id, пользователь, trace id), а не для передачи зависимостей и обычных параметров. Ключ — свой неэкспортируемый тип

Кто первым?
```go
package main

import (
	"context"
	"fmt"
	"time"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 50*time.Millisecond)
	defer cancel()

		fmt.Println("отмена:", ctx.Err())

```
--- answer
отмена: context deadline exceeded
--- why
`select` ждёт первый готовый канал. Через 50 мс контекст закрывает `Done()`, и `Err()` возвращает `DeadlineExceeded`. Это базовый шаблон любой операции с таймаутом.

## Утечка горутин — главная ошибка с таймаутами:
```go
func fetch(ctx context.Context) (string, error) {
    ch := make(chan string)          // небуферизованный!
    go func() {
        ch <- slowCall()             // если никто не читает — висит вечно
    }()
    select {
    case res := <-ch:
        return res, nil
    case <-ctx.Done():
        return "", ctx.Err()         // ушли, а горутина осталась ждать
    }
}
```
Каждый таймаут оставляет одну навсегда заблокированную горутину. За сутки их миллионы, и память кончается. Лечение: `make(chan string, 1)`, тогда отправка не блокируется, или передать `ctx` в `slowCall`, чтобы она сама прерывалась.

::: quiz bug q111-4 собес
Сервис постепенно съедает память. В профиле — сотни тысяч горутин в одной и той же строке. Какая это строка?
```go
func (c *Client) Price(ctx context.Context, id int) (int, error) {
	res := make(chan int)
	go func() { res <- c.slowPriceAPI(id) }()   // (A)
	select {
	case p := <-res:                              // (B)
		return p, nil
	case <-ctx.Done():                            // (C)
		return 0, ctx.Err()
	}
}
```
- [x] (A): после таймаута никто не читает `res`, и отправка блокируется навсегда
- [ ] (B): чтение из канала держит горутину
- [ ] (C): `ctx.Done()` создаёт новую горутину при каждом вызове
- [ ] утечки нет, сборщик мусора уберёт горутину вместе с каналом
--- why
Сборщик мусора не убивает заблокированные горутины. Канал с буфером 1 позволит отправить результат и завершиться, даже если его уже никто не ждёт.
:::

## errgroup — запустить пачку и дождаться:
`golang.org/x/sync/errgroup` — стандарт де-факто для «параллельно сходить в три места»:
```go
g, ctx := errgroup.WithContext(r.Context())
var ad Ad
var reviews []Review
g.Go(func() error {
    var err error
    ad, err = store.Get(ctx, id)
    return err
})
g.Go(func() error {
    var err error
    reviews, err = reviewsClient.List(ctx, id)
    return err
})
if err := g.Wait(); err != nil {   // ждёт всех; возвращает первую ошибку
    return err                     // и при первой ошибке отменяет ctx для остальных
}
```
`g.SetLimit(n)` ограничивает число одновременных горутин. В домашке ты напишешь свою мини-версию errgroup: на собесах это частая задача.

* `Sleep` — подождать, но проснуться раньше при отмене {TestSleep}
+ `t := time.NewTimer(d)`, `defer t.Stop()`, затем `select` между `t.C` (вернуть nil) и `ctx.Done()` (вернуть `ctx.Err()`).
! `time.Sleep` здесь не подойдёт: его нельзя прервать.
* `FirstSuccess` — гонка запросов: первый успешный ответ, остальных отменить {TestFirstSuccess}
+ Дочерний `ctx, cancel := context.WithCancel(ctx)` и `defer cancel()`. Канал результатов с буфером `len(fns)`. Каждую функцию запусти в горутине. Читай результаты: первый без ошибки — вернуть сразу (`defer cancel()` остановит остальных). Ошибки копи и, если успехов не было, верни `errors.Join(errs...)`.
! Без буфера проигравшие горутины зависнут на отправке. Тест проверяет, что остальные функции увидели отмену.
* `Group` — своя errgroup {TestGroup}
+ Внутри: `sync.WaitGroup`, `sync.Once` для первой ошибки, `cancel` от `context.WithCancel`. `Go` делает `wg.Add(1)` и запускает горутину, при ошибке через `once.Do` сохраняет её и вызывает `cancel`. `Wait` делает `wg.Wait()`, затем `cancel()`, и возвращает ошибку.
! Ошибку записывают из разных горутин: без `Once` или мьютекса это гонка, а тест запускается с `-race`.
* `ProcessAll` — обработать всё, но не больше limit одновременно {TestProcessAll}
+ Семафор — буферизованный канал `sem := make(chan struct{}, limit)`: `sem <- struct{}{}` перед запуском, `<-sem` после работы. Используй свою `Group` или `WaitGroup` и первую ошибку. Перед запуском новой задачи проверь, не отменён ли `ctx`.
! После первой ошибки новые задачи запускаться не должны. Тест считает, сколько их стартовало.
* `RetryCtx ★` — повторы с экспоненциальной паузой, прерываемой контекстом {TestRetryCtx}
+ Паузы `base, 2·base, 4·base…` между попытками. Жди через свой `Sleep(ctx, d)`: если контекст отменён, сразу верни `ctx.Err()`, обернув вместе с последней ошибкой.
! После последней попытки не нужно ждать. Тест проверяет и число вызовов, и общее время.

## Вопросы с собеседования по уроку:
::: quiz open q111-5 собес
Что такое context в Go и зачем он нужен?
--- answer
`context.Context` переносит через цепочку вызовов сигнал отмены, дедлайн и значения, привязанные к запросу. Он нужен, чтобы прекращать ненужную работу (клиент ушёл, истёк таймаут, упала соседняя задача) во всех горутинах и запросах к БД и сетевых вызовах, порождённых одной операцией. Контексты образуют дерево: отмена родителя отменяет всех потомков. Функции принимают ctx первым параметром и проверяют `ctx.Done()` в select или передают его дальше (в `database/sql`, `http.NewRequestWithContext`). `ctx.Err()` говорит о причине: Canceled или DeadlineExceeded. `cancel` нужно вызывать всегда. Контекст не хранят в структурах, nil не передают, через WithValue передают только request-scoped данные.
--- points
- отмена, дедлайн и значения запроса
- дерево: отмена идёт вниз
- ctx первым параметром, проверка Done в select
- Err: Canceled / DeadlineExceeded
- всегда вызывать cancel
- не хранить в структуре, WithValue — только для данных запроса
:::

::: quiz open q111-6 собес
Какие виды контекста знаешь?
--- answer
Корневые: `context.Background()` (main, тесты, инициализация) и `context.TODO()` (заглушка, когда ещё не решили, какой нужен). Производные: `WithCancel` (ручная отмена), `WithTimeout` и `WithDeadline` (автоматическая отмена по времени), `WithValue` (значение по ключу), `WithCancelCause` (отмена с указанием причины, `context.Cause`), `WithoutCancel` (сохраняет значения, но не наследует отмену — для фоновой работы после ответа), `AfterFunc` (вызвать функцию при отмене). В HTTP-сервере у каждого запроса свой контекст `r.Context()`.
--- points
- Background и TODO
- WithCancel
- WithTimeout / WithDeadline
- WithValue
- WithCancelCause, WithoutCancel, AfterFunc
:::
