# 9.1 HTTP и REST на net/http

## HTTP за пять минут:
HTTP — текстовый протокол «запрос → ответ». Запрос состоит из строки с методом и путём, заголовков и (не всегда) тела:
```text
POST /ads HTTP/1.1
Host: api.barakholka.ru
Content-Type: application/json
Authorization: Bearer 7f3a…

{"title": "Велосипед", "price": 5000}
```
Ответ: статус, заголовки, тело.
```text
HTTP/1.1 201 Created
Content-Type: application/json
Location: /ads/42

{"id": 42, "title": "Велосипед", "price": 5000}
```

## Методы и их свойства:
| Метод | Для чего | Безопасный | Идемпотентный |
|---|---|---|---|
| GET | получить | да | да |
| POST | создать, выполнить действие | нет | **нет** |
| PUT | заменить целиком | нет | да |
| PATCH | изменить часть | нет | не обязательно |
| DELETE | удалить | нет | да |

- **безопасный** — не меняет состояние сервера
- **идемпотентный** — повтор запроса даёт тот же результат, что один запрос. `DELETE /ads/42` дважды — объявления нет в обоих случаях. `POST /ads` дважды — два объявления. Это важно для повторов при сетевых ошибках: идемпотентное можно смело повторять

::: quiz choice q91-1 собес
Какие методы идемпотентны? Выбери все.

--- why
Повтор `PUT /ads/42` с тем же телом оставит объявление в том же состоянии, повтор `DELETE` тоже. Повтор `POST` создаст дубль. Поэтому для POST вводят ключи идемпотентности (`Idempotency-Key`) — это тема части 3.
:::

## Статус-коды, которые нужно знать наизусть:
| Код | Когда |
|---|---|
| 200 OK | всё хорошо, в теле результат |
| 201 Created | ресурс создан; в `Location` — его адрес |
| 204 No Content | всё хорошо, тела нет (удаление) |
| 400 Bad Request | запрос кривой: невалидный JSON, id не число |
| 401 Unauthorized | не представился: нет токена или он невалиден |
| 403 Forbidden | представился, но нельзя: чужое объявление |
| 404 Not Found | ресурса нет |
| 409 Conflict | конфликт состояния: уже продано, дубль |
| 422 Unprocessable Entity | JSON нормальный, но данные не проходят валидацию |
| 429 Too Many Requests | превышен лимит запросов |
| 500 Internal Server Error | упали мы |
| 502 / 503 / 504 | проблема на пути: плохой ответ апстрима / сервис недоступен / таймаут апстрима |

Правило: **4xx — виноват клиент, 5xx — виноват сервер**. Клиент 4xx не повторяет, 503 и 504 повторяет.

## REST:
REST — стиль API, где всё строится вокруг **ресурсов**:
- адреса — существительные: `/ads`, `/ads/42`, `/users/7/ads`. Не `/getAds` и не `/deleteAd?id=42`
- действие выражает метод: `GET /ads`, `POST /ads`, `DELETE /ads/42`
- сервер не хранит состояние между запросами: всё нужное, включая токен, приходит в запросе
- фильтры и пагинация — в query: `GET /ads?city=kazan&max_price=10000&limit=20&offset=40`
- версия в пути: `/v1/ads`, чтобы менять API, не ломая старых клиентов

## net/http: Handler — это интерфейс
```go
type Handler interface {
    ServeHTTP(w http.ResponseWriter, r *http.Request)
}
```
Любой тип с этим методом может обрабатывать запросы. `http.HandlerFunc` превращает обычную функцию в Handler. Отсюда и middleware в следующем уроке.

## Роутинг (Go 1.22+):
```go
mux := http.NewServeMux()
mux.HandleFunc("GET /ads", api.listAds)
mux.HandleFunc("GET /ads/{id}", api.getAd)     // {id} — параметр пути
mux.HandleFunc("POST /ads", api.createAd)
mux.HandleFunc("DELETE /ads/{id}", api.deleteAd)

func (a *API) getAd(w http.ResponseWriter, r *http.Request) {
    id, err := strconv.Atoi(r.PathValue("id"))   // параметр пути
    maxPrice := r.URL.Query().Get("max_price")   // параметр запроса, "" если нет
    ...
}
```
Если путь есть, а метода нет, mux сам ответит 405 Method Not Allowed. До 1.22 для такого брали chi или gorilla/mux, сейчас стандартной библиотеки хватает.

## Ответ: порядок важен
```go
w.Header().Set("Content-Type", "application/json") // 1. заголовки
w.WriteHeader(http.StatusCreated)                  // 2. статус
json.NewEncoder(w).Encode(ad)                      // 3. тело
```
После `WriteHeader` (или первого `Write`, который неявно отправляет 200) заголовки уже ушли клиенту, и менять их бесполезно.

::: quiz bug q91-2
Клиент получает ответ без `Content-Type: application/json`. Почему?
```go
func (a *API) createAd(w http.ResponseWriter, r *http.Request) {

    w.WriteHeader(http.StatusCreated)
    w.Header().Set("Content-Type", "application/json")

```
- [ ] `json.Encoder` перезаписывает заголовки
- [x] заголовок выставлен после `WriteHeader`: к этому моменту заголовки уже отправлены
- [ ] для статуса 201 заголовки не передаются
- [ ] нужно писать `w.Header().Add`, а не `Set`
--- why
`WriteHeader` отправляет строку статуса и все накопленные заголовки. Всё, что добавлено после, игнорируется. Сначала заголовки, потом статус, потом тело.

## JSON и теги структур:
```go
type Ad struct {
    ID        int       `json:"id"`
    Title     string    `json:"title"`
    Price     int       `json:"price,omitempty"` // не выводить, если 0
    CreatedAt time.Time `json:"created_at"`      // RFC 3339: "2026-10-11T18:00:00Z"
    OwnerHash string    `json:"-"`               // никогда не выводить
    note      string                            // строчная буква — json её не видит
}
```
- в JSON попадают только **экспортированные** поля
- чтение тела запроса:
```go
r.Body = http.MaxBytesReader(w, r.Body, 1<<20) // не больше 1 МБ — защита от огромных тел
dec := json.NewDecoder(r.Body)
dec.DisallowUnknownFields()                   // опечатка в поле → ошибка, а не тишина
var in CreateAdRequest
if err := dec.Decode(&in); err != nil {
    writeError(w, http.StatusBadRequest, "невалидный JSON")
    return
}
```
- для входа и выхода часто заводят **отдельные структуры** (`CreateAdRequest`, `AdResponse`), чтобы клиент не мог прислать `id` или `owner_id`

::: quiz output q91-3 собес
Что окажется в JSON?
```go
package main

import (
	"encoding/json"
	"fmt"
)

type Ad struct {
	ID     int      `json:"id"`
	Title  string   `json:"title"`
	Price  int      `json:"price,omitempty"`
	Tags   []string `json:"tags"`
	Owner  string   `json:"-"`
	secret string
}

func main() {
	b, _ := json.Marshal(Ad{ID: 1, Title: "Шкаф", Owner: "gosha", secret: "x"})
	fmt.Println(string(b))
}
```
--- answer
{"id":1,"title":"Шкаф","tags":null}
--- why
`Price` равен 0 и помечен `omitempty`, поэтому пропал. `Owner` скрыт тегом `-`, `secret` не экспортирован. `Tags` — nil-слайс, а он кодируется как `null`, не `[]`. Фронтенд, который ждёт массив, на этом упадёт. Поэтому для пустого списка инициализируй `[]string{}`.
:::

## Клиент: всегда с таймаутом
```go
client := &http.Client{Timeout: 5 * time.Second} // у http.DefaultClient таймаута НЕТ
resp, err := client.Get(url)
if err != nil {
    return err
}
defer resp.Body.Close()                // иначе утекут соединения
if resp.StatusCode != http.StatusOK {  // 404 и 500 — не ошибки для err!
    return fmt.Errorf("status %d", resp.StatusCode)
}
```

- [ ] через 30 секунд Go сам прервёт запрос

`http.Get` использует `http.DefaultClient`, а у него нет таймаута. Каждый запрос к сервису будет висеть вечно. Всегда создавай свой `http.Client{Timeout: ...}` или передавай контекст с дедлайном.

## Вопросы с собеседования по уроку:
::: quiz design q91-5
Спроектируй REST API для объявлений Барахолки: список с фильтрами и пагинацией, просмотр, создание, редактирование, снятие с продажи, «мои объявления». Напиши методы, пути, ключевые статусы.
--- answer
```text
GET    /v1/ads?city=kazan&min_price=0&max_price=10000&q=велосипед&limit=20&cursor=…   200
GET    /v1/ads/{id}                                  200 / 404
POST   /v1/ads                                       201 + Location / 400 / 401 / 422
PATCH  /v1/ads/{id}         (частичное изменение)    200 / 401 / 403 / 404 / 409 / 422
POST   /v1/ads/{id}/sold    (действие над ресурсом)  200 / 403 / 409 (уже продано)
DELETE /v1/ads/{id}                                  204 / 403 / 404
GET    /v1/users/me/ads                              200 / 401
```
Решения: версия в пути. Фильтры в query. Курсорная пагинация (`cursor` + `limit`, в ответе `next_cursor`) устойчивее offset к вставкам и быстрее на больших таблицах. Ошибки в едином формате `{"error": {"code": "...", "message": "...", "fields": {...}}}`. Владелец берётся из токена, а не из тела. Действие «продано» — отдельный подресурс, потому что это переход состояния с правилами, а не просто правка поля.
--- points
- ресурсы во множественном числе, методы как глаголы
- фильтры и пагинация в query, limit с ограничением сверху
- правильные статусы: 201 + Location, 204, 401 и 403, 404, 409, 422
- владелец из токена, а не из тела запроса
- единый формат ошибок
- версионирование API
:::

::: quiz open q91-6 собес
Что происходит, когда вводишь адрес сайта в браузере и нажимаешь Enter?
--- answer
1. Браузер разбирает URL и ищет IP домена: свой кэш, кэш ОС, файл hosts, затем DNS-резолвер провайдера, который при необходимости опрашивает корневые серверы, серверы зоны и авторитетный сервер домена.
2. Устанавливается TCP-соединение с IP на порт 443 (тройное рукопожатие SYN, SYN-ACK, ACK). Для HTTP/3 — QUIC поверх UDP.
3. TLS-рукопожатие: согласование версии и шифров, сервер присылает сертификат, браузер проверяет цепочку доверия и имя, стороны получают общий сеансовый ключ.
4. Браузер отправляет HTTP-запрос: `GET /` с заголовками (Host, cookies, Accept…).
5. Запрос проходит балансировщик или reverse proxy (nginx), который передаёт его приложению. Приложение ходит в БД, кэш, другие сервисы и формирует ответ.
6. Ответ (статус, заголовки, HTML) возвращается. Браузер парсит HTML, догружает CSS, JS и картинки (часто из CDN, по тому же соединению), строит DOM и рисует страницу.
--- points
- DNS-резолвинг и кэши
- TCP-соединение (рукопожатие)
- TLS: сертификат, ключи
- HTTP-запрос и ответ
- балансировщик / reverse proxy → приложение → БД
- рендер страницы и догрузка ресурсов
:::

::: quiz open q91-7 собес
Чем PUT отличается от PATCH, а POST — от PUT?
--- answer
PUT заменяет ресурс целиком по известному адресу: что не прислали — сбросится. Он идемпотентен. PATCH меняет только переданные поля, и его идемпотентность зависит от семантики (например, «увеличить счётчик» — не идемпотентно). POST создаёт ресурс, адрес которого назначает сервер (`POST /ads` → `/ads/42`), или выполняет действие. Он не идемпотентен: повтор создаст дубль. PUT тоже может создавать, но клиент сам знает адрес (`PUT /users/7/avatar`).
--- points
- PUT — замена целиком, идемпотентен
- PATCH — частичное изменение
- POST — создание с адресом от сервера, не идемпотентен
- повтор POST создаёт дубль
:::
