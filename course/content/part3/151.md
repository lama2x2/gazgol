# 15.1 PostgreSQL изнутри: MVCC, индексы, планы, блокировки

## MVCC — читатели не блокируют писателей:
PostgreSQL не перезаписывает строку при UPDATE. Он создаёт **новую версию** строки, а старую помечает «устаревшей». У каждой версии есть служебные поля:
- `xmin` — транзакция, создавшая версию
- `xmax` — транзакция, удалившая или заменившая её

Каждая транзакция (или запрос, на Read Committed) работает со **снимком**: видит версии, закоммиченные к моменту снимка. Поэтому:
- чтение **не блокирует** запись, а запись — чтение. Это главное преимущество MVCC
- две записи в одну строку всё-таки конфликтуют: вторая ждёт, пока первая закоммитится или откатится

## VACUUM и раздувание:
Старые версии строк (*dead tuples*) остаются в таблице, пока их не уберёт **VACUUM**. Обычно его запускает autovacuum. Если мусор не успевают убирать, таблица и индексы раздуваются (*bloat*): места больше, запросы медленнее.

**Долгие транзакции — враг VACUUM:** пока открыта транзакция, которая *может* увидеть старые версии, их нельзя удалить. Забытая `BEGIN` в psql или аналитический запрос на час — и вся база копит мусор.

**WAL** (write-ahead log): каждое изменение сначала пишется в журнал и сбрасывается на диск (`fsync`), и только потом считается закоммиченным. На WAL держатся долговечность (восстановление после сбоя) и репликация (реплики проигрывают WAL мастера).

## Индексы глубже:
| Тип | Для чего |
|---|---|
| **B-tree** (по умолчанию) | `=`, `<`, `>`, `BETWEEN`, `ORDER BY`, `LIKE 'abc%'` |
| Hash | только `=` |
| **GIN** | «содержит»: `jsonb`, массивы, полнотекстовый поиск |
| GiST | геоданные, диапазоны, «ближайшие» |
| BRIN | огромные таблицы, где значение растёт вместе с физическим порядком (время событий) — крошечный индекс |

Приёмы:
```sql
-- частичный: индексируем только то, что ищем
CREATE INDEX ads_active_cat_price ON ads (category, price) WHERE status = 'active';

-- покрывающий: Index Only Scan — в таблицу ходить не нужно
CREATE INDEX ads_cat_price_inc ON ads (category, price) INCLUDE (title);

-- по выражению: для WHERE lower(email) = $1
CREATE INDEX users_email_lower ON users (lower(email));

-- на живой таблице — без блокировки записи
CREATE INDEX CONCURRENTLY ...;
```
Обычный `CREATE INDEX` блокирует запись в таблицу на всё время построения. На проде это авария. Поэтому в миграциях — только `CONCURRENTLY`.

`@>` — оператор «содержит», это работа инвертированного индекса GIN. B-tree умеет только сравнивать значения целиком.
:::

## EXPLAIN ANALYZE:
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM ads WHERE category = 'мебель' AND status = 'active' ORDER BY price LIMIT 20;
```
```text
Limit  (cost=0.43..12.1 rows=20) (actual time=0.05..0.21 rows=20 loops=1)
  ->  Index Scan using ads_active_cat_price on ads  (actual rows=20 loops=1)
        Index Cond: (category = 'мебель')
Planning Time: 0.1 ms
Execution Time: 0.3 ms
```
| Узел | Что значит |
|---|---|
| Seq Scan | полный проход по таблице |
| Index Scan | по индексу, потом за строкой в таблицу |
| Index Only Scan | всё нашлось в индексе |
| Bitmap Heap Scan | собрали много адресов по индексу и читаем страницы пачкой |
| Nested Loop | для каждой строки слева ищем справа; хорошо, если слева мало строк, а справа есть индекс |
| Hash Join | строим хеш-таблицу по меньшей стороне; большие соединения по равенству |
| Merge Join | обе стороны уже отсортированы |
| Sort | сортировка в памяти или на диске (`external merge` — плохо) |

Главное, что надо смотреть: **оценка `rows` против `actual rows`**. Если планировщик ждал 10 строк, а пришло 100 000, у него устаревшая статистика (`ANALYZE ads`), и план выбран неправильно.

::: quiz choice q151-4
Индекс по `category` есть, а EXPLAIN показывает Seq Scan. Какие причины возможны? Выбери все.
- [x] условию подходит большая часть таблицы, и читать её целиком дешевле, чем прыгать по индексу
- [x] таблица маленькая
- [x] статистика устарела, и планировщик ошибается в оценке числа строк
- [ ] PostgreSQL не использует индексы в запросах с LIMIT
- [x] в условии функция над колонкой: `WHERE lower(category) = ...`
--- why
Планировщик выбирает по стоимости, а не по наличию индекса. Seq Scan не всегда плох: для 80% таблицы он быстрее. Тревожно, когда в Seq Scan уходит запрос, возвращающий единицы строк из миллионов.
:::

## Блокировки строк:
```sql
SELECT * FROM ads WHERE id = $1 FOR UPDATE;  -- заблокировать строку до конца транзакции
SELECT ... FOR UPDATE NOWAIT;                -- занято — сразу ошибка, без ожидания
SELECT ... FOR UPDATE SKIP LOCKED;           -- пропустить занятые строки
```
**Очередь задач на PostgreSQL** — классика собесов:
```sql
UPDATE jobs SET status = 'running', worker = $1, started_at = now()
WHERE id IN (
    SELECT id FROM jobs
    WHERE status = 'pending'
    ORDER BY id
    LIMIT 10
    FOR UPDATE SKIP LOCKED   -- воркеры не мешают друг другу и не берут одно и то же
)
RETURNING id, payload;
```
**Дедлоки в БД:** две транзакции обновляют строки A и B в разном порядке. PostgreSQL сам обнаруживает цикл и убивает одну транзакцию с ошибкой `40P01`. Её нужно повторить, а порядок обновлений — сделать единым (например, по id).

**Оптимистичная блокировка** — без удержания замков. Колонка `version`, и обновляем «только если никто не успел раньше»:
```sql
UPDATE ads SET price = $1, version = version + 1 WHERE id = $2 AND version = $3;
-- 0 строк → кто-то изменил раньше нас → 409 Conflict, пусть клиент перечитает
```

## Пагинация: OFFSET против keyset
```sql
-- OFFSET: база читает 100 020 строк и выбрасывает 100 000
SELECT * FROM ads ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 100000;

-- keyset (seek): продолжаем с последнего увиденного
SELECT * FROM ads
WHERE (created_at, id) < ($1, $2)          -- курсор = значения последней строки прошлой страницы
ORDER BY created_at DESC, id DESC LIMIT 20;
```
Keyset работает одинаково быстро на любой странице (по индексу `(created_at, id)`), и записи не «прыгают» между страницами, когда добавляются новые. Минус: нельзя перейти сразу на страницу 500, только вперёд или назад. Для ленты объявлений это нормально.

::: quiz choice q151-5 собес
Почему `LIMIT 20 OFFSET 100000` медленный и как это исправить?
- [ ] PostgreSQL не умеет OFFSET больше 65535
- [x] база всё равно читает и отбрасывает первые 100 000 строк; исправление — keyset-пагинация по индексу
- [ ] нужен индекс по OFFSET
- [ ] надо увеличить `work_mem`
--- why
Стоимость OFFSET растёт линейно с номером страницы. Keyset-пагинация идёт по индексу сразу с нужного места. Бонус: при вставке новых записей не появляются дубли и пропуски между страницами.
:::

## Вопросы с собеседования по уроку:
::: quiz open q151-6 собес
Что такое MVCC и VACUUM в PostgreSQL?
--- answer
MVCC (многоверсионное управление конкурентным доступом): при UPDATE и DELETE строка не перезаписывается, создаётся новая версия, а у старой проставляется xmax. У версий есть xmin/xmax (идентификаторы транзакций), и каждая транзакция видит версии согласно своему снимку. В результате читатели не блокируют писателей и наоборот, а конфликтуют только одновременные записи одной строки. Цена — мёртвые версии строк. VACUUM помечает их место как свободное для повторного использования, обновляет visibility map (нужна для Index Only Scan) и замораживает старые xid, чтобы не случился wraparound. Autovacuum запускает его автоматически по порогам. Долгие транзакции мешают VACUUM удалять версии и приводят к раздуванию таблиц. VACUUM FULL переписывает таблицу целиком под эксклюзивной блокировкой.
--- points
- новая версия строки при UPDATE, xmin/xmax
- снимки: читатели не блокируют писателей
- мёртвые версии и VACUUM / autovacuum
- раздувание (bloat) и вред долгих транзакций
- visibility map, wraparound
:::

::: quiz open q151-7 собес
Запрос стал медленным. Как будешь разбираться?
--- answer
Сначала найти и подтвердить: pg_stat_statements (топ по суммарному и среднему времени), логи медленных запросов, APM-трейсы. Затем `EXPLAIN (ANALYZE, BUFFERS)` на реальных параметрах. Смотрю на тип сканирования (Seq Scan по большой таблице при малом результате), на расхождение оценки rows и actual rows (устаревшая статистика → ANALYZE), сортировки на диск, тип соединений и петли Nested Loop с большим loops, объём прочитанных буферов. Типичные исправления: подходящий составной, частичный, покрывающий индекс или индекс по выражению (создавать CONCURRENTLY); переписать запрос (убрать функцию над индексируемой колонкой, OFFSET → keyset, N+1 → JOIN или пакет); обновить статистику; уменьшить выборку колонок; материализовать тяжёлые агрегаты; проверить блокировки (pg_locks) и раздувание. После изменения — повторный EXPLAIN и метрики.
--- points
- найти: pg_stat_statements, логи, трейсы
- EXPLAIN ANALYZE BUFFERS на реальных данных
- оценка rows против actual: статистика
- индексы: составной, частичный, покрывающий, CONCURRENTLY
- переписать запрос: функции, OFFSET, N+1
- проверить блокировки и раздувание, измерить после
:::

::: quiz open q151-8 собес
Как сделать очередь задач на PostgreSQL, чтобы воркеры не брали одну задачу дважды?
--- answer
Таблица jobs со статусом (pending/running/done/failed), временем и счётчиком попыток. Воркер атомарно захватывает пачку одним запросом `UPDATE jobs SET status='running', locked_by=$1, locked_at=now() WHERE id IN (SELECT id FROM jobs WHERE status='pending' AND run_at <= now() ORDER BY id LIMIT $2 FOR UPDATE SKIP LOCKED) RETURNING ...`. FOR UPDATE блокирует выбранные строки, а SKIP LOCKED заставляет другие воркеры пропускать их вместо ожидания. Поэтому воркеры не конфликтуют и не берут одно и то же. После выполнения статус меняется на done. При ошибке — повтор с увеличением run_at (backoff) и лимитом попыток. Зависшие задачи (воркер умер) возвращаются в pending по таймауту locked_at. Нужен индекс по (status, run_at). Альтернатива при больших объёмах — брокер сообщений (Kafka/RabbitMQ), но очередь в PG проста и транзакционно согласована с данными.
--- points
- таблица со статусами и попытками
- атомарный захват UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED) RETURNING
- SKIP LOCKED — воркеры не ждут друг друга
- ретраи с backoff и лимитом
- возврат зависших по таймауту
- индекс; сравнение с брокером
:::
