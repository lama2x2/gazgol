# 18.2 Разборы system design и подготовка к собеседованию

## Разбор: Барахолка на 10 миллионов пользователей
Пройдём по плану из 18.1 на знакомой системе.

**Требования.** Публикация объявлений с фото, лента с фильтрами (город, категория, цена), полнотекстовый поиск, карточка объявления, чат покупателя с продавцом, избранное, уведомления. Нефункциональные: 10 млн активных пользователей в месяц, чтение ≫ запись, карточка открывается за < 200 мс (p99), доступность 99.9%, лента может отставать на несколько секунд (eventual consistency), деньги и сделки — строгая согласованность.

**Оценки.** Просмотры ~10 000 RPS в пике (18.1), публикации ~1 млн в день ≈ 12 RPS в среднем (×5 в пике — 60), фото ~1.5 ТБ в день, сообщения в чате ~20 млн в день ≈ 230 RPS.

**Схема:**
```text
клиенты ─► CDN (фото, статика)
        └► L7-балансировщик / API-шлюз (auth, rate limit)
              ├─► ads-service ──► PostgreSQL (мастер + реплики) ◄─ кэш Redis
              │        └─ outbox ─► Kafka ─► search-indexer ─► OpenSearch
              ├─► search-service ──► OpenSearch
              ├─► media-service ──► S3 (presigned upload) ─► Kafka ─► resize-workers
              ├─► chat-service ──► WebSocket-шлюзы ◄─► Redis pub/sub, Cassandra (история)
              └─► notification-service ◄─ Kafka (AdSold, NewMessage…) ─► push / email
```

**Углубление:**
- **фото**: клиент получает presigned URL и грузит файл напрямую в S3, минуя наши серверы. Событие о загрузке → воркеры делают превью → CDN
- **лента и поиск**: читаются из OpenSearch, который наполняется событиями из outbox. Отставание в секунды допустимо. PostgreSQL — источник истины для карточки и сделок
- **карточка**: Redis с cache-aside и singleflight, горячие объявления ещё и в локальном кэше
- **чат**: долгие WebSocket-соединения на отдельных шлюзах. Чтобы доставить сообщение получателю на другом шлюзе — Redis pub/sub или Kafka. История — в хранилище, оптимизированном под запись (Cassandra или партиционированный PostgreSQL)
- **отказы**: stateless-сервисы в нескольких экземплярах, реплики БД с автоматическим failover, таймауты, circuit breaker к поиску (фолбэк — простая лента из PostgreSQL)

::: quiz design q182-1 собес
Спроектируй сервис коротких ссылок (как bit.ly): создание короткой ссылки и редирект. 100 млн новых ссылок в месяц, чтений в 100 раз больше.
--- answer
**Требования:** POST создаёт короткий код для длинного URL (опционально — свой алиас и срок жизни), GET /{code} отвечает 301/302 на оригинал. Редирект быстрый (< 50 мс), высокая доступность, ссылки живут годами.

**Оценки:** 10⁸ / (30·10⁵) ≈ 40 записей в секунду, чтения ≈ 4 000 RPS (пик ~10–20 тыс.). Хранение: ~500 байт × 10⁸ × 12 × 5 лет ≈ 3 ТБ. Длина кода: 62⁷ ≈ 3.5·10¹², 7 символов base62 хватит.

**Генерация кода:** уникальный 64-битный id (Snowflake или диапазоны id, которые каждый инстанс берёт у счётчика пачками) → base62. Хеш URL с усечением — риск коллизий, нужна проверка. Случайный код — проверка уникальности при вставке.

**Хранилище:** key-value по коду (PostgreSQL с индексом по коду или Cassandra/DynamoDB), шардинг по коду при росте.

**Чтение:** Redis-кэш горячих кодов (cache-aside), CDN или edge-кэш для редиректов. 301 кэшируется браузером, но мешает аналитике, 302 — наоборот.

**Аналитика переходов:** асинхронно — событие в Kafka → ClickHouse, чтобы не замедлять редирект.

**Прочее:** rate limiting на создание, проверка URL на вредоносность, TTL, удаление просроченных.
--- points
- требования и выбор 301/302
- оценки RPS и объёма, длина кода
- генерация уникального кода без коллизий (id → base62)
- хранилище key-value и шардинг по коду
- кэш и CDN для чтения
- аналитика асинхронно, rate limiting
:::

::: quiz design q182-2
Спроектируй распределённый rate limiter: 100 запросов в минуту на пользователя, у API 50 инстансов.
--- answer
Счётчики должны быть общими для всех инстансов, поэтому храним их в Redis. Алгоритм — token bucket или скользящее окно. Чтобы проверка и списание были атомарными, — Lua-скрипт в Redis (или `INCR` + `EXPIRE` для фиксированного окна). Ключ — `rl:{user_id}`, TTL по размеру окна. Ответ при превышении — 429 с заголовками `Retry-After` и `X-RateLimit-Remaining`.

Масштаб: Redis Cluster с шардированием по ключу. Чтобы не ходить в Redis на каждый запрос, можно локально держать часть квоты (выдавать инстансам пачки токенов), жертвуя точностью.

Отказ Redis: решение fail-open (пропускать, защищая доступность) или fail-closed (отказывать, защищая бэкенд) — компромисс, который нужно назвать. Плюс локальный лимитер как запасной.

Где ставить: на API-шлюзе, до бизнес-логики. Разные лимиты для разных эндпоинтов и тарифов.
--- points
- общее хранилище счётчиков (Redis)
- алгоритм: token bucket / скользящее окно
- атомарность через Lua
- ответ 429 и заголовки
- масштабирование и локальные квоты
- поведение при отказе Redis
:::

::: quiz design q182-3
Спроектируй уведомления о новых сообщениях в чате Барахолки: пуш на телефон, email, если пользователь не прочитал за 10 минут, без дублей и с учётом настроек пользователя.
--- answer
Сервис чата публикует событие `MessageSent` в Kafka через outbox (ключ — id получателя, чтобы события одного пользователя шли по порядку). Notification-service потребляет события идемпотентно (dedup по message_id) и читает настройки пользователя (кэш). Пуш отправляется сразу через провайдеров (APNs, FCM) с ретраями и backoff. Невалидные токены устройств удаляются.

Email с задержкой: создать отложенную задачу «проверить через 10 минут» (таблица задач с run_at и SKIP LOCKED или отложенная очередь). Если к моменту проверки сообщение прочитано (событие `MessageRead` уже обновило состояние), то не отправлять. Защита от лавины: агрегировать несколько сообщений в одно письмо, лимиты частоты на пользователя. Тихие часы и часовые пояса. Учёт отправленного для идемпотентности. DLQ для упавших. Метрики доставки и открытий.
--- points
- событие через outbox в Kafka, ключ — получатель
- идемпотентный консьюмер и настройки пользователя
- пуш сразу, ретраи, работа с токенами
- отложенная проверка прочтения для email
- агрегация, лимиты, тихие часы
- DLQ и метрики
:::

## Как проходить собеседование:
**Этапы** обычно такие: скрининг с HR → техническое интервью по теории (вопросы из карточек этого курса) → лайвкодинг (алгоритмы и задачи на Go, часто конкурентность) → system design (на middle) → поведенческое интервью → финал с командой.

**На технических секциях:**
- **думай вслух**: интервьюер оценивает рассуждение, а не только ответ. Молчание — худшая стратегия
- уточняй условие, прежде чем писать код: граничные случаи, размеры входа, что делать с ошибками
- начни с простого рабочего решения, потом улучшай и называй сложность
- не знаешь — так и скажи, а потом порассуждай: «точно не помню, но логично, что…». Это ценится больше уверенной ошибки
- на лайвкодинге по Go проверяют идиомы: обработку ошибок, закрытие каналов, `defer`, отсутствие гонок

**Поведенческие вопросы** отвечай по схеме **STAR**: Situation (контекст), Task (твоя задача), Action (что сделал *ты*), Result (измеримый результат и выводы).

::: quiz open q182-4 собес
Расскажи о самой сложной технической задаче, которую ты решал. (Ответь по STAR на примере своего проекта, например платформы жалоб с Telegram-ботом.)
--- answer
Пример структуры (подставь свой проект):

**Situation:** в сервисе жалоб на городские проблемы (FastAPI + PostgreSQL + Telegram-бот) при росте пользователей бот начал терять сообщения и отвечать с задержкой до минуты.

**Task:** мне нужно было найти причину и сделать обработку надёжной, не останавливая сервис.

**Action:** снял метрики и профиль. Выяснил, что обработчик синхронно ходил во внешний API геокодинга внутри цикла приёма апдейтов, а при его таймаутах апдейты копились. Вынес геокодинг в фоновую очередь с ретраями и backoff, добавил таймауты, кэш адресов и идемпотентность по id апдейта, чтобы повторы не создавали дубли жалоб.

**Result:** задержка ответа упала до 1–2 секунд, потерь не стало, а отказы геокодера больше не влияли на приём жалоб. Вывод для себя: внешние вызовы — только с таймаутом и вне критического пути.

Чего ждут: конкретики, твоей личной роли, цифр, рефлексии. Не ждут: «мы всей командой как-то сделали».
--- points
- ситуация с контекстом и масштабом
- задача и твоя роль
- конкретные действия: диагностика, решение, альтернативы
- измеримый результат
- выводы и что сделал бы иначе
:::

::: quiz open q182-5
Какие вопросы стоит задать работодателю в конце собеседования? Назови хотя бы четыре и объясни, что они тебе скажут.
--- answer
- **«Как выглядит первый месяц и через сколько ожидается самостоятельность?»** — есть ли онбординг и реалистичны ли ожидания
- **«Как устроены код-ревью, тесты и деплой? Как часто релизитесь?»** — инженерная культура и CI/CD
- **«Какой стек и в каком состоянии кодовая база? Сколько легаси?»** — чем реально придётся заниматься
- **«Как устроены дежурства и разбор инцидентов?»** — нагрузка, культура постмортемов без поиска виноватых
- **«Как растут разработчики: ревью грейдов, менторство, критерии перехода на middle?»** — перспективы
- **«Какая самая большая техническая проблема у команды сейчас?»** — честный ответ многое говорит о команде
- **«Почему открыта вакансия?»** — рост или текучка

Вопросы показывают интерес и помогают тебе выбрать, а не только быть выбранным.
--- points
- онбординг и ожидания
- инженерная культура: ревью, тесты, релизы
- стек и состояние кода
- дежурства и инциденты
- рост и критерии грейдов
:::

## План подготовки:
1. пройди тренажёры всех трёх частей: где ошибся — перечитай урок
2. перед собеседованием прогони **карточки «Вопросы с собеседований»** в конце каждой части: отвечай вслух, по таймеру, 2–3 минуты на вопрос
3. реши все домашки ★ без подсказок: это уровень лайвкодинга
4. доделай итоговый проект части 2, положи его на GitHub с README — о нём спросят
5. проведи 2–3 пробных собеседования (с другом, с Claude в роли интервьюера) с разбором ошибок
6. на каждом настоящем собеседовании записывай вопросы, которые застали врасплох, и добавляй в свою колоду

::: checklist Готов к middle, если:
- объясняешь устройство слайсов, map, интерфейсов, каналов и планировщика без подсказок
- пишешь конкурентный код без гонок и утечек и находишь их в чужом коде
- проектируешь сервис со слоями, тестами, наблюдаемостью и graceful shutdown
- понимаешь индексы, планы запросов, изоляцию транзакций и блокировки
- знаешь, как сервисы общаются надёжно: таймауты, ретраи, идемпотентность, outbox
- можешь за 45 минут спроектировать систему и обосновать компромиссы
- умеешь профилировать и доказывать оптимизации цифрами
:::
