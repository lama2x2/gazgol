# 16.2 Наблюдаемость: логи, метрики, трейсы, SLO

## Три столпа observability:
Мониторинг отвечает на вопрос «работает ли?», наблюдаемость — на вопрос «*почему* не работает?», даже если такой поломки раньше не было.
| | Что | Когда смотреть |
|---|---|---|
| **метрики** | числа во времени: RPS, ошибки, задержки, память | дашборды и алерты: «что-то не так» |
| **логи** | события с подробностями | разбор конкретного случая |
| **трейсы** | путь одного запроса через все сервисы со временем каждого шага | «где именно тормозит» в микросервисах |

Связывает их **trace id**: он есть в логах, в трейсах и (через exemplars) в метриках. Нашёл всплеск на графике — открыл трейс — нашёл логи этого запроса.

## Метрики Prometheus:
Prometheus сам приходит к сервису (pull) за `/metrics` раз в 15–30 секунд и читает текст:
```text
# HELP http_requests_total Число HTTP-запросов.
# TYPE http_requests_total counter
http_requests_total{method="GET",route="/ads/{id}",status="200"} 1027
http_requests_total{method="GET",route="/ads/{id}",status="404"} 3
```
| Тип | Что это | Пример |
|---|---|---|
| **counter** | только растёт (сбрасывается при рестарте) | запросы, ошибки, байты. Смотрят скорость: `rate(x[5m])` |
| **gauge** | может расти и падать | горутины, соединения в пуле, размер очереди |
| **histogram** | раскладывает наблюдения по корзинам (`le` — «меньше или равно») | задержки. Перцентили на сервере: `histogram_quantile(0.99, ...)` |
| summary | перцентили считаются в самом приложении | редко: их нельзя агрегировать между инстансами |

**Кардинальность** — главная опасность. Каждое уникальное сочетание меток — отдельный временной ряд. Метка `user_id` или сырой путь `/ads/123456` создаёт миллионы рядов и роняет Prometheus. В метки идут только значения из маленького фиксированного множества: метод, *шаблон* маршрута, класс статуса.

::: quiz choice q162-1 собес
Какой тип метрики подходит? Сопоставь правильно — выбери верный вариант.
- [ ] число запросов — gauge, текущее число горутин — counter, задержка — counter
- [x] число запросов — counter, текущее число горутин — gauge, задержка — histogram
- [ ] всё — gauge, так проще
- [ ] число запросов — histogram, горутины — summary, задержка — gauge
--- why
Счётчик событий только растёт, поэтому counter, а из него `rate()` даёт RPS. Горутины — текущее значение, которое колеблется: gauge. Задержки нужны как распределение, чтобы видеть хвосты: histogram.
:::

::: quiz choice q162-2 собес
Разработчик добавил метку `path` с реальным URL (`/ads/91234`) к метрике запросов. Чем это плохо?
- [ ] ничем, так даже подробнее
- [x] взрыв кардинальности: каждый id — новый временной ряд, память и CPU Prometheus растут без предела
- [ ] Prometheus не поддерживает слэши в метках
- [ ] метрики будут считаться медленнее в приложении
--- why
Нужен шаблон маршрута `/ads/{id}`. В Go 1.22+ его даёт `r.Pattern` (с 1.23). Для разбора конкретного запроса существуют логи и трейсы, а не метрики.
:::

## Почему среднее врёт — перцентили:
::: quiz output q162-3 собес
Задержки 10 запросов, мс. Что напечатает?
```go
package main

import (
	"fmt"
	"slices"
)

func main() {
	lat := []int{12, 10, 11, 9, 13, 10, 12, 11, 10, 902}
	sum := 0
	for _, v := range lat {
		sum += v
	}
	slices.Sort(lat)
	fmt.Println("среднее:", sum/len(lat))
	fmt.Println("медиана:", lat[len(lat)/2-1])
	fmt.Println("p90:", lat[len(lat)*9/10-1])
	fmt.Println("максимум:", lat[len(lat)-1])
}
```
--- answer
среднее: 100
медиана: 11
p90: 13
максимум: 902
--- why
Девять пользователей получили ответ за 9–13 мс, а одного продержали почти секунду. Среднее (100 мс) не описывает никого: ни типичный опыт, ни плохой. Поэтому смотрят перцентили: p50 — типичный запрос, p99 — «хвост». И при большом числе запросов хвост достаётся многим: если страница делает 50 запросов к бэкенду, почти каждый пользователь хоть раз попадёт в p99.
:::

## RED и USE:
- **RED** для сервисов: **R**ate (запросы в секунду), **E**rrors (доля ошибок), **D**uration (перцентили задержки). Три графика на каждый эндпоинт — основа любого дашборда
- **USE** для ресурсов (CPU, пул соединений к БД, очередь): **U**tilization (занятость), **S**aturation (сколько ждёт в очереди), **E**rrors
- Go-рантайм отдаёт свои метрики: горутины, GC-паузы, куча (`collectors.NewGoCollector`)

## SLI, SLO, SLA и бюджет ошибок:
- **SLI** — измеряемый показатель: доля успешных запросов, доля запросов быстрее 300 мс
- **SLO** — цель: «99.9% запросов успешны за 30 дней»
- **SLA** — договор с клиентом с последствиями (деньги), обычно мягче SLO
- **бюджет ошибок** = 100% − SLO. При 99.9% за 30 дней это ~43 минуты полной недоступности. Бюджет есть — можно рисковать релизами. Сожгли — замедляемся и чиним надёжность

**Алерты — на симптомы, а не на причины:** «доля ошибок выросла и сжигает бюджет в 10 раз быстрее нормы» (burn rate), а не «CPU 80%». CPU 80% бывает и при нормальной работе, а пользователя волнуют ошибки и задержки.

::: quiz choice q162-4
SLO доступности — 99.9% за 30 дней. Сколько примерно минут полного простоя допускает бюджет ошибок?
- [ ] 4 минуты
- [x] 43 минуты
- [ ] 7 часов
- [ ] 1 минуту в день
--- why
30 × 24 × 60 = 43 200 минут, 0.1% от них — 43.2 минуты. Для 99.99% — 4.3 минуты, для 99% — 7.2 часа. Каждая «девятка» в 10 раз дороже.
:::

## Распределённый трейсинг:
Запрос «купить объявление» проходит API-шлюз → сервис объявлений → сервис платежей → PostgreSQL → Kafka. Трейс — дерево **спанов**, каждый спан — операция со временем начала, длительностью и атрибутами.
- **trace id** один на весь запрос, **span id** — на каждую операцию, у спана есть родитель
- контекст передаётся между сервисами в заголовке W3C **`traceparent`**:
```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                │
             │  trace id (16 байт, 32 hex)      span id (8 байт) флаги (01 = sampled)
             версия
```
- в Go — **OpenTelemetry**: SDK создаёт спаны, `otelhttp` и `otelgrpc` автоматически оборачивают клиенты и серверы, `ctx` несёт текущий спан внутри процесса. Данные уходят в коллектор, а оттуда в Jaeger или Tempo
- **сэмплирование**: хранить 100% трейсов дорого. Берут, например, 1% плюс все ошибочные и медленные (tail sampling в коллекторе)

::: quiz choice q162-5
Сервис A вызывает B по HTTP, но в Jaeger трейсы A и B выглядят как два несвязанных запроса. Самая вероятная причина?
- [ ] у сервисов разные часы
- [x] HTTP-клиент A не передаёт заголовок `traceparent` (не обёрнут `otelhttp` или запрос создан без контекста)
- [ ] Jaeger не умеет склеивать HTTP-запросы
- [ ] B должен генерировать тот же span id, что и A
--- why
Связь трейсов держится только на передаче контекста: A кладёт `traceparent` в исходящий запрос, B его читает и создаёт дочерний спан с тем же trace id. Частая причина обрыва — `http.NewRequest` без `ctx` или голый `http.Client` без инструментирования.
:::

* `CounterVec` — счётчик с метками {TestCounterVec}
+ Map из строки-ключа значений меток (склей через `\x00`) в `*atomic.Uint64` или число под мьютексом. `With(values...)` проверяет число значений и возвращает объект с `Inc()` и `Add(n)`.
! Счётчик дёргают из многих горутин — тест запускается с `-race`.
* `Histogram` — корзины, сумма и количество {TestHistogram}
+ Отсортированные границы `bounds`, счётчик на каждую корзину плюс `+Inf`, `sum` и `count`. `Observe(v)` увеличивает первую корзину, где `v <= bound`, или `+Inf`.
! В выводе корзины **кумулятивные**: `le="0.5"` включает и всё, что попало в `le="0.1"`. Храни как удобно, но в `WriteText` складывай нарастающим итогом.
* `Registry.WriteText` — формат /metrics {TestExposition}
+ Для каждой метрики в порядке регистрации: `# HELP`, `# TYPE`, затем строки. У счётчика серии отсортированы по значениям меток: `name{a="x",b="y"} 5`. У гистограммы — строки `_bucket{le="..."}` по возрастанию и `le="+Inf"`, затем `_sum` и `_count`.
! Числа форматируй через `strconv.FormatFloat(v, 'g', -1, 64)`: тогда `0.1` останется `0.1`, а `5` — `5`.
* `Instrument` — RED-метрики для HTTP {TestInstrument}
+ Обёртка над хендлером: `statusRecorder`, после ответа `requests.With(r.Method, route, strconv.Itoa(status)).Inc()` и `duration.Observe(секунды)`. `route` — `r.Pattern` (шаблон маршрута, который заполняет ServeMux), если пустой — `"unmatched"`.
! `r.Pattern` заполняется, только когда запрос прошёл через `ServeMux`. Поэтому оборачивают mux целиком, а шаблон читают *после* `next.ServeHTTP`, из того же `*http.Request`.
* `ChildTraceparent ★` — разобрать и продолжить traceparent {TestTraceparent}
+ Формат `00-<32 hex>-<16 hex>-<2 hex>`. Проверь длины, что это hex и что trace id и span id не из одних нулей. Дочерний заголовок: тот же trace id и флаги, новый span id от `newSpanID()`.
! Невалидный или пустой заголовок — начать новый трейс: новый trace id от `newTraceID()`, флаги `01`.

## Вопросы с собеседования по уроку:
::: quiz open q162-6 собес
Как ты организуешь мониторинг и наблюдаемость сервиса?
--- answer
Три сигнала. Метрики (Prometheus): RED на каждый эндпоинт и консьюмер — rate, errors, duration гистограммой с перцентилями; USE для ресурсов (пул соединений к БД, очереди, горутины, GC, память). Метки только с низкой кардинальностью (шаблон маршрута, а не URL). Логи — структурированные JSON (slog) с request id и trace id, уровни, без персональных данных, централизованный сбор (Loki/ELK). Трейсы — OpenTelemetry с передачей контекста (traceparent) через HTTP, gRPC и брокеры, сэмплирование с сохранением ошибок и медленных запросов. Поверх — SLI/SLO (доступность и задержка), бюджет ошибок и алерты на симптомы через burn rate, дашборды RED, health/ready-пробы, pprof для разборов.
--- points
- метрики: RED и USE, histogram для задержек
- кардинальность меток
- структурированные логи с trace id
- трейсинг OpenTelemetry, traceparent, сэмплирование
- SLI/SLO, бюджет ошибок
- алерты на симптомы (burn rate)
:::

::: quiz open q162-7 собес
Почему для задержек смотрят перцентили, а не среднее? Чем histogram отличается от summary?
--- answer
Среднее скрывает распределение: редкие очень медленные запросы сдвигают среднее так, что оно не описывает ни типичный, ни худший опыт. Перцентили показывают: p50 — типичный запрос, p95/p99 — хвост, который при большом числе запросов задевает многих пользователей (особенно при fan-out, когда один ответ собирается из многих вызовов). Histogram в Prometheus считает наблюдения по заданным корзинам, а перцентили вычисляются на сервере через `histogram_quantile` приблизительно, с точностью до границ корзин. Зато гистограммы можно агрегировать между инстансами. Summary считает квантили в самом приложении точнее, но их нельзя корректно агрегировать, поэтому в распределённых системах предпочитают histogram (или native histograms).
--- points
- среднее скрывает хвост
- p50 и p99, влияние хвоста при fan-out
- histogram: корзины, histogram_quantile, агрегация
- summary: квантили в приложении, не агрегируются
:::
