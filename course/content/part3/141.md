# 14.1 Как устроены канал, мьютекс и модель памяти

## Модель памяти Go:
Процессор и компилятор переставляют операции ради скорости. В одной горутине это незаметно, но другая горутина без синхронизации может увидеть записи **в другом порядке или не увидеть вовсе**. Модель памяти отвечает на вопрос: когда запись в одной горутине гарантированно видна чтению в другой?

Ответ — через отношение **happens-before** («происходит раньше»). Его создают только синхронизирующие операции:
- отправка в канал happens-before завершения соответствующего получения
- `close(ch)` happens-before получения нулевого значения из закрытого канала
- n-й `Unlock` happens-before (n+1)-го `Lock`
- `once.Do(f)`: завершение `f` happens-before возврата любого `Do`
- атомарные операции из `sync/atomic` (с Go 1.19 официально последовательно согласованы)
- `wg.Done()` happens-before возврата `wg.Wait()`

Если две горутины обращаются к переменной, хотя бы одна пишет, и между ними нет happens-before, это **data race**, и результат не определён. «Безобидных гонок» не бывает: компилятор вправе, например, вынести чтение флага из цикла.

::: quiz output q141-1 собес
Гарантирован ли вывод?
```go
package main

import "fmt"

func main() {
	var msg string
	done := make(chan struct{})
	go func() {
		msg = "привет"
		close(done)
	}()
	<-done
	fmt.Println(msg)
}
```
--- answer
привет
--- why
Запись `msg` идёт до `close(done)` в той же горутине. `close` happens-before завершения `<-done`, а оно — до `Println`. Цепочка замкнулась, поэтому запись гарантированно видна. Без канала это была бы гонка.
:::

## Канал изнутри:
`make(chan T, n)` создаёт в куче структуру `hchan`:
```go
type hchan struct {
    qcount   uint           // сколько элементов в буфере
    dataqsiz uint           // размер буфера (cap)
    buf      unsafe.Pointer // кольцевой буфер на dataqsiz элементов
    sendx    uint           // куда писать
    recvx    uint           // откуда читать
    recvq    waitq          // очередь ждущих получателей (sudog)
    sendq    waitq          // очередь ждущих отправителей
    closed   uint32
    lock     mutex          // все операции — под этим замком
}
```
**Отправка:**
1. если в `recvq` ждёт получатель — значение копируется **прямо в его стек**, буфер не используется, получатель будится
2. иначе, если в буфере есть место — кладём в `buf[sendx]`
3. иначе горутина заворачивается в `sudog`, встаёт в `sendq` и паркуется

**select:** перебирает case в **случайном порядке** (чтобы никто не голодал), блокирует все каналы и берёт первый готовый. Если готовых нет, ставит горутину в очереди всех каналов сразу и паркует. Проснувшись, убирает себя из остальных очередей.

## Mutex изнутри:
`sync.Mutex` — одно 32-битное слово состояния (заблокирован, есть разбуженный, режим голодания, число ждущих) плюс семафор для парковки.
- **быстрый путь**: свободен — захватить одной атомарной CAS-операцией
- **спиннинг**: на многоядерной машине горутина несколько раз «крутится», надеясь, что держатель скоро отпустит. Это дешевле, чем засыпать
- **нормальный режим**: проснувшаяся горутина соревнуется с только что пришедшими, и новенькие часто выигрывают: они уже на CPU. Так выше пропускная способность
- **режим голодания**: если кто-то ждёт дольше **1 мс**, мьютекс переходит в строгую очередь FIFO и передаётся напрямую первому ждущему. Когда очередь рассосалась, режим возвращается в нормальный

**RWMutex:** много читателей или один писатель. Когда писатель ждёт `Lock`, **новые читатели тоже ждут**, иначе писатель голодал бы вечно. Отсюда ловушка: повторный `RLock` в той же горутине, пока ждёт писатель, — дедлок.

::: quiz choice q141-4 собес
Что такое режим голодания (starvation mode) у `sync.Mutex`?
- [ ] режим, в котором мьютекс отключает спиннинг навсегда
- [x] если горутина ждёт мьютекс дольше 1 мс, он передаётся ждущим строго по очереди, без конкуренции с новичками
- [ ] режим, когда мьютекс никому не отдаётся, пока не вызовут Unlock дважды
- [ ] паника при слишком долгом ожидании
--- why
Нормальный режим быстрее, но несправедлив: новички на CPU обгоняют разбуженных. Режим голодания включается, чтобы хвост очереди не ждал вечно, и выключается, когда ждать некому.
:::

## Атомики и CAS:
```go
var hits atomic.Int64
hits.Add(1)

// CAS-цикл: обновить, только если никто не успел раньше
for {
    old := maxSeen.Load()
    if v <= old || maxSeen.CompareAndSwap(old, v) {
        break
    }
}
```
**Ложное разделение (false sharing):** два счётчика, которые обновляют разные ядра, лежат в одной кэш-линии (64 байта), и ядра постоянно отбирают её друг у друга. Лечится выравниванием (`_ [56]byte` между полями) или шардированием счётчиков.

::: hw 141
* `SpinLock` — замок на CAS {TestSpinLock}
+ Поле `atomic.Bool`. `Lock`: крутись, пока `CompareAndSwap(false, true)` не вернёт true, внутри цикла вызывай `runtime.Gosched()`, чтобы уступить P. `Unlock`: `Store(false)`.
! Без `Gosched` на GOMAXPROCS=1 держатель замка может никогда не получить процессор.
* `StoreMax` — атомарный максимум {TestStoreMax}
+ CAS-цикл из теории: прочитай текущее значение, и если новое больше, попробуй `CompareAndSwap`. Не вышло — кто-то успел, повтори.
! `if v > a.Load() { a.Store(v) }` — гонка: между Load и Store другой может записать большее значение, и ты его затрёшь.
* `Semaphore` — семафор с отменой через ctx {TestSemaphore}
+ Буферизованный канал на n мест. `Acquire`: `select` между `s.ch <- struct{}{}` и `<-ctx.Done()`. `Release`: `<-s.ch`.
* `OnceErr` — «один раз, но до первого успеха» {TestOnceErr}
+ Мьютекс и флаг `done`. `Do` берёт мьютекс. Если `done`, вернуть nil. Иначе вызвать `f`: при успехе поставить `done = true`. Параллельные вызовы ждут на мьютексе.
! В отличие от `sync.Once`, после ошибки следующий `Do` должен попробовать снова.
* `Barrier ★` — точка сбора на n горутин, многоразовая {TestBarrier}
+ `sync.Mutex` + `sync.Cond` + счётчик + номер «поколения». Пришедший увеличивает счётчик. Если он последний (n-й), сбрасывает счётчик, увеличивает поколение и делает `Broadcast`. Остальные ждут `for gen == myGen { cond.Wait() }`.
! Без поколения многоразовый барьер ломается: быстрая горутина из следующего раунда может «съесть» сигнал предыдущего.
:::

## Вопросы с собеседования по уроку:
::: quiz open q141-5 собес
Как устроен канал в Go?
--- answer
Канал — указатель на структуру `hchan` в куче. В ней кольцевой буфер (`buf`, `dataqsiz`, `qcount`, индексы `sendx`/`recvx`), очереди ожидающих отправителей и получателей (`sendq`, `recvq` из структур `sudog`), флаг закрытия и мьютекс, под которым выполняются все операции. Отправка: если есть ждущий получатель, значение копируется напрямую в его стек и он будится; иначе, если есть место в буфере, значение кладётся в буфер; иначе горутина паркуется в `sendq`. Получение симметрично. Закрытие будит всех ждущих: получатели получают нулевые значения, отправители паникуют. `select` перебирает case в случайном порядке, блокирует каналы, берёт готовый или паркуется сразу во всех очередях.
--- points
- hchan в куче, мьютекс внутри
- кольцевой буфер с индексами
- очереди sendq / recvq из sudog
- прямая передача ждущему получателю
- закрытие будит всех
- select: случайный порядок, парковка во всех очередях
:::

::: quiz open q141-6 собес
Как работает sync.Mutex? Чем от него отличается RWMutex и когда его использовать?
--- answer
Mutex — слово состояния плюс семафор. Захват свободного мьютекса — одна CAS-операция. При конкуренции горутина немного крутится (spinning), потом паркуется. В нормальном режиме разбуженная горутина соревнуется с новичками, что повышает пропускную способность. Если ожидание превышает 1 мс, включается режим голодания со строгой передачей FIFO. RWMutex допускает много одновременных читателей (RLock) или одного писателя (Lock). Ждущий писатель блокирует новых читателей, чтобы не голодать. Использовать RWMutex имеет смысл, когда чтений намного больше, чем записей, и критическая секция чтения не крошечная: иначе накладные расходы RWMutex больше выигрыша. Ловушки: рекурсивный RLock при ждущем писателе — дедлок; копирование мьютекса (go vet copylocks); забытый Unlock на одном из путей — используйте defer.
--- points
- CAS-захват, спиннинг, парковка
- нормальный режим и режим голодания (1 мс)
- RWMutex: много читателей или один писатель
- писатель блокирует новых читателей
- когда выгоден RWMutex
- ловушки: рекурсивный RLock, копирование, забытый Unlock
:::

::: quiz open q141-7 собес
Что такое модель памяти Go и отношение happens-before?
--- answer
Модель памяти определяет, при каких условиях чтение переменной в одной горутине гарантированно увидит запись в другой. Внутри горутины действует порядок программы, а между горутинами гарантии дают только синхронизирующие операции, которые устанавливают happens-before: отправка в канал до завершения получения, close до получения нулевого значения, Unlock до следующего Lock, завершение функции в Once.Do до возврата Do, wg.Done до возврата Wait, атомарные операции. Если между записью и чтением нет такой цепочки, это data race с неопределённым поведением: компилятор и процессор могут переупорядочить или кэшировать операции, поэтому «безобидных» гонок не бывает.
--- points
- зачем: видимость записей между горутинами
- happens-before и его источники: каналы, мьютексы, Once, WaitGroup, атомики
- без синхронизации — data race
- компилятор и CPU переупорядочивают операции
:::
