# 14.2 Паттерны конкурентности уровня middle

## Cache stampede и singleflight:
Объявление с главной страницы смотрят 10 000 раз в секунду, оно лежит в кэше. Кэш истёк, и в ту же миллисекунду **тысяча** запросов промахивается и идёт в базу за одним и тем же. База ложится. Это **cache stampede** (эффект толпы).

**singleflight** склеивает одновременные запросы с одним ключом: первый идёт в базу, остальные ждут его результата.
```go
var g singleflight.Group // golang.org/x/sync/singleflight

func (s *Service) Ad(ctx context.Context, id int64) (Ad, error) {
    if ad, ok := s.cache.Get(id); ok {
        return ad, nil
    }
    v, err, _ := g.Do(strconv.FormatInt(id, 10), func() (any, error) {
        ad, err := s.db.Get(ctx, id)   // выполнится один раз на всю толпу
        if err == nil {
            s.cache.Set(id, ad, time.Minute)
        }
        return ad, err
    })
    if err != nil {
        return Ad{}, err
    }
    return v.(Ad), nil
}
```
Другие защиты: небольшой случайный разброс TTL (чтобы ключи не истекали одновременно), фоновое обновление до истечения, отдача устаревшего значения, пока идёт обновление (stale-while-revalidate).

## Шардирование замка (lock striping):
Одна `map` под одним мьютексом при высокой нагрузке становится узким местом: все ждут один замок. Решение — N независимых шардов, каждый со своим мьютексом. Шард выбирается по хешу ключа:
```go
type Sharded struct{ shards [32]shard }
type shard struct {
    mu sync.RWMutex
    m  map[string]entry
}
func (c *Sharded) shard(key string) *shard {
    h := fnv.New32a()
    h.Write([]byte(key))
    return &c.shards[h.Sum32()%32]
}
```
Конкуренция за замок падает примерно в N раз. Так устроены многие in-memory кэши (bigcache, ristretto).

## Копирование при записи (copy-on-write):
Конфиг читают на каждом запросе, а меняют раз в час. Мьютекс на каждое чтение — лишнее. Храни указатель на **неизменяемый** снимок и подменяй его целиком:
```go
var cfg atomic.Pointer[Config]
cfg.Store(&Config{Limit: 100})
c := cfg.Load()                   // чтение — одна атомарная операция, без блокировок
newCfg := *c; newCfg.Limit = 200  // меняем копию
cfg.Store(&newCfg)                // и атомарно подменяем
```
Если писателей несколько, подмену делают CAS-циклом, иначе одно обновление затрёт другое. Это задача ★ в домашке.

## Медленные подписчики и backpressure:
Издатель рассылает события подписчикам через каналы. Один подписчик тормозит. Если отправлять блокирующе, весь издатель встанет из-за одного медленного. Варианты политики:
- **drop** — неблокирующая отправка (`select` с `default`), событие для медленного подписчика теряется, растёт счётчик потерь
- **буфер** — терпим временные всплески
- **отключить** медленного подписчика
- **backpressure** — замедлить источник: ограниченная очередь, а при переполнении ответ `429`/`503` или блокировка отправителя

Выбор зависит от смысла данных: котировки можно терять (придут новые), платежи — нет.

## Дедлоки:
Условия дедлока: взаимное исключение, удержание с ожиданием, нельзя отобрать, **циклическое ожидание**. Самый частый случай — два мьютекса в разном порядке:
```go
// горутина 1: a.mu.Lock(); b.mu.Lock()   — перевод a → b
// горутина 2: b.mu.Lock(); a.mu.Lock()   — перевод b → a
```
Лечение — **единый порядок захвата** (например, по возрастанию id счёта), короткие критические секции, никаких внешних вызовов под замком, `TryLock` или таймауты там, где это допустимо. Рантайм Go ловит дедлок, только если спят *все* горутины. В сервере с HTTP-листенером такого не бывает, поэтому зависание выглядит как молчаливый рост числа горутин.

::: quiz output q142-2 собес
Счётчик посещений:
```go
package main

import (
	"fmt"
	"sync"
)

type Counter struct {
	mu sync.Mutex
	n  int
}

func (c Counter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n++
}

func main() {
	var c Counter
	for range 3 {
		c.Inc()
	}
	fmt.Println(c.n)
}
```
--- answer
0
--- why
Получатель — значение, поэтому каждый `Inc` работает с копией структуры, включая копию мьютекса. Счётчик оригинала не меняется. `go vet` предупредит: «Inc passes lock by value». Структуры с мьютексом используют только по указателю: `func (c *Counter) Inc()`.

::: quiz choice q142-3
Перевод между счетами иногда навсегда зависает под нагрузкой. Код: `from.mu.Lock(); to.mu.Lock(); ...`. Как исправить надёжнее всего?
- [ ] поменять порядок: сначала `to`, потом `from`
- [x] всегда захватывать мьютексы в одном порядке, например сначала счёт с меньшим id
- [ ] заменить Mutex на RWMutex
- [ ] добавить `time.Sleep` между захватами
--- why
Перевод A→B и одновременный перевод B→A захватывают замки в противоположном порядке и ждут друг друга. Перестановка внутри функции ничего не меняет: встречный перевод перевернётся так же. Только глобальный порядок (по id) разрывает цикл.

::: quiz design q142-4
Сервис объявлений получает 20 000 RPS, 30% запросов — к десяти самым популярным объявлениям. Кэш в Redis с TTL 60 секунд. Каждую минуту на графиках видны всплески нагрузки на PostgreSQL и рост задержек. Что происходит и что предложишь?
--- answer
Горячие ключи истекают одновременно, и каждый раз тысячи запросов промахиваются и идут в базу: cache stampede. Что предложить, по нарастанию сложности:
- склейка запросов singleflight на каждом инстансе (из N инстансов в базу придёт N запросов вместо тысяч)
- случайный разброс TTL (60 ± 10 с), чтобы ключи не истекали синхронно
- раннее вероятностное обновление: чем ближе истечение, тем выше шанс, что запрос обновит значение заранее
- stale-while-revalidate: отдавать старое значение, пока одна горутина обновляет
- распределённая блокировка на перестроение ключа (SET NX в Redis), если инстансов много
- для самых горячих ключей — локальный in-memory кэш на 1–5 секунд перед Redis, это снимает и нагрузку на сам Redis

Проверить гипотезу можно по метрикам cache miss rate и запросам к БД, сгруппированным по ключу.
--- points
- диагноз: одновременное истечение горячих ключей, stampede
- singleflight
- разброс TTL
- раннее обновление или stale-while-revalidate
- блокировка на перестроение ключа
- локальный кэш для горячих ключей, подтверждение метриками
:::

* `Group.Do` — свой singleflight {TestSingleflight}
+ Map из ключа в «вызов в процессе» (`*call` с `sync.WaitGroup`, результатом и ошибкой) под мьютексом. Если вызов уже идёт, отпусти мьютекс и жди `c.wg.Wait()`. Иначе создай `call`, выполни `fn`, сохрани результат, удали ключ из map и сделай `wg.Done()`.
! Ключ удаляется после завершения, иначе следующие запросы получат старый результат навсегда. Третий результат `shared` — true, если результатом поделились с кем-то ещё.
* `Cache` — шардированный кэш с TTL {TestShardedCache}
+ 16 шардов, каждый — `sync.RWMutex` + `map[string]entry{val, expires}`. Шард выбирай по `fnv.New32a`. В `Get` просроченная запись считается отсутствующей. Время — только через переданный `now()`.
! `Len` считает только живые записи. Просроченные можно не удалять сразу, но и не считать.
* `Broker` — pub/sub с отбрасыванием для медленных {TestBroker}
+ Подписчики — map с id → канал. `Publish` под `RLock` перебирает подписчиков и шлёт через `select` с `default`. При переполнении увеличивает `dropped` (atomic). `Subscribe` возвращает канал и функцию отписки, которая удаляет подписчика и закрывает его канал (один раз!).
! Нельзя закрывать канал, в который `Publish` может прямо сейчас писать: отписка берёт полный `Lock`, а `Publish` — `RLock`, так они не пересекаются.
* `KeyedMutex` — замок на ключ {TestKeyedMutex}
+ Map из ключа в `{mu sync.Mutex; refs int}` под общим мьютексом. `Lock(key)`: под общим замком найти или создать запись, `refs++`, отпустить общий замок и взять `entry.mu.Lock()`. Вернуть функцию, которая отпускает `entry.mu` и под общим замком делает `refs--`, удаляя запись при нуле.
! Если не удалять записи, map будет расти бесконечно, и тест это проверяет. Если брать `entry.mu` под общим замком, разные ключи начнут блокировать друг друга.
* `ConfigStore.Update ★` — copy-on-write с CAS {TestConfigUpdate}
+ `atomic.Pointer[Config]`. `Update` в цикле: `old := s.p.Load()`, `n := f(*old)` (копия!), `if s.p.CompareAndSwap(old, &n) { return }`.
! `Load` — изменение — `Store` без CAS потеряет обновления при параллельной записи: тест делает 200 одновременных инкрементов.

## Вопросы с собеседования по уроку:
::: quiz open q142-5 собес
Что такое дедлок? Как его избежать и как найти в Go-программе?
--- answer
Дедлок — ситуация, когда горутины бесконечно ждут друг друга (например, каждая держит ресурс, нужный другой). Необходимые условия: взаимное исключение, удержание с ожиданием, невозможность отобрать ресурс, циклическое ожидание. Избежать: единый глобальный порядок захвата блокировок, минимальные критические секции без вызовов чужого кода и I/O под замком, defer Unlock, неблокирующие операции с каналами (select с default или таймаутом), контексты с дедлайнами, понятное владение каналами (кто закрывает). В Go рантайм сообщает «all goroutines are asleep - deadlock!», только если заблокированы все горутины. В сервисах дедлок проявляется как зависшие запросы и рост числа горутин. Диагностика: профиль goroutine (pprof) или дамп стеков по SIGQUIT, где видно, какие горутины ждут Lock или каналы.
--- points
- определение и условия (циклическое ожидание)
- единый порядок захвата
- короткие критические секции, defer Unlock
- таймауты и контексты, select с default
- рантайм ловит только полный дедлок
- диагностика через goroutine-профиль или SIGQUIT
:::

::: quiz open q142-6 собес
Как бы ты реализовал потокобезопасный кэш в памяти для высоконагруженного сервиса?
--- answer
Базовый вариант — map под `sync.RWMutex`: чтения не блокируют друг друга. При высокой конкуренции — шардирование: N шардов со своими замками, шард по хешу ключа, что снижает конкуренцию за замок. TTL — время истечения в записи, проверка при чтении и фоновая очистка тикером (с остановкой по контексту). Ограничение размера — LRU/LFU-вытеснение (list + map) или готовые библиотеки (ristretto, bigcache: меньше нагрузки на GC за счёт хранения байтов без указателей). Против stampede — singleflight на загрузку. Метрики: hit/miss, размер, вытеснения. `sync.Map` подходит, когда ключи пишутся один раз и много читаются. Важно учитывать согласованность с источником: инвалидация при изменениях, разброс TTL.
--- points
- RWMutex, затем шардирование
- TTL и фоновая очистка
- ограничение размера: LRU
- singleflight от stampede
- готовые библиотеки и нагрузка на GC
- метрики и инвалидация
:::
