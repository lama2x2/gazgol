# 16.1 Архитектура сервиса

## Слои и правило зависимостей:
Сервис растёт, и через год в хендлере оказываются SQL, бизнес-правила и отправка писем вперемешку. Чтобы так не случилось, код делят на слои с одним правилом: **зависимости направлены внутрь, к бизнес-логике**.
```text
transport (HTTP, gRPC, консьюмеры Kafka)     ← знает о сервисах
        │
service / usecase (бизнес-правила)            ← знает только о домене и интерфейсах
        │  интерфейсы, объявленные здесь
        ▼
domain (сущности, value objects, ошибки)      ← ни от кого не зависит
        ▲
repository / adapters (PostgreSQL, Redis, внешние API) ← реализуют интерфейсы сервиса
```
- бизнес-логика **не знает** про HTTP, SQL и JSON. Её можно вызвать из хендлера, из консьюмера Kafka, из CLI и из теста
- интерфейсы объявляет **потребитель** (сервис), реализации живут в адаптерах. Это «порты и адаптеры» (гексагональная архитектура), она же суть Clean Architecture
- в Go это делают прагматично: без десяти слоёв абстракций, но с чётким направлением зависимостей

## Пакеты: по фичам, а не по типам
```text
internal/
├── ad/            # всё про объявления: модель, сервис, интерфейсы хранилища, ошибки
├── wallet/
├── user/
├── postgres/      # адаптер: реализует ad.Repository, wallet.Repository...
└── httpapi/       # транспорт: хендлеры для всех фич
```
Пакеты `models/`, `services/`, `utils/` — антипаттерн: всё зависит от всего, и легко получить циклический импорт. А Go циклические импорты запрещает.

::: quiz choice q161-1 собес
Где должно проверяться бизнес-правило «нельзя купить собственное объявление»?
- [ ] в HTTP-хендлере: там есть id пользователя из токена
- [x] в сервисном слое: правило должно работать для любого транспорта
- [ ] в SQL-триггере
- [ ] в репозитории, рядом с запросом
--- why
Если правило живёт в хендлере, его обойдёт gRPC-ручка или консьюмер Kafka, написанные через полгода. Транспорт только переводит запрос в вызов сервиса и ошибку сервиса — в ответ. Ограничения в БД (CHECK, UNIQUE) хороши как последняя линия защиты, но правила с понятными ошибками для пользователя живут в сервисе.
:::

## Транзакции через несколько репозиториев:
Покупка трогает объявления и кошельки — два репозитория, а транзакция нужна одна. Частое решение — **менеджер транзакций**, который кладёт транзакцию в контекст:
```go
type TxManager interface {
    WithinTx(ctx context.Context, fn func(ctx context.Context) error) error
}

func (s *Service) Buy(ctx context.Context, buyerID, adID int64) error {
    err := s.tx.WithinTx(ctx, func(ctx context.Context) error {
        ad, err := s.ads.GetForUpdate(ctx, adID)   // репозиторий берёт tx из ctx
        ...
        return s.wallets.Transfer(ctx, buyerID, ad.SellerID, ad.Price)
    })
    if err != nil {
        return err
    }
    s.notifier.AdSold(ctx, adID)   // побочные эффекты — ПОСЛЕ коммита
    return nil
}
```
**Побочные эффекты снаружи транзакции:** письмо, отправленное изнутри транзакции, которая потом откатилась, уже не вернёшь. Если уведомление обязательно, его пишут в таблицу outbox в той же транзакции (модуль 17).

## Доменные ошибки и value objects:
- сервис возвращает **доменные ошибки** (`ad.ErrNotFound`, `ad.ErrAlreadySold`), а транспорт переводит их в статусы. В сервисе нет `http.StatusConflict`
- **value object** — маленький неизменяемый тип с правилами: `Price` не бывает отрицательной, `Email` всегда валиден. Проверка один раз — в конструкторе, дальше тип гарантирует корректность:
```go
type Price struct{ kopecks int64 }
func NewPrice(rub int64) (Price, error) { ... } // единственный способ получить Price
```

## SOLID по-гоферски:
- **S** — у пакета и типа одна причина меняться
- **O** — расширяем через новые реализации интерфейса, а не правкой `switch` по типам
- **L** — любая реализация интерфейса должна вести себя так, как ждёт потребитель (фейк в тестах тоже)
- **I** — маленькие интерфейсы у потребителя: хендлеру нужен `Buyer` с одним методом, а не весь сервис
- **D** — сервис зависит от интерфейсов, конкретные реализации подставляет `main`

::: quiz review q161-2
Код-ревью: что не так с архитектурой этого хендлера?
```go
func (h *Handler) Buy(w http.ResponseWriter, r *http.Request) {
    adID, _ := strconv.ParseInt(r.PathValue("id"), 10, 64)
    userID := userFrom(r.Context())
    var price, seller int64
    h.db.QueryRow("SELECT price, user_id FROM ads WHERE id = $1", adID).Scan(&price, &seller)
    if seller == userID {
        http.Error(w, "own ad", 403)
        return
    }
    tx, _ := h.db.Begin()
    tx.Exec("UPDATE wallets SET balance = balance - $1 WHERE user_id = $2", price, userID)
    tx.Exec("UPDATE wallets SET balance = balance + $1 WHERE user_id = $2", price, seller)
    smtp.SendMail(h.smtpAddr, nil, "noreply@b.ru", []string{sellerEmail(seller)}, []byte("Продано!"))
    tx.Exec("UPDATE ads SET status = 'sold' WHERE id = $1", adID)
    tx.Commit()
    w.WriteHeader(200)
}
```
--- answer
1. Бизнес-логика, SQL и транспорт в одном месте: правило «нельзя купить своё» и сама покупка не переиспользуются и не тестируются без базы и HTTP.
2. Чтение цены и продавца — вне транзакции, без блокировки строки: гонка, два покупателя купят одно объявление. Нет проверки статуса «уже продано».
3. Все ошибки проигнорированы (`ParseInt`, `Scan`, `Begin`, `Exec`, `Commit`): при сбое пользователь получит 200, а деньги могут уйти частично. Нет `defer tx.Rollback()`.
4. Письмо отправляется изнутри транзакции: при откате продавец получит «Продано!», а сетевой вызов держит транзакцию открытой.
5. Не проверяется достаточность баланса.
6. Нет контекста в запросах (`QueryRowContext`).

Как исправить: сервис `Buy` с репозиториями и менеджером транзакций, блокировка строки или условный UPDATE, уведомление после коммита через outbox, а хендлер только парсит, вызывает сервис и отображает доменные ошибки в статусы.
--- points
- логика, SQL и HTTP смешаны, не тестируется
- чтение вне транзакции: гонка двойной продажи
- все ошибки проигнорированы, нет Rollback
- внешний вызов (почта) внутри транзакции
- нет проверки баланса и статуса
- без контекста
:::

* `BuyHandler` — тонкий транспорт {TestBuyHandler}

! Хендлер получает интерфейс `Buyer`, а не `*Service`: в тесте подставляется фейк.
* `Price` — value object {TestPrice}
+ Храни копейки (`int64`). `NewPrice(rub)` возвращает ошибку для отрицательной суммы. `String()` форматирует с разделением тысяч пробелом: `1 500 ₽`, `12 000 000 ₽`, `0 ₽`.
! Поле с маленькой буквы: снаружи пакета нельзя создать `Price{-5}` в обход конструктора.
* `Buy` идемпотентна по requestID ★ {TestBuyIdempotent}
+ Перед транзакцией проверь `s.Requests.Seen(ctx, requestID)`: уже обработан — вернуть сохранённый результат (nil или ошибку). После покупки — `s.Requests.Save(ctx, requestID, err)`.
! Сохраняй результат и для успеха, и для бизнес-ошибки: повтор должен получить тот же ответ, а деньги не должны списаться дважды. Сохранение лучше делать внутри той же транзакции (в фейке это видно по контексту).

## Вопросы с собеседования по уроку:
::: quiz open q161-3 собес
Как ты организуешь слои в Go-сервисе? Что такое чистая (гексагональная) архитектура?
--- answer
Делю на транспорт (HTTP/gRPC/консьюмеры), бизнес-логику (сервисы/usecase с доменными сущностями, value objects и ошибками) и адаптеры инфраструктуры (репозитории БД, клиенты внешних API, брокеры). Главное — правило зависимостей: внутренние слои не знают о внешних. Сервис объявляет нужные ему интерфейсы (порты), а адаптеры их реализуют. Это и есть гексагональная архитектура или Clean Architecture в прагматичном варианте. Транспорт переводит запрос в вызов сервиса и доменную ошибку в код ответа. Транзакции через несколько репозиториев — менеджером транзакций в сервисном слое, побочные эффекты — после коммита или через outbox. Зависимости собираются вручную в main (или wire/fx). Пакеты по фичам, без util/models. Плюсы: тестируемость сервисов на фейках, замена транспорта или БД без переписывания логики. Минус — больше кода, поэтому без фанатизма.
--- points
- слои: транспорт, сервис/домен, адаптеры
- правило зависимостей внутрь
- интерфейсы у потребителя (порты), реализации в адаптерах
- доменные ошибки → коды в транспорте
- транзакции в сервисе, побочные эффекты после коммита
- DI в main, пакеты по фичам; тестируемость
:::

::: quiz open q161-4 собес
Как в Go применяются принципы SOLID?
--- answer
Single responsibility — пакет и тип решают одну задачу: хендлер не ходит в SQL, репозиторий не содержит бизнес-правил. Open/closed — поведение расширяется новыми реализациями интерфейсов (новый способ доставки, новый провайдер платежей), а не правкой switch по типам. Liskov — любая реализация интерфейса должна соблюдать его контракт, включая ошибки и граничные случаи. Это важно для фейков в тестах. Interface segregation — в Go особенно естественно: маленькие интерфейсы у потребителя (io.Reader, Buyer с одним методом). Dependency inversion — сервисы зависят от интерфейсов, конкретные реализации внедряются через конструкторы в main. Плюс идиомы Go: «accept interfaces, return structs», композиция через встраивание вместо наследования.
--- points
- SRP — разделение ответственности по слоям и пакетам
- OCP — расширение через новые реализации
- LSP — контракт интерфейса, фейки
- ISP — маленькие интерфейсы у потребителя
- DIP — зависимость от интерфейсов, DI в main
:::
