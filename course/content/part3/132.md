# 13.2 Память, GC и профилирование

## Стек и куча:
| | Стек | Куча |
|---|---|---|
| чей | у каждой горутины свой | общая для всей программы |
| выделение | сдвинуть указатель, почти бесплатно | через аллокатор, дороже |
| освобождение | автоматически при выходе из функции | сборщиком мусора |
| что там живёт | локальные переменные, которые не «убегают» | всё, что переживает функцию или размер неизвестен |

В Go ты не выбираешь, где жить переменной: решает компилятор с помощью **escape analysis**. Если он может доказать, что значение не нужно после выхода из функции, оно живёт на стеке. Иначе «убегает» в кучу.

## Когда значение убегает в кучу:
```go
func newAd() *Ad {
    ad := Ad{Title: "Шкаф"}
    return &ad              // указатель переживёт функцию → куча
}

fmt.Println(x)              // аргументы ...any: значение упаковывается в интерфейс → часто куча
s := make([]int, n)         // размер неизвестен при компиляции → куча
var global *Ad; global = &ad // сохранили в глобальную → куча
go func() { use(ad) }()     // захват в горутине, которая живёт дольше → куча
```
Посмотреть решения компилятора:
```bash
go build -gcflags=-m ./...
# ./ad.go:12:2: moved to heap: ad
# ./ad.go:20:13: ... argument does not escape
```
Аллокация сама по себе — не беда. Беда — миллионы мелких аллокаций в горячем цикле: они нагружают аллокатор и GC.

::: quiz choice q132-1 собес
Какие из этих значений, скорее всего, окажутся в куче? Выбери все.
- [x] `ad` в `func f() *Ad { ad := Ad{}; return &ad }`
- [ ] `buf` в `func f() int { var buf [64]byte; return len(buf) }`
- [x] срез из `make([]byte, n)`, где `n` — параметр функции
- [x] `p` в `cache[id] = &p`, где `cache` — глобальная map

--- why
Массив фиксированного размера, который не покидает функцию, и обычные числа живут на стеке. Указатель наружу, глобальное хранение и размер, известный только во время выполнения, отправляют значение в кучу.
:::

## Выравнивание структур:
Поля выравниваются по своему размеру: `int64` начинается с адреса, кратного 8. Между полями появляется «пустота» (padding):
::: quiz output q132-2 собес
Размеры структур:
```go
package main

import (
	"fmt"
	"unsafe"
)

type A struct {
	a bool
	b int64
	c bool
}

type B struct {
	b int64
	a bool
	c bool
}

func main() {
	fmt.Println(unsafe.Sizeof(A{}), unsafe.Sizeof(B{}))
}
```
--- answer
24 16
--- why
В `A`: bool (1) + 7 пустых байтов, чтобы int64 начался с кратного 8, + int64 (8) + bool (1) + 7 пустых до кратного 8 = 24. В `B` два bool идут подряд после int64: 8 + 2 + 6 = 16. Правило: поля от больших к маленьким. Для миллиона объектов в памяти это 8 МБ разницы. Линтер `fieldalignment` подскажет сам.
:::

## Сборщик мусора Go:
**Конкурентный, неперемещающий, непоколенческий mark-and-sweep с трёхцветной маркировкой.**
1. **Mark setup** — короткая остановка мира (STW, десятки микросекунд): включается барьер записи
2. **Маркировка** идёт *параллельно* с программой (подробности ниже)
3. **Mark termination** — снова короткая STW
4. **Sweep** — белые объекты освобождаются, понемногу и параллельно с работой программы

Трёхцветная маркировка делит объекты на три цвета:
- **белые** — ещё не проверены, кандидаты на удаление
- **серые** — достижимы, но их ссылки ещё не просмотрены
- **чёрные** — достижимы, ссылки просмотрены

Начинаем с корней (стеки горутин, глобальные переменные), красим их в серый и обходим, пока серых не останется. **Барьер записи** следит, чтобы программа, меняющая указатели во время маркировки, не спрятала живой объект от GC.

Чтобы GC успевал, горутины, которые много аллоцируют, привлекаются к маркировке (*mark assist*). Это видно как рост задержек при частых аллокациях.

## Когда запускается GC и как им управлять:
- **GOGC** (по умолчанию 100): следующий цикл начнётся, когда куча вырастет на 100% от живых данных после прошлого цикла. 50 — чаще и экономнее по памяти, 200 — реже и больше памяти
- **GOMEMLIMIT** (Go 1.19+) — мягкий лимит памяти: при приближении к нему GC работает активнее. В контейнере ставят чуть ниже лимита пода, чтобы не получить OOMKilled
- **выключить**: `GOGC=off` или `debug.SetGCPercent(-1)`. Разумно только вместе с `GOMEMLIMIT` или для коротких утилит
- стоимость маркировки пропорциональна числу **живых указателей**: `map[int]Ad` дешевле для GC, чем `map[int]*Ad`

::: quiz choice q132-3 собес
Что значит `GOGC=100`?
- [ ] GC запускается каждые 100 мс
- [ ] GC может использовать до 100% CPU
- [x] следующий цикл GC стартует, когда куча вырастет вдвое относительно живых данных после предыдущего
- [ ] куча ограничена 100 МБ
--- why
GOGC — процент прироста кучи между циклами. Живых данных 200 МБ при GOGC=100 — GC начнётся примерно на 400 МБ. Это компромисс между памятью и временем CPU на сборку.
:::

## Как уменьшить нагрузку на память:
- меньше аллокаций в горячем пути: заранее выделенные `make(..., 0, n)`, `strings.Builder` с `Grow`, `strconv.Append*` вместо `fmt.Sprintf`
- переиспользование временных объектов через `sync.Pool` (буферы, энкодеры). Пул может очищаться при каждом GC, поэтому это кэш, а не хранилище
- значения вместо указателей в больших коллекциях: меньше работы для GC
- не держать огромные массивы через маленькие слайсы (пример из 7.1)

## Профилирование: сначала измерь
Оптимизация без профиля — гадание. В Go всё есть из коробки:
```go
import _ "net/http/pprof"     // регистрирует /debug/pprof/* в DefaultServeMux
go http.ListenAndServe("localhost:6060", nil) // отдельный порт, наружу не открывать!
```
```bash
go tool pprof -http=:8081 http://localhost:6060/debug/pprof/profile?seconds=30  # CPU
go tool pprof -http=:8081 http://localhost:6060/debug/pprof/heap                 # память
curl 'localhost:6060/debug/pprof/goroutine?debug=1'                             # горутины
go test -bench=. -benchmem -cpuprofile=cpu.out -memprofile=mem.out              # в бенчмарках
```
| Профиль | Что показывает |
|---|---|
| `profile` (CPU) | где тратится процессорное время |
| `heap` | `inuse` — кто держит память сейчас, `alloc` — кто больше всего аллоцировал |
| `goroutine` | стеки всех горутин: утечки, зависания |
| `block` / `mutex` | где горутины ждут каналы и мьютексы (включаются отдельно) |
| `trace` | хронология: планировщик, GC-паузы, задержки отдельных запросов |

**Flame graph** — главный способ смотреть: ширина полосы — доля времени. Ищи широкие «плато» в своём коде.

Сравнивать бенчмарки «до» и «после» — `benchstat`: он учитывает разброс и скажет, значима ли разница. **PGO** (Go 1.21+): положи CPU-профиль с прода в `default.pgo`, и компилятор оптимизирует горячие пути (обычно +2–14%).

::: quiz choice q132-4
Задержка p99 выросла с 50 до 800 мс, а CPU сервиса — 15%. Какой инструмент поможет найти причину?
- [ ] CPU-профиль: он покажет медленную функцию
- [x] профили block/mutex и trace: похоже, горутины не работают, а ждут (блокировки, пул соединений, каналы)
- [ ] heap-профиль
- [ ] увеличить GOMAXPROCS и посмотреть, что изменится
--- why
Низкий CPU при высоких задержках значит, что время уходит на ожидание, а не на вычисления. CPU-профиль покажет только работу. Ожидание видно в block/mutex профилях и в трейсе. Частые виновники — мьютекс вокруг всего кэша и исчерпанный пул соединений к БД.
:::

## Вопросы с собеседования по уроку:
::: quiz open q132-6 собес
Как работает сборщик мусора в Go и как его оптимизировать?
--- answer
GC в Go — конкурентный трёхцветный mark-and-sweep, неперемещающий и непоколенческий. Цикл: короткая STW-пауза для включения барьера записи, затем конкурентная маркировка от корней (стеки, глобальные переменные) с раскраской белый/серый/чёрный, барьер записи не даёт программе «спрятать» объект во время маркировки. Аллоцирующие горутины помогают маркировать (mark assist). Потом короткая STW на завершение маркировки и ленивый конкурентный sweep белых объектов. Запуск регулирует pacer по GOGC (100 — при удвоении кучи относительно живых данных) и мягкий лимит GOMEMLIMIT. Выключить можно через GOGC=off или SetGCPercent(-1), обычно вместе с GOMEMLIMIT. Оптимизация: меньше аллокаций (prealloc, Builder, strconv.Append, переиспользование через sync.Pool), меньше указателей в больших структурах, настройка GOGC/GOMEMLIMIT под контейнер, и сначала — профилирование heap/alloc через pprof.
--- points
- конкурентный трёхцветный mark-and-sweep
- барьер записи и короткие STW-паузы
- mark assist
- GOGC и GOMEMLIMIT, можно выключить
- оптимизация: меньше аллокаций и указателей, sync.Pool
- сначала профилирование
:::

::: quiz open q132-7 собес
Что такое escape analysis? Чем отличаются стек и куча, и как понять, где окажется переменная?
--- answer
Стек — память горутины для локальных переменных, выделение и освобождение почти бесплатны и не требуют GC. Куча — общая память, выделение дороже, освобождает сборщик мусора. Escape analysis — анализ компилятора, который определяет, может ли значение пережить функцию или быть доступно извне. Если нет — оно размещается на стеке, иначе «убегает» в кучу. Типичные причины: возврат указателя на локальную переменную, сохранение в глобальную переменную или в структуру в куче, упаковка в интерфейс (в том числе аргументы fmt), захват замыканием, переживающим функцию, слайсы с размером, неизвестным на этапе компиляции, или слишком большие. Проверить: `go build -gcflags=-m`.
--- points
- стек: дёшево, без GC; куча: дороже, освобождает GC
- компилятор решает сам через escape analysis
- причины: возврат указателя, интерфейсы, замыкания, глобальные, динамический размер
- go build -gcflags=-m
:::

::: quiz open q132-8 собес
Что такое sync.Pool и когда его использовать?
--- answer
`sync.Pool` — потокобезопасный пул временных объектов для переиспользования между горутинами, чтобы сократить аллокации и нагрузку на GC. `Get` возвращает объект из пула (или создаёт через `New`), `Put` возвращает его обратно. Важные свойства: пул может быть очищен при любом GC (с 1.13 объекты переживают один цикл через victim cache), поэтому это не кэш с гарантией хранения. Объект нужно сбрасывать перед повторным использованием (`buf.Reset()`), не стоит класть огромные объекты, чтобы не держать лишнюю память. Используют для буферов (`bytes.Buffer`), энкодеров, временных структур в горячем пути; так сделаны fmt и encoding/json. Применять только после того, как профиль показал проблему с аллокациями.
--- points
- переиспользование временных объектов, меньше нагрузки на GC
- Get / Put / New
- может очищаться при GC — не хранилище
- сбрасывать состояние объекта
- применять по результатам профилирования
:::
