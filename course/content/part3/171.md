%% 17 | Распределённые системы
# 17.1 Взаимодействие сервисов и отказоустойчивость

## Сеть ненадёжна — заблуждения распределённых систем:
В монолите вызов функции либо работает, либо паникует. В микросервисах вызов через сеть может:
- не дойти до сервера
- дойти, выполниться, но ответ потеряется. **Клиент не знает, было ли действие выполнено**
- выполняться очень долго
- отказать частично: один из десяти инстансов тормозит

Все приёмы этого урока — ответы на эти ситуации: таймауты, повторы, идемпотентность, автоматические выключатели.

## REST и gRPC:
| | REST/JSON | gRPC/protobuf |
|---|---|---|
| формат | текст, читаемый | бинарный, компактный, быстрый |
| контракт | OpenAPI (часто необязательный) | `.proto`, из которого генерируется код клиента и сервера |
| транспорт | HTTP/1.1 или 2 | HTTP/2: мультиплексирование, стриминг в обе стороны |
| где | публичные API, браузер | общение сервисов внутри компании |
| дедлайны | вручную | встроены: дедлайн передаётся по цепочке вызовов |

```protobuf
syntax = "proto3";
service Ads {
  rpc GetAd(GetAdRequest) returns (Ad);
  rpc WatchPrices(WatchRequest) returns (stream PriceUpdate); // серверный стриминг
}
message Ad {
  int64 id = 1;      // номер поля — это и есть контракт в бинарном формате
  string title = 2;
  int64 price = 3;
  reserved 4;        // поле удалили — номер больше никогда не использовать
}
```
**Совместимость protobuf:** имена полей можно менять (в бинарном виде они не передаются), номера — никогда. Новые поля можно добавлять: старые клиенты их проигнорируют. Удалённые номера помечают `reserved`.

::: quiz choice q171-1 собес
Что сломает обратную совместимость protobuf-контракта? Выбери все.
- [ ] переименовать поле `title` в `name`, сохранив номер 2
- [x] поменять номер поля `price` с 3 на 5
- [ ] добавить новое поле `city = 6`
- [x] удалить поле 4 и позже использовать номер 4 для поля другого типа
- [x] изменить тип поля с `int64` на `string`
--- why
На проводе поле определяется номером и типом. Имена важны только для сгенерированного кода и JSON-маппинга. Повторное использование номера заставит старые сообщения неправильно разбираться новыми клиентами, поэтому и нужен `reserved`.
:::

## Таймауты и бюджет дедлайна:
**Таймаут должен быть у каждого сетевого вызова.** Без него зависший сосед подвешивает твои горутины, а потом и тебя.

Дедлайн передаётся по цепочке: пользователь ждёт 2 секунды, шлюз отдал тебе 1.5, ты тратишь 0.2 на свои дела, значит у вызова в платежи остаётся меньше 1.3 секунды. Если ты дашь ему свои стандартные 5 секунд, будешь ждать ответа, который уже никому не нужен. В Go `ctx` с дедлайном передаётся в HTTP- и gRPC-клиенты, и дедлайн уходит вниз сам. Если бюджета не осталось, лучше сразу отказать (fail fast), чем начинать работу.

## Повторы — осторожно:
- повторять можно только **идемпотентное** или с **ключом идемпотентности**
- повторять только **временные** ошибки: таймаут, 503, 429. Ошибки 400 и 404 не исправятся от повтора
- **экспоненциальная пауза с джиттером**: `random(0, min(max, base·2^n))`. Без случайности тысяча клиентов, упавших одновременно, будут повторять синхронно и добивать восстанавливающийся сервис
- **шторм повторов:** три слоя по 3 попытки каждый дают до 27 запросов на одно действие пользователя. Повторяют на одном уровне (обычно ближе к клиенту), остальные слои — нет, а ещё ограничивают долю повторов (*retry budget*: не больше 10% от потока)

::: quiz choice q171-2 собес
Зачем к экспоненциальной паузе между повторами добавляют случайный разброс (jitter)?
- [ ] чтобы повторы шли быстрее
- [x] чтобы клиенты, получившие ошибку одновременно, не повторяли тоже одновременно и не создавали волны нагрузки
- [ ] этого требует протокол HTTP/2
- [ ] чтобы обойти rate limiter
--- why
Без разброса все клиенты повторят ровно через 100 мс, потом через 200, потом через 400: синхронные волны, которые бьют по сервису именно тогда, когда он пытается подняться. Случайность размазывает нагрузку во времени.
:::

::: quiz bug q171-3
Сервис заказов вызывает платёжный сервис так. Иногда покупатели жалуются на двойное списание. Почему?
```go
for attempt := range 3 {
    resp, err := payments.Charge(ctx, &ChargeRequest{OrderID: id, Amount: total})
    if err == nil {
        return resp, nil
    }
    time.Sleep(time.Duration(attempt+1) * 200 * time.Millisecond)

```

- [x] при таймауте платёж мог пройти, а ответ потеряться; повтор создаёт второе списание, потому что запрос не идемпотентен — нужен ключ идемпотентности, по которому платёжка распознает повтор
- [ ] три попытки — слишком мало
- [ ] `OrderID` должен быть строкой
--- why
Неудача на клиенте ≠ неудача на сервере. Решение — ключ идемпотентности (например, `order_id` + номер попытки оплаты), который сервер платежей хранит вместе с результатом: повтор с тем же ключом вернёт сохранённый ответ, а не спишет снова. Ещё стоит повторять только временные ошибки и учитывать `ctx`.

## Circuit breaker — автоматический выключатель:
Сервис рекомендаций лёг. Каждый запрос к нему ждёт таймаут 1 секунду, горутины копятся, и мы падаем следом. Выключатель следит за ошибками и при их избытке **сразу** отказывает, давая соседу время подняться:
```text
        ошибок ≥ порога
CLOSED ───────────────────► OPEN ───── прошло openFor ─────► HALF-OPEN
  ▲   (запросы идут)         (сразу ErrOpen, вызова нет)       (пропускаем пробный запрос)
  │                                                               │
  └──────────────── пробный успешен ─────────────────────────────┤
                    пробный неуспешен → снова OPEN ◄──────────────┘
```
Вместе с ним используют **fallback** (рекомендаций нет — показываем популярные), **bulkhead** (отдельный пул горутин или соединений на каждую зависимость, чтобы одна медленная не съела все) и **load shedding** (при перегрузке сразу отвечаем 503, а не копим очередь).

::: quiz choice q171-4
Зачем выключателю состояние half-open?
- [ ] чтобы пропускать половину запросов всегда
- [x] чтобы после паузы осторожно проверить одним или несколькими пробными запросами, восстановился ли сервис, а не обрушивать на него весь поток сразу
- [ ] это состояние, в котором сервис перезапускается
- [ ] чтобы логировать ошибки
--- why
Если из OPEN сразу перейти в CLOSED, весь накопившийся поток ударит по едва поднявшемуся сервису и уронит его снова. Пробный запрос — дешёвая проверка.
:::

## Ключи идемпотентности:
Клиент генерирует уникальный ключ на *действие* (не на попытку) и шлёт его в заголовке `Idempotency-Key`. Сервер:
1. ключ новый — помечает «в работе», выполняет, сохраняет ответ (статус и тело) вместе с хешем запроса
2. ключ уже выполнен — возвращает сохранённый ответ, ничего не делая
3. ключ «в работе» (параллельный дубль) — 409, клиент повторит позже
4. тот же ключ, но другое тело запроса — 422: клиент ошибся

Хранить ключи — сутки или больше, в Redis или в той же БД, что и результат.

@@
::: hw 171
* `Backoff` — экспоненциальная пауза с полным джиттером {TestBackoff}
+ `cap := base << attempt` (следи за переполнением: если вышло больше `max` или стало отрицательным, бери `max`), затем `time.Duration(rnd() * float64(cap))`.
! `rnd` возвращает число от 0 до 1. Его передают параметром, чтобы тест был детерминированным.
* `Breaker` — автоматический выключатель с тремя состояниями {TestBreaker}
+ Поля: состояние, число подряд идущих ошибок, время открытия, флаг «пробный запрос уже идёт». `Call`: в OPEN, если `openFor` ещё не прошло, — `ErrOpen`; иначе перейти в HALF-OPEN и пропустить ровно один запрос. Успех в HALF-OPEN → CLOSED и сброс счётчика, ошибка → снова OPEN.
! Пока пробный запрос идёт, остальные получают `ErrOpen`. Состояние защищай мьютексом, но сам `fn` вызывай **без** мьютекса.
* `Retrier.Do` — повторы только временных ошибок и с учётом дедлайна {TestRetrier}
+ До `Attempts` попыток. Успех → nil. Ошибка не `ErrTemporary` (по `errors.Is`) → вернуть сразу. Перед паузой: если у `ctx` есть дедлайн и до него меньше, чем пауза, — вернуть последнюю ошибку, не засыпая. Пауза — через `r.Sleep(ctx, d)`, длина — `Backoff(attempt, ...)`.
! Тест подменяет `Sleep` и `Rand` и проверяет и число вызовов, и длительность пауз.
* `Idempotent` — middleware ключей идемпотентности {TestIdempotency}
+ Map ключ → запись `{inFlight bool; bodyHash; status; body}` под мьютексом. Без заголовка — пропустить как есть. Новый ключ: записать `inFlight`, выполнить хендлер с захватом статуса и тела (`httptest.NewRecorder` годится как буфер), сохранить, отдать клиенту. Повтор: тело отличается → 422, в работе → 409, готово → сохранённый ответ с заголовком `Idempotent-Replayed: true`.
! Тело запроса нужно прочитать для хеша и потом вернуть хендлеру: `r.Body = io.NopCloser(bytes.NewReader(b))`.
* `OutgoingTimeout ★` — сколько дать вызову вниз по цепочке {TestOutgoingTimeout}
+ Нет дедлайна у `ctx` → `max, true`. Иначе `left := time.Until(deadline) - reserve`. Если `left <= 0` → `0, false`, иначе `min(left, max), true`.
:::

## Вопросы с собеседования по уроку:
::: quiz open q171-5 собес
Как сделать взаимодействие микросервисов отказоустойчивым?
--- answer
Исходить из того, что сеть ненадёжна. Таймауты на каждый вызов и передача дедлайна по цепочке (ctx), fail fast при исчерпанном бюджете. Повторы только для временных ошибок, только идемпотентных операций или с ключом идемпотентности, с экспоненциальной паузой и джиттером, на одном уровне цепочки и с retry budget, чтобы не устроить шторм. Circuit breaker для быстрого отказа при падении зависимости и fallback (деградация функциональности). Bulkhead — изоляция пулов ресурсов по зависимостям. Rate limiting и load shedding на входе. Асинхронное взаимодействие через брокер там, где не нужен синхронный ответ. Health-проверки и балансировка, мониторинг ошибок и задержек по каждой зависимости, трейсинг. Тестирование отказов (chaos engineering).
--- points
- таймауты и передача дедлайна
- повторы: временные ошибки, идемпотентность, backoff + jitter, без шторма
- circuit breaker и fallback
- bulkhead, rate limiting, load shedding
- асинхронность через брокер
- наблюдаемость по зависимостям
:::

::: quiz open q171-6 собес
Что такое gRPC и чем он отличается от REST? Когда что выбрать?
--- answer
gRPC — RPC-фреймворк от Google поверх HTTP/2 с сериализацией Protocol Buffers. Контракт описывается в `.proto`, из него генерируются типизированные клиент и сервер для многих языков. Плюсы: компактный бинарный формат и высокая скорость, мультиплексирование HTTP/2, стриминг (серверный, клиентский, двунаправленный), встроенные дедлайны и их передача, стандартные коды статусов, перехватчики (interceptors) для логов, метрик и аутентификации. Минусы: не читается глазами, сложнее отлаживать (нужны grpcurl или evans), браузеру нужен gRPC-Web или шлюз, требуется дисциплина совместимости proto (номера полей). REST/JSON прост, понятен, кэшируется HTTP-инфраструктурой, удобен для публичных и браузерных API. Обычно выбирают gRPC для внутреннего взаимодействия сервисов, REST — для внешнего API (часто через grpc-gateway).
--- points
- HTTP/2 + protobuf + кодогенерация из .proto
- скорость, стриминг, дедлайны, перехватчики
- совместимость по номерам полей
- минусы: читаемость, браузер
- gRPC внутри, REST снаружи
:::
